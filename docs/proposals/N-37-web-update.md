# N-37 网页检查与触发更新，带排空

状态：实施中（已确认，U-98） · 范围已答（U-96） · 优先级：二 · 2026-11-07 · 相关：[12](../design/12-operations.md) 第 1、5 节、[部署指南](../guides/deployment.md)、[11](../design/11-web-ui.md)、U-29、U-48、U-96；取代 N-12

## 问题

更新现在只能在服务器终端里做：下载发布包、核对摘要、执行 `sudo maestroctl update <包>`（U-29）。管理员日常配置都在网页完成，唯独更新要登录服务器。有运行在执行时 `update` 只能拒绝或中断，想挑空闲时更新就得反复回来看；终端断线也可能打断更新命令。后两点就是暂缓的 N-12（U-48），与网页更新是同一件事的两半，本提案一起做，N-12 由本提案取代。

## 方案

### 1. 检查更新：只看 GitHub 正式版

- 获取源固定为 GitHub Releases 的正式版本（不含草稿与预发布），仓库在 `/etc/maestro/config.toml` 中配置，默认 `au12321ua/maestro`。网页不能修改获取源：它决定 root 会执行哪份代码（U-96）。
- 服务每天查询一次，管理员也可以在管理页点“检查更新”。走服务已有的代理设置（`/etc/maestro/environment`）。GitHub 匿名 API 每小时 60 次，够用，不需要令牌。
- 只有比当前安装版本新的正式版才提示，所以装着开发预览（`.dev`）的实例在下一个正式版出来前不会被提示“降级”。
- 管理页显示当前版本、最新正式版、发布说明链接，以及发布说明中的破坏性变更与“需要重新做首次准备”这类提示。查询失败只显示原因，不影响服务。
- 配置里可以关闭检查，关闭后网页不显示更新入口。

开发预览仍走现有渠道：从 Gitea 下载 `dev-` 包，`sudo maestroctl update <包>`。

### 2. 网页触发：排空后由 root 的更新任务执行

1. 管理员在管理页点“更新到 X”，确认发布说明后，服务进入**待更新**：排队照常受理，不再派发新运行；新的导入、首次准备等 Operation 拒绝启动并说明原因。页面列出还在执行的运行与 Operation 及其提交者。
2. 待更新状态存在数据库里，服务重启后仍然有效。管理员可以随时“取消待更新”，恢复派发；也可以“立即更新”，这时在途工作按重启语义中断，已得评分保留（与 `--interrupt-running` 相同）。
3. 在途工作全部结束（或选择了立即更新）后，服务在 `/var/lib/maestro/update/` 写入请求：目标版本、是否中断、操作者与时间。服务只能写版本号，不能给下载地址或文件。
4. root 身份的 `maestro-update.path` 监视这个目录，触发一次性的 `maestro-update.service`。它执行 `maestroctl update --release <版本>`：按配置的仓库从 GitHub 下载该版本的发布包与 `SHA256SUMS` 并核对，确认版本比当前新（不降级），然后走现有的更新流程，备份、迁移、就绪检查与失败回滚都不变。它不挂在任何终端上，断线不影响。
5. 进度与结果写进同一目录的状态文件，详细输出进 journald。网页在服务重启期间显示“更新中”，恢复后显示结果：成功是新版本号，失败是已回到旧版本及原因。不论成功、失败，启动后都退出待更新、恢复派发。

`maestroctl update --release <版本>` 在终端里也能直接用，省去手动下载。终端里的 `maestroctl update <包>` 保持现状，不接入排空。

### 3. 安全边界

- 服务能做的只是“请求更新到获取源里的某个正式版本”。获取源和是否开启都在 root 所有的配置里。
- `SHA256SUMS` 与发布包来自同一个 Release，只防传输损坏，不防发布源本身被篡改；信任落在 GitHub 仓库与发布流程上。以后需要时可以加 GitHub 的构建来源证明（artifact attestation）作校验，本提案不做。
- `maestro` 账户在 Docker 组里，本来约等于 root（U-29），这套机制不明显扩大服务被攻破时的影响。

### 放弃的做法

- **Docker 镜像加自动拉取（如 Watchtower）**：自托管软件里最常见，但要把部署形态从系统级布局（U-13）改成容器，范围太大。
- **apt / yum 软件源**：要为各发行版打包，且版本迁移和回滚仍要自己处理。
- **定时全自动更新**：数据库迁移、中断运行、重新做首次准备应该由人挑时间。
- **从 Gitea 检查、包括开发预览**：Gitea 可能需要令牌，预览版每次 dev 推送都会出新的，不适合作为一键更新的提示。
- **全部迁到 GitHub**：主要测试留在 Gitea 是 U-42 的决定，与更新机制无关；只读 GitHub 的正式 Release 已经够用。

## 影响

- 运维：`ops/maestroctl.py` 增加 `update --release`、`maestro-update.path` 与 `.service` 两个单元（`install`、`update` 时写入，`uninstall` 删除，`check` 与 `status` 报告）、`/var/lib/maestro/update/` 目录；配置增加检查开关与 GitHub 仓库。
- 服务：调度器在待更新时不派发、Operation 拒绝启动；管理员接口：查询与检查更新、发起、取消、立即更新、读取结果；数据库记录待更新状态（新迁移）。
- 网页：管理页新增“更新”分区；工作台与系统状态显示待更新。
- 系统说明：[12](../design/12-operations.md) 第 1、3、5、9 节（删去“网页不发起维护动作”“不排空”），[11](../design/11-web-ui.md) 管理分区，[05](../design/05-scheduling-execution.md) 派发条件，[13](../design/13-testing-plan.md)，[部署指南](../guides/deployment.md)“更新”。
- 提案索引：N-12 移入“被取代”。

## 验收

- 本机伪造的 GitHub 接口（测试中通过配置覆盖 API 地址）返回新正式版时，管理页提示更新；预发布与更旧的版本不提示；查询失败只显示原因。
- 有运行在执行时发起更新：排队受理、不派发；运行结束后自动更新，新版本启动后排队的运行接着执行。
- 取消待更新后恢复派发；立即更新时在途运行标为中断、评分保留。
- 摘要不符、版本不比当前新、迁移或就绪失败时都不切换版本或回到旧版本，网页显示原因，并恢复派发。
- 更新期间关掉浏览器或断开 SSH 不影响更新。
- 以上在 `tests/maestro/live/test_install.py` 的安装测试环境中覆盖，不用已有团队 state。
