# N-44 按试次与阶段动态调度资源

状态：已确认，待实施 · 更新：2026-11-16 · 相关：[配置解析](../design/03-configuration-attachments.md)、[调度与执行](../design/05-scheduling-execution.md)、[Harbor 集成](../design/15-stack-harbor.md)、[N-13 试次粒度调度](N-13-trial-granularity.md)、U-54、U-105、U-106、U-107、D-020

## 目标与授权状态

用户最初要求修改按资源之和计算的预算，并明确先写提案。随后提出：“有没有更好的编排方案。我感觉这个很像是背包问题？固定大小，然后每个任务有占用上限？甚至可以算的更精细一点，按阶段识别？这样比如主任务需求4核8GB，但验证只需要1核2GB，那这个运行进入验证就主动释放资源？一次性做好会不会更好？”

本提案确定采用**平台统一调度试次，按当前环境阶段授予和回收资源**。静态峰值用于判断单个阶段是否可能执行，不再用于整个运行全程预占容量。

用户选择允许有限填空（U-105），随后明确排序单位是运行：“实际上是运行按先来后到，毕竟一个运行一版都会设置多个试次和并行数，而试次才记录了资源占用？”（U-106）。因此跨运行按受理顺序优先，同一运行内按试次资源需求和并发上限调度；提交批次不构成优先级分组。

用户已确认整体方案（U-107）。本次仅提交提案、合入 `dev` 并推送，版本号不变；代码实施另行开展，现行执行行为尚未改变。具体评分、候选范围与等待保护阈值属于实施选择，须满足本稿的排序、容量和验收约束。

## 术语：一组实验与对一道题完整跑一次

沿用现有领域名称，区分计划中的样本与实际执行：

| 名称 | 好记的解释 | 在本提案中的职责 |
| --- | --- | --- |
| 任务 Task | 数据集里的一道题 | 定义题目、环境和评测方式 |
| 运行 Run | 提交的一组实验 | 固定配置、每任务试次数和并发上限，决定跨运行的排队顺序 |
| 试次 Trial | 对一道题计划完整跑一次，形成一个样本 | 跟踪从准备、执行、评测到收尾的全过程；失败重试仍属于同一试次 |
| 执行尝试 ExecutionAttempt | 为完成这个试次实际执行的一次；重试另算一次 | 归属具体的执行过程、结果与清理责任 |
| 环境阶段 | 本次尝试当前使用的执行或验证环境 | 申请、持有和归还 CPU / 内存许可 |

例如，选 10 个任务、每任务 3 个试次、并发 5，就是一个运行里有 30 个计划样本，最多同时活动 5 个试次。某个试次失败后重试，增加的是执行尝试，计划样本数仍是 30。共享镜像准备与缓存恢复可以服务多个试次，不是每个试次都独立重做一次。

试次终态、产物保存和资源清理分别记录；有了评分不代表环境已经释放。按本稿建议，运行当前占用是其所有有效阶段许可的总和，包括已授权尚未启动和释放未确认的资源，不是全部计划试次资源之和，也不是始终按并发上限乘单试次峰值。现有实现仍在运行上整体预留资源，尚未具备上述动态记账能力。

## 为什么需要改编排

在 `40d220b` 上，平台按运行领取，一个 Runner 执行整个 Harbor Job。现有三层高估或闲置相互叠加：

1. `Resolver._task_settings` 把主环境、独立验证器和辅助服务相加，没有排除串行阶段。
2. `capacity.reservation` 使用“并发宽度 × 最大单试次资源”，可能虚构计划里不存在的多个大试次。
3. 预留从领取到清理结束保持不变：等待缓存、转入小验证环境、部分试次完成时，都不能把空余容量交给别的运行。

只改前两项可以降低静态上界，但解决不了第三项。建议本轮统一改调度与资源归属，避免以后再次更换 Worker、预留和清理模型。

这可以建模为**有阶段依赖的在线多资源调度**：主机有 CPU、内存、试次槽位和提供商额度，每个可执行阶段提出一组需求。单轮选择像多维背包，但完整系统还要处理任务陆续到达、时长未知、阶段切换、失败重试和清理。单次把 CPU 填满并不等于最早完成全部任务，因此先把资源许可与回收做正确，再优化选择策略。

## 推荐架构

### 1. 平台调度试次，Runner 执行一次尝试

运行继续是用户提交、观察和取消的单位，并发值表示该运行最多同时活动的试次数。Worker 从各运行的就绪试次中统一派发，不为整个运行提前包下一组 CPU / 内存。

一个 Runner 只执行一个试次的一次尝试。建议继续使用现有 Harbor Job 接口：Job 中只有一个试次、一次尝试、并发为一，并关闭 Harbor 自动重试。平台根据冻结的错误策略安排下一次尝试，上一尝试资源未确认释放前不重试。

这样复用目前的 Job 生成、事件、附件、网络与结果适配，不必为了试次级调度直接调用 Harbor 的单试次私有入口。代价是每次尝试都启动 Runner，进程、导入与初始化开销增加。`40d220b` 的本地隔离 HOME 样例中，三次单独导入 `harbor.job.Job` 约为 0.13～0.15 秒、峰值 RSS 约 46 MiB；这仅是导入开销，不代表完整 Runner 或十个并行试次的成本，真实执行验收仍须测量。

这是对 N-13 核心领取、重试与尝试归属的重新设计。本轮不顺带开放单试次取消或不同任务不同重复次数；N-13 的其余范围不随本提案确认而恢复实施。

### 2. 按实际环境生命周期定义资源阶段

资源阶段取决于哪些容器仍然存在，而不是网页进度名称：

| 环境阶段 | CPU / 内存需求 | 归还条件 |
| --- | --- | --- |
| 环境启动、附件安装、Agent 执行、产物收集 | 主环境加同时运行的辅助服务 | 该组计算资源确认停止 |
| 共享验证器 | 继续使用同一组环境及上限 | 共享环境确认停止 |
| 独立验证器 | 独立验证容器加其同时运行的辅助服务 | 验证环境确认停止 |
| 阶段间等待 | 已停止的环境不占 CPU / 内存；仍存在的环境继续占用 | 下一阶段获批或运行被停止 |

独立验证器使用 `tests/` 镜像时计入 `tests/` 服务；回退主环境定义时计入重新启动的 `environment/` 服务。辅助服务未声明上限时仍取团队默认值。收集尚需读取原容器时，原环境预算仍然有效。

例如，执行环境总需求 4 核 / 8 GiB，独立验证环境总需求 1 核 / 2 GiB：

| 时点 | 该试次占用 | 可供其他试次使用的变化 |
| --- | --- | --- |
| 执行及收集 | 4 核 / 8 GiB | 尚未归还 |
| 原环境停止已确认，验证获批 | 1 核 / 2 GiB | 归还 3 核 / 6 GiB |
| 验证环境停止已确认 | 0 核 / 0 GiB | 再归还 1 核 / 2 GiB |

如果验证仍在原来的 4 核 / 8 GiB 容器中运行，不能仅因“验证估计只需 1 核 / 2 GiB”就减账。本轮不自动缩小仍在运行的容器内存上限；真正降低需求需要使用资源已受限的独立环境。瞬时监控使用率用于诊断，不作为超额派发的依据。

同一运行的多个试次可以分别处于不同阶段，因此释放按具体执行尝试和环境组记录，不能依据运行详情页的聚合阶段一次性缩减整个运行。

### 3. 资源许可必须先于容器启动

平台维护持久化资源账本。阶段请求使用冻结配置派生的需求，Runner 不能只凭进度上报自行声明资源已减少。流程为：

1. 试次缓存和材料就绪，满足运行并发与主机试次槽位后，申请首个环境阶段的资源。
2. Worker 在一个短写事务中检查当前容量并写入许可；事务提交后才能启动 Runner / 对应环境。
3. Runner 在已获批的阶段内执行。需要新环境时先申请，获得对应尝试和阶段的有效许可后才能启动。
4. 原环境停止并由平台按尝试、阶段标签核对后，才能归还该阶段资源。
5. 若下一阶段需求能够放下，在同一事务中归还旧许可、授予新许可；上述 4 核 / 8 GiB 到 1 核 / 2 GiB 的转换因此可以直接交接并释放差额。
6. 若下一阶段在某项资源上更大且暂时放不下，原环境停止后先释放其预算，下一阶段进入等待。不能持有旧环境资源等待扩容，形成相互占用。

账本同时计入已授予但尚未启动、正在执行和释放未确认的许可。申请失败或仍在队列中的阶段不占 CPU / 内存。重复申请、授权和释放必须幂等；旧尝试、旧阶段、旧服务进程的消息不能修改新许可。

心跳超时只把资源归属变成待核对，不直接释放。取消、进程退出和停止失败后，确认相关容器及辅助资源不再执行，才可减账或启动下一次尝试。已确认评分不因清理失败被推翻。

### 4. 各种容量分别限制

- **CPU、内存**：所有有效环境阶段许可之和不能超过配置的执行容量。
- **运行并发、主机试次槽位**：限制活动尝试 / Runner 数；一个试次在执行、等待验证及验证期间仍占一个活动名额。它转入小环境会归还 CPU / 内存，但不凭空增加其运行允许的活动试次数。释放未确认的尝试继续占主机槽位。
- **提供商名额**：模型执行阶段申请，确认模型调用已结束且不会由原阶段继续发起后归还；验证无需占用。Oracle 和提交评分不申请模型名额。申请首阶段时整体检查其必要额度，避免先占住环境再等待提供商。
- **共享准备**：等待恢复的试次不预占执行 CPU / 内存或活动尝试槽位。构建仍受独立恢复并发限制；把构建 CPU / 内存纳入同一主机总账还需要可强制执行的构建限额，不在本轮默认范围内。

执行容量仍须给系统、数据库、Runner 和出口控制等开销留余量。本稿约束的是已纳入预算的试次环境，不承诺整台机器的一切进程都受同一上限约束。

受理时检查每个不可拆分环境组能否在空闲主机上执行，而不是要求整个运行的最大并发组合同时放得下。运行配置的并发是上限，实际并发可以受主机和提供商限制降低；既有团队策略对任务数、并发值和总时限的上限仍需满足。

### 5. 运行间先来优先，运行内优化试次组合

跨运行采用用户已澄清的“早运行优先，允许有限填空”（U-105、U-106）。建议在这个边界内分层选取，优先级由运行受理顺序、尝试状态与等待保护自动派生，先不增加用户填写的数值优先级。

运行是排序单位，试次是运行内派发的单位，资源许可归属试次的具体执行尝试及环境阶段。提交批次只负责一次成组受理多个运行，不增加一层调度优先级；批次内的运行也各自按受理顺序排列，同一受理时刻使用持久化的稳定顺序区分。阶段切换和试次重试不重置所属运行的受理顺序。旧运行的重跑是新受理的运行，不能借来源运行插回队首。批次的原子受理和逐运行取消语义保持原样。

| 层次 | 建议规则 | 目的 |
| --- | --- | --- |
| 已启动尝试的阶段推进 | 允许必要的验证和收尾继续申请资源，不因所属运行较晚而禁止推进；重试是新的尝试，按所属运行顺序重新竞争派发名额 | 已启动工作可以结束并归还槽位，避免全部槽位被等待续行的尝试占住 |
| 新尝试的运行顺序 | 先从最早运行的就绪候选中选择，再考虑后续运行 | 让受理顺序决定运行优先权 |
| 同运行内的选择 | 在依赖、运行并发、CPU、内存、槽位及提供商限额内，选取资源互补的就绪试次组合；同等条件优先等待较久的候选 | 减少碎片与空闲，不强制按任务输入顺序执行 |
| 后续运行填空 | 较早运行没有能利用余量的候选、处于准备 / 退避等待或达到自身并发限制时，允许后续运行使用余量；受到等待保护限制 | 提高利用率，无需等前一运行全部结束 |

优先权作用于尚未授予的许可，不强行中断已经执行的容器。后续运行通过填空启动的尝试可继续完成；其下一次重试不继承阶段续行的优先处理。已启动尝试的阶段推进也必须满足资源上限，不能借“收尾优先”超额授权。

为避免同运行的大请求、或较早运行暂时放不下的请求被持续越过，允许有限填空。请求超过等待或越过阈值后进入保护：停止继续授予会妨碍它启动的其他新尝试，等待在途工作释放资源；保护不阻止已启动尝试完成必要后续阶段。阈值作为策略明确记录并测试，不登记为未经用户决定的固定要求。

“有限填空”不保证后续运行完全不影响较早运行。例如主机有 8 核，运行 A 的并发上限为 1，当前验证占 1 核；后受理的运行 B 借空闲启动一个 6 核阶段。A 验证结束后，下一个 4 核试次仍要等 B 释放资源。运行时长未知、又不抢占已启动工作时，不能同时承诺充分利用这些空闲资源和较早运行绝不被推迟。

运行内优化以推进该运行完成、减少 CPU / 内存空闲为目标，但没有可靠耗时就不能保证整个运行最短完成时间。“当前资源组合更好”不等于“未来完成时间最优”，运行时限也不是耗时预测。建议先采用有界候选范围内的资源组合评分与等待保护，保留稳定的同分顺序；具体评分为实现选择，须用混合资源场景验证，不只按任务大小或某一个维度排序。以后有真实耗时数据时，可在同一资源许可接口上改进预测和选取算法。

这与线程调度的就绪队列和优先规则相似，但本稿采用在环境阶段边界重新申请的方式，不引入时间片轮转或强制抢占容器。

## 为什么需要改 Runner 协议

当前 `HarborExecutor` 写入一次 JSON 后关闭 stdin；Runner 读取到 EOF 后执行，stdout 只上报事件。现有 `phase_changed` 能说明进度，不能阻止 Harbor 启动环境或内部重试。

建议将执行协议改成可持续双向通信：初始规格之后，平台可发送阶段许可或停止命令，Runner 上报资源申请、环境启动与释放确认。许可只对指定尝试和阶段有效；通道丢失后不得再启动新环境。

等待许可时，事件读取、日志、心跳和取消必须继续工作。平台不能在 stdout 的顺序分发循环里阻塞等待容量，否则释放事件可能也被堵住，形成死锁。资源请求进入调度队列，由独立调度步骤授予许可。

阶段边界适配仍会依赖 Harbor 的环境创建、停止和收集顺序。必须验证实际 Docker 状态，不能只凭 `verification-start` 或成功返回的试次结果释放资源；停止错误可能被上游捕获，仍须由平台兜底。

## 资源配置、历史运行与重启

调度依据是每个容器实际下发的上限。现有统一覆盖输入如何拆分到容器，不能因为换成动态调度而悄悄改变；先展开实际容器限制，再派生环境阶段需求。独立验证器继承的作者资源也不能被主环境覆盖意外抬高。新请求若要增加独立的执行 / 验证资源覆盖入口，应作为明确的接口变更确认，而不是混入预算算法。

已有运行快照不重写，原样重跑保留相同容器限制、并发上限及错误策略。旧总量口径应先按其原算法还原实际容器设置，再生成单独的调度计划；不能把旧总量直接当作某个阶段的预算。排队运行可以使用新调度器，但其冻结配置不变，不必为旧运行长期维护第二套调度器。

升级时先排空或沿既有中断规则清理在途尝试，不能让同一运行的新旧 Runner 同时调度。服务重启后先核对 Runner 身份、尝试与阶段标签，清理或确认遗留资源，再派发；不自动续跑旧容器。原有已完成结果和未开始的排队身份保留。

持久账本和阶段归属可能需要扩展表结构，应按现有迁移链追加迁移并验证已有数据升级。不能沿用 N-13 中“表结构保持不变”的旧假设。新的协议、资源归属和等待原因需同步执行器边界、网页 / SDK 契约、管理页容量及运行详情。

## 备选方案与建议范围

| 方案 | 收益 | 代价与局限 |
| --- | --- | --- |
| 只修静态峰值 | 改动较小，减少串行环境与异构任务的预留高估 | 等待准备、转入小验证环境和运行尾部仍无法归还容量 |
| 保留每运行一个 Job，给其内部试次增加阶段许可 | 减少 Runner 启动次数，也能通过许可守住资源上限 | Harbor 与平台同时掌握排队和重试；未就绪试次可能隐藏在 Job 内，平台难以统一比较和派发 |
| 平台派发试次、Runner 执行一次尝试、阶段资源许可 | 全局可见的候选任务、明确的重试与清理归属，覆盖本次动态释放目标 | 增加进程启动次数、双向协议、持久账本及恢复验证工作 |

已确认选择第三项，作为同一项完整改动设计、实现和验收，不先交付一套以后要撤掉的静态预留机制。实现可以拆成资源账本、单尝试执行、阶段切换和恢复验收等可审查提交；对用户交付的目标仍是完整的动态调度。

确认的实施范围包括全局试次派发、阶段资源许可与归还、平台重试、准备等待不占执行容量、取消与重启对账，以及容量 / 等待原因展示。单试次取消、不同重复次数、远端执行、多租户公平份额、容器运行中缩容、构建资源隔离和最优装箱求解器不随之加入。

## 实施验收

1. 用全新独立 state 的 Oracle 验证“执行 4 核 / 8 GiB → 独立验证 1 核 / 2 GiB”：验证尚未完成时，另一个试次已能使用归还的 3 核 / 6 GiB。共享验证器用例不得同样减账。
2. 使用混合 CPU / 内存需求、异构任务和多次重复验证全局派发；任意事件顺序下，已授予、执行中和释放未确认的许可总量都不超过配置容量。
3. 验证阶段资源更大时可以释放旧阶段并排队，不超额启动、不持有旧环境等待扩容；收集所需文件在环境停止前已完整保存。
4. 验证缓存等待、运行尾部和模型阶段结束及时归还相应容量；运行并发、主机活动试次数和提供商上限各自仍然有效。
5. 对重复消息、旧许可、授权后未启动、取消与授权竞争、停止失败、Runner 失联、管道断开和服务重启做故障验证；无重复启动、无未确认释放即重用资源，已有评分保留。
6. 平台是唯一重试决策者；尝试次数、退避、错误分类及总时限沿用冻结策略。等待许可不阻塞心跳、日志与取消。
7. 验证运行优先、运行内试次组合与有限填空：较早运行可派发时后续运行不优先获得新尝试名额；较早运行暂时无法利用的余量可用于填空；等待保护能停止持续越过。单独提交与成组提交中的运行均独立排序，同一时刻受理的顺序稳定；阶段切换和试次重试保留所属运行顺序，重跑按新运行受理。后续运行已启动的尝试仍可推进验证和归还槽位，不形成阶段推进死锁。显示运行排序、填空及等待原因，不把排队误记为执行失败。
8. 验证旧快照、旧资源覆盖、原样重跑与追加迁移，确认容器实际限制不因调度升级变化。
9. 测量完整 Runner 启动、十个活动试次的进程开销、阶段交接延迟和资源利用变化；真实 Docker Oracle 验收不调用模型。若启动成本成为实质瓶颈，再评估复用执行进程，不改变资源许可语义。

当前仅完成源码调查及无容器的 Job 导入测量，尚未进行上述真实执行或故障验收。运行优先与有限填空登记为 U-105、U-106，整体方案确认登记为 U-107。实施时同步改写系统说明；在代码落地前不把提案机制写成系统现状。
