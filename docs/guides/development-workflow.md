# 开发与协作

项目采用轻量的 `feature → dev → master + tag` 流程。开发使用独立分支和工作树（只改文档时只建分支），正式服务运行固定发布版本。

## 分支职责

| 分支 | 用途 |
| --- | --- |
| `master` | 已验收的发布主线；日常开发不直接在此提交，也不在部署目录编辑源码。 |
| `dev` | 下一阶段的集成分支；功能、修复和文档修改从这里开始。它不等于生产部署版本。 |
| `feature/<topic>`、`fix/<topic>`、`docs/<topic>` | 单项工作的短期分支；改代码时每个成员或bot使用自己的工作树。 |

暂不常设 `release/*` 或 `hotfix/*` 分支。确有并行维护稳定版本或紧急发布需要时，再按当次任务确定流程；从发布版本修复的变更也应回到 `dev`，避免后续发布丢失修复。

## 开始一项工作

先读[开发交接](../HANDOFF.md)和当前任务。已有工作目录有未提交修改时，保留现场，另建工作树；不要为切换分支清理或覆盖别人的修改。

从 `origin/dev` 建立，在自己的仓库执行以下示例；工作树路径与主题名按本次任务选择，不复用其他人的目录：

```bash
git fetch origin
git worktree add -b feature/my-change ../harbor-helper-my-change origin/dev
cd ../harbor-helper-my-change
git status --short --branch
```

只改文档时，除非用户明确要求，不建工作树（U-52）：在自己的检出上从 `origin/dev` 新建分支即可（`git switch -c docs/my-change origin/dev`），合入后切回并删除分支。

后续修改、构建和验证都在这项工作的工作树内。前端构建会更新包内 `static/`，应与对应前端源码一起交付。测试须沿[开发验证](testing.md)的独立 HOME/state/凭据隔离要求执行，不能使用正式团队state作随手测试。

提交前按影响范围完成必要检查，再推送自己的分支。检查命令、隔离前提与 CI 的检查范围以[开发验证](testing.md)为准。纯格式提交独立保存。

```bash
git diff --check
git add -- path/to/changed-file
git commit -m "Describe the change"
git push -u origin feature/my-change
```

## 提案、系统说明与实施证据

一项增量从[提案](../proposals/README.md)开始（U-33、U-64）：

1. 写提案或更新提案索引，与用户确认范围和待定问题；用户的决定写入[决策记录](../design/14-decisions.md)第 0 节，并保留原话或可追溯的对话出处；旧条目不追补来源。
2. 按已确认的提案实现。
3. 合入 `dev` 的同一个 PR 中：把结论改写进受影响的[系统说明](../design/README.md)（只写现状，直接改，不追加“原设计 / 现状”分层）；提案标记完成、移入 `proposals/archive/`，索引保留状态与归档链接。取消或被取代的提案同样归档并说明原因与替代项。
4. 改了什么、验证了什么、没覆盖什么写在提交说明与 PR 描述中；原始证据放私有仓库 `maestro-site` 的 `evidence/`。不再新增 `design/records/` 下的实施记录。

小修复不需要提案，直接修改代码和受影响的系统说明。

## 问题与修复

能当场修的问题直接开 `fix/<topic>` 分支修复，不建记录。当场修不了、需要调查或要跨会话跟进时，在主仓库的 Gitea issues 建一条（U-70）：

- issue 是公开的，只写现象、原因与能用 fixture 复现的步骤。现场主机信息、原始日志与 capture 仍放 `maestro-site`，issue 里注明其中的证据路径。
- 引用写明平台，如 `Gitea#12`：主分支也推到 GitHub，裸写 `#12` 会被链接到 GitHub 的同号 issue。分支 `fix/<编号>-<短名>`，提交与 PR 写 `Fixes Gitea#12`。带平台前缀不会触发 Gitea 的自动关闭，合入 `dev` 后手动关闭。
- 状态只用开启 / 关闭；决定不修的加 `wontfix` 标签后关闭，并写明原因。是否在修，看有没有对应分支。

修复收尾时自查：

1. 加了能复现该问题的回归测试吗？放进所测行为所在的测试文件，按行为命名，不按 issue 命名。
2. 修法不显然时，修复处有注释写明约束吗？注释先写约束本身，可以附 `Gitea#N`（U-71）；不写文档路径、章节或 U / N 编号。
3. 揭示了没记录的约束吗？有的话把约束本身写进系统说明，不写问题的经过。
4. 发现是设计本身的问题吗？是的话就不只是修复：开提案，必要时请用户决定。
5. 是外部或环境问题吗？绕行办法写进[开发验证](testing.md)“环境陷阱”或[部署指南](deployment.md)。

多数修复只需要第 1 步和提交说明。

## 集成与多人或多bot协作

- 以PR/MR交付单项工作（目标为 `dev`），说明可观察变化、固定提交、实际验证及未覆盖范围。暂时无法使用PR/MR时，负责人也应基于同样的固定提交与证据完成审查后集成。
- 不共用一个checkout写文件，不修改其他工作树的分支或未提交内容；一项任务的负责人负责自己的提交和冲突处理。
- 集成前核对最新目标分支与候选提交。出现相关代码变化或冲突时，验证受影响的行为；旧提交的检查结论不能自动作为合并后版本的结论。
- 只合并必要修改；需要的工程审查和独立验收按任务影响范围安排，不因文档排版等低影响修改机械调用完整产品测试。
- 不改写已共享的 `master`/`dev` 历史，不强制推送；个人分支已被别人使用时，重写前先协调。

CI 在所有分支 push 时运行；PR 使用对应提交的结果，不再双触发。新的合并提交按 push 检查。CI 不覆盖真实 Docker、Hub 与模型测试，这些仍按开发验证指南另行执行。分支保护、必需检查和远端运行结果仍需在各仓库实时核对，配置文件不代表保护已经生效。

只改 Markdown 文档的推送不跑 CI（U-37）：工作流用 `paths` 自动判断，不必再写 `[skip ci]`（U-43）。`skills/` 与 `sdk/README.md` 由测试核对，改了仍会触发；改了代码、配置、依赖锁文件、前端、测试或工作流也都会触发。跳过后 CI 不会检查链接，只改文档时提交前在本地运行 `python3 tools/check_doc_links.py` 和 `git diff --check`。推送后在 Actions 页确认出现了这次的运行：Gitea 对没有新提交的推送（例如强推回旧提交）不触发，新分支的首推偶尔也不触发、原因未明；没有运行时在 Actions 页手动运行 `verify`（`workflow_dispatch`），或用 API `POST /repos/<仓库>/actions/workflows/verify.yml/dispatches`。

## 资料与交付证据

Git 保留通用使用、API、架构、产品契约、发布规则和验收标准。现场工程/独立验收报告、原始日志、capture、截图、执行脚本、证据索引及部署现场说明放私有仓库 `auua/maestro-site`（CI 的输出看 Gitea Actions 的运行日志，不要求存成 artifacts，U-57），开发草稿放本机 ignored `.local/`，都不得换一个公开目录提交。本仓库不放 state、凭据和主密钥。`maestro-site` 不放主密钥文件、初始化令牌、Gitea 凭据和 SSH 私钥，其余日志里的模型 key 等不要求逐项脱敏（U-36）；证据归档不能整包复制运行目录，复制前先用该仓库的 `tools/check_forbidden.py` 检查。

Agent 交付原始报告或 capture 路径时，负责人保存本地出处、固定提交、覆盖范围和未完成项，不要求将原件塞进 Git。公开说明只保留短的固定版本范围摘要，不链接私有档案，也不把历史失败或 PARTIAL 改成成功。测试文件属于可维护代码；单次执行的测试输出属于现场证据。

提交前检查暂存路径，确认没有现场材料或秘密，并检查维护文档相对链接。不用 `git add -f` 绕过忽略规则；忽略规则发现不了其他目录或已经 tracked 的误入资料，仍须审阅暂存内容。

## 集成后的收尾

完成集成后，负责人必须收尾自己的 worktree（如有）和短期分支，记录移除数量与保留原因。先核实提交已合入、没有独有未提交内容，并实时检查进程 cwd/argv、运行服务、state 和凭据引用；运行中的代码与发布环境不能随 worktree 删除。正在执行任务的树从另一个安全 checkout 收尾，必要时由集成负责人完成。

移除前运行 `git status --porcelain --ignored`；`git worktree remove` 即使没有 force 也可能删除 ignored 内容。除可重建依赖/cache外，所有未跟踪和 ignored 现场材料先逐字归档到主仓 `.local/` 或保留现场，记录原路径与摘要；不能在待删树中保存唯一原件。无法证明安全时保留并报告原因，不用 force、git clean 或全局 prune 制造干净状态。

核实上述条件后精确移除对应 worktree，并用 `git branch -d` 清理已合入的本地短期分支。远端短期分支在所有者授权范围内正常删除；未合入、仍被协作引用的分支先保留并交接。不得删除 dev/master 或改写共享历史。
