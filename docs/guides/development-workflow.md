# 开发、协作与发布

项目采用轻量的 `feature → dev → master + tag` 流程。开发使用独立分支和工作树，正式服务运行固定发布版本。

## 分支职责

| 分支 | 用途 |
| --- | --- |
| `master` | 已验收的发布主线；日常开发不直接在此提交，也不在部署目录编辑源码。 |
| `dev` | 下一阶段的集成分支；功能、修复和文档修改从这里开始。它不等于生产部署版本。 |
| `feature/<topic>`、`fix/<topic>`、`docs/<topic>` | 单项工作的短期分支；每个成员或bot使用自己的工作树。 |

上表与“发布与运行版本”是当前的常规流程。

暂不常设 `release/*` 或 `hotfix/*` 分支。确有并行维护稳定版本或紧急发布需要时，再按当次任务确定流程；从发布版本修复的变更也应回到 `dev`，避免后续发布丢失修复。

重写曾在长期分支 `feature/rewrite` 上进行，2026-10-24 以 `git merge -s ours dev`（`4bf8b2a`）记录两条历史的汇合后快进合入 `dev`，没有改写共享历史。之后的工作都从 `dev` 开始。

## 开始一项工作

先读[开发交接](../HANDOFF.md)和当前任务。已有工作目录有未提交修改时，保留现场，另建工作树；不要为切换分支清理或覆盖别人的修改。

从 `origin/dev` 建立，在自己的仓库执行以下示例；工作树路径与主题名按本次任务选择，不复用其他人的目录：

```bash
git fetch origin
git worktree add -b feature/my-change ../harbor-helper-my-change origin/dev
cd ../harbor-helper-my-change
git status --short --branch
```

后续修改、构建和验证都在这项工作的工作树内。前端构建会更新包内 `static/`，应与对应前端源码一起交付。测试须沿交接的独立HOME/state/凭据隔离要求执行，不能使用正式团队state作随手测试。

提交前按影响范围完成必要检查，再推送自己的分支。检查命令和隔离前提以[开发交接](../HANDOFF.md)的验证入口为准；CI（`.gitea/workflows/verify.yml`）检查 lint、OpenAPI 契约与 SDK 模型漂移、Markdown 链接、不用 Docker / Hub / 真实模型的 pytest，以及网页 lint、类型漂移与构建。纯格式提交独立保存。

```bash
git diff --check
git add -- path/to/changed-file
git commit -m "Describe the change"
git push -u origin feature/my-change
```

## 提案、系统说明与实施证据

一项增量从[提案](../proposals/README.md)开始（U-33）：

1. 写提案或更新提案索引，与用户确认范围和待定问题；用户的决定写入[决策记录](../design/14-decisions.md)第 0 节。
2. 按已确认的提案实现。
3. 合入 `dev` 的同一个 PR 中：把结论改写进受影响的[系统说明](../design/README.md)（只写现状，直接改，不追加“原设计 / 现状”分层）、删除提案文件、在索引中移到“已完成”。
4. 改了什么、验证了什么、没覆盖什么写在提交说明与 PR 描述中；原始证据放私有仓库 `maestro-site` 的 `evidence/`。不再新增 `design/records/` 下的实施记录。

小修复不需要提案，直接修改代码和受影响的系统说明。

## 集成与多人或多bot协作

- 以PR/MR交付单项工作（目标为 `dev`），说明可观察变化、固定提交、实际验证及未覆盖范围。暂时无法使用PR/MR时，负责人也应基于同样的固定提交与证据完成审查后集成。
- 不共用一个checkout写文件，不修改其他工作树的分支或未提交内容；一项任务的负责人负责自己的提交和冲突处理。
- 集成前核对最新目标分支与候选提交。出现相关代码变化或冲突时，验证受影响的行为；旧提交的检查结论不能自动作为合并后版本的结论。
- 只合并必要修改；需要的工程审查和独立验收按任务影响范围安排，不因文档排版等低影响修改机械调用完整产品测试。
- 不改写已共享的 `master`/`dev` 历史，不强制推送；个人分支已被别人使用时，重写前先协调。

CI 在推送和 PR 时运行，不覆盖真实 Docker、Hub 与模型测试，这些仍按交接另行执行。分支保护、必需检查和远端运行结果仍需在各仓库实时核对，配置文件不代表保护已经生效。

## 资料与交付证据

Git 保留通用使用、API、架构、产品契约、发布规则和验收标准。现场工程/独立验收报告、原始日志、capture、截图、执行脚本、证据索引及部署现场说明放私有仓库 `auua/maestro-site`（CI 证据用 Gitea Actions artifacts），开发草稿放本机 ignored `.local/`，都不得换一个公开目录提交。本仓库不放 state、凭据和主密钥。`maestro-site` 不放主密钥文件、初始化令牌、Gitea 凭据和 SSH 私钥，其余日志里的模型 key 等不要求逐项脱敏（U-36）；证据归档不能整包复制运行目录，复制前先用该仓库的 `tools/check_forbidden.py` 检查。

Agent 交付原始报告或 capture 路径时，负责人保存本地出处、固定提交、覆盖范围和未完成项，不要求将原件塞进 Git。公开说明只保留短的固定版本范围摘要，不链接私有档案，也不把历史失败或 PARTIAL 改成成功。测试文件属于可维护代码；单次执行的测试输出属于现场证据。

提交前检查暂存路径，确认没有现场材料或秘密，并检查维护文档相对链接。旧现场目录 `docs/reference/acceptance/` 已忽略，不使用 `git add -f` 绕过；忽略规则不能发现其他目录或已经 tracked 的误入资料，仍须审阅暂存内容。

## 集成后的收尾

完成集成后，负责人必须收尾自己的 worktree 和短期分支，记录移除数量与保留原因。先核实提交已合入、没有独有未提交内容，并实时检查进程 cwd/argv、运行服务、state 和凭据引用；运行中的代码与发布环境不能随 worktree 删除。正在执行任务的树从另一个安全 checkout 收尾，必要时由集成负责人完成。

移除前运行 `git status --porcelain --ignored`；`git worktree remove` 即使没有 force 也可能删除 ignored 内容。除可重建依赖/cache外，所有未跟踪和 ignored 现场材料先逐字归档到主仓 `.local/` 或保留现场，记录原路径与摘要；不能在待删树中保存唯一原件。无法证明安全时保留并报告原因，不用 force、git clean 或全局 prune 制造干净状态。

核实上述条件后精确移除对应 worktree，并用 `git branch -d` 清理已合入的本地短期分支。远端短期分支在所有者授权范围内正常删除；未合入、仍被协作引用的分支先保留并交接。不得删除 dev/master 或改写共享历史。

## 发布与运行版本

1. 选定 `dev` 的固定候选提交，完成该版本需要的验证；之后若候选内容变化，补验受影响的部分。
2. 将已验收候选集成到 `master`，为最终发布提交创建不再移动的版本tag（例如 `v0.2.0`）。tag、包版本、前端构建产物与依赖锁应对应同一发布；例子不是本轮已发布的版本。
3. 记录发布提交、构建标识、检查范围及迁移要求。正式服务从独立发布目录启动，固定到commit/tag；不通过部署目录的日常编辑或自动拉取来跟随 `dev`。
4. 服务state和外置主密钥独立于发布物。上线前核活动任务、资源与所有写者，按当时版本的维护说明执行合适的升级和恢复步骤（重写后的运维见设计 [12](../design/12-operations.md)）。

数据库升级后的回退需要单独说明数据兼容或恢复路径；代码回退不代表state可以回退。旧备份不能覆盖后来新增的业务数据。现存已部署checkout在迁移到独立发布目录之前继续按现场保护说明维护，不能直接切分支或移动目录。

## 项目状态与工作入口

用户决定写入[决策记录](../design/14-decisions.md)第 0 节，下一步做什么见[提案索引](../proposals/README.md)，验收场景见[测试与验收](../design/13-testing-plan.md)。用户当前明确指令优先；提案在用户确认前不是实施授权。开始工作时核对决策记录、相关提案和本次明确任务。

仓库保存产品契约、通用协作和发布规则；带日期、固定版本和覆盖边界的现场说明、报告及证据放私有仓库 `maestro-site`，本机 ignored `.local/` 只放草稿。实际源码行为以所查代码版本为准，运行身份和部署状态仍须在操作前实时核验。

修改示例中的 `path/to/changed-file` 等参数时，替换为本次实际文件和主题。
