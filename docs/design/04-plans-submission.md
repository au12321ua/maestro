# 04 实验方案与运行提交

导航：[总览](00-overview.md) · [配置](03-configuration-attachments.md) · [调度](05-scheduling-execution.md) · [API](10-api-sdk-cli.md) · 相关代码：`src/maestro/services/{runs,plans,idempotency}.py`、`src/maestro/api/routes/{runs,batches,plans}.py`

## 1. 模块职责与需求

| 编号 | 要求 | 现状 |
| --- | --- | --- |
| RUN-01 | 实验方案可保存和修改，运行引用其修订而不受后续修改影响 | 满足；方案只保留当前修订 |
| RUN-02 | 提交前可展开任务和批次，查看配置、规模和阻塞项 | 配置解析与批次预览 |
| RUN-03 | 受理原子写入运行、快照、试次、队列和操作记录 | 满足 |
| RUN-04 | 单次与成组提交、取消未完成部分、按失败项重跑 | 满足；批次只支持显式列表 |
| RUN-05 | 强制执行运行时限、任务 / 试次 / 并发限制与 PAT 总提交数 | 满足；并发只有运行级与提供商级 |
| RUN-06 | 重跑和修改后运行创建新运行，保留来源与差异 | 满足 |

实验方案是按修订保存的部分请求。请求带 `plan_id` 时本次字段优先、其余由方案补上（可带 `plan_revision` 要求方案未变）；运行记录方案修订，之后方案再改不影响它，重跑也不读方案。只有创建者能改方案内容（管理员也不能），所有人可读、可复制；创建者或管理员可归档（不能再选用）或删除，已有运行不受影响。

## 2. 预检与受理边界

- **配置与执行条件**（配置解析，[03](03-configuration-attachments.md)）：字段与上限、准入、内容可得性、凭据、Harness 与执行器兼容性、主机网络能力；所需槽位、CPU、内存或提供商并发超过本机静态容量的运行直接拒绝（`RUN_EXCEEDS_CAPACITY`），不永久挂在队列里。
- **受理**：身份与 PAT 状态、额度、磁盘水位、规模上限。

Worker 忙不构成受理失败，运行排队。预检不占额度；受理失败返回结构化错误，不留“半个运行”。冷缓存只产生恢复提示；准入与内容不可得的规则见 [02](02-datasets-preparation.md) 第 5 节，超时、限流或鉴权失败不会被记成内容不可得。

已知限制：受理不检查 Worker 是否在运行（`/api/v1/system-status` 的 `accepting_runs` 只供观察）；没有维护模式（暂缓，U-48）。

## 3. 单次提交事务

`POST /api/v1/runs`（`Runs.submit`）：

1. 按原样的请求体计算摘要，在任何随时间变化的检查之前按（用户，动作，Idempotency-Key）查找已有结果，同键不同内容冲突；这样方案被改或上限调低后，重试仍拿回原运行。
2. 检查磁盘水位，解析或凭 `resolution_id` 复核配置，展开明确的任务列表。
3. 写事务内：再查幂等记录；复检账户、准入修订与内容可得性（`ADMISSION_CHANGED`）、团队策略修订与模型 / Harness / 附件 / 凭据（`CONFIG_CHANGED`）、容量、修改后运行的来源仍未删除；PAT 提交用一条条件更新扣额度，同时核对未撤销、未过期、额度够。
4. 同一事务写入运行、快照、试次、队列项、Operation、幂等记录与审计；返回 202 与查询入口，Worker 异步领取。

带 `collection_id` 时，集合的固定字段像方案一样补上请求没给的部分，解析把与集合固定值不符的地方报为阻塞项，受理事务内把新运行加入集合；不符合时不受理（[08](08-collections-comparison.md) 第 6 节）。批次成员同样可带。

计划试次数 N = 任务数 × 重复次数，执行时不再扩展；自动重试只增加执行尝试。额度代表实际受理次数，取消或失败不返还；网页会话提交不扣 PAT 额度。

## 4. 成组提交

`POST /api/v1/run-batches` 接受显式的运行列表，全有或全无：任一成员有阻塞项、超出批次上限或额度不够时整批拒绝，什么都不写；否则一个事务扣足额度并写入批次与全部运行。预览接口不扣额度。

成员各自执行，互不影响；取消批次即取消每个未结束的成员。

已知限制：没有笛卡尔积展开，由调用方展开成列表；预览不检查解析是否过期、来源运行是否仍在。

## 5. 额度、时限与停止条件

| 限制 | 生效时点 | 达到后 |
| --- | --- | --- |
| 任务数、试次数、批次规模（团队策略） | 解析与受理 | 拒绝 |
| 运行并发；主机容量与提供商并发 | 派发 / 领取 | 等待，不改配置 |
| Agent、验证、附件安装时限（快照） | 对应阶段 | 记具体错误，释放资源 |
| 运行总时限 | 从受理时刻起，含排队、缓存恢复与安装 | 停止派发，终止在途项并收尾 |
| PAT 提交数 | 原子受理 | 拒绝新增，不取消已受理项 |
| PAT 有效期 / 撤销 | 每次请求及受理 | 阻止后续调用，已受理项继续 |

无人值守的连续提交用专用 PAT 的提交数与有效期限制；额度管受理授权，总时限管终止既有工作，两者不能互相替代。费用与 token 可观测，不是金额预算。

已知限制：没有按成员或按 PAT 的并发上限，没有公平调度。

## 6. 取消与完成竞争

成员取消自己的运行，管理员网页会话可取消任何运行（原因分别为 `USER_CANCELLED`、`ADMIN_CANCELLED`）。取消幂等；未被领取的运行当场结束、试次记 `not_started`，已领取的写 `stop_requested`，由 Worker 走取消协议（[05](05-scheduling-execution.md) 第 7 节）。

以服务端首次接受的终态为准：取消生效前的有效评分保留，之后到达的结果不改变试次终态。总时限到达同样走停止协议（`RUN_DEADLINE_EXCEEDED`），保留已完成结果；收尾与清理有有限宽限期，运行不会无限停在 running。

## 7. 后续操作

| 操作 | 入口 | 允许变化 | 来源记录 |
| --- | --- | --- | --- |
| 全量重跑 | `POST /runs/{id}/rerun`，`all` | 运行身份、时间、凭据当前值 | `relation=rerun`、来源运行与快照摘要 |
| 部分重跑 | 同上，`unfinished` / `explicit` | 缩小任务范围 | 所选任务及其原结局 |
| 修改后运行 | `GET /runs/{id}/request` 取请求，编辑后带 `source_run_id` 提交 | 任何合法变化 | `relation=modified`、逐字段差异 |

重跑从快照里的原请求重建（`pinned_request`）：团队默认填的字段固定为原值、模型固定在原修订、任务改为明确列表，再走正常的解析与受理；结果必须与原快照在所选任务上完全一致，否则返回 `RERUN_CONFIG_CHANGED`。这样所有当前检查（权限、准入、凭据、额度、上限、水位）自然生效，又不会悄悄换配置。缓存能按原标识恢复时照常受理，原内容不可得时拒绝，不用新标签替代。

部分重跑以任务为粒度（D-008），`unfinished` 选有试次未得分的任务，只在原运行结束后可用。任何有提交权限的主体都能重跑团队里的运行，新运行归发起者、扣其额度。原运行与重跑各自汇总；比较时重跑也是独立的一行，不与来源合并（[08](08-collections-comparison.md) 第 4 节，U-46）。

已知限制：不能按单个试次补跑。

## 8. 默认值与可解释性

默认值与上限是团队策略项（`src/maestro/services/policy.py`，管理员在网页修改），结构性常量在 `src/maestro/domain/limits.py`，与机器有关的在部署配置；当前生效值由 `/api/v1/capabilities` 的 `limits` 返回。所有限制都有限（D-011）。

权限不允许的动作不显示，但隐藏按钮不代替服务端授权。

## 9. 验收

- 两个并发请求争夺最后一个 PAT 额度，只受理一个；同幂等键重试不重复扣减。
- 批次中一个配置失效，全批无运行、无试次、无额度消耗。
- 取消时已评分的结果保持，其余试次为未开始或已取消。
- 只重跑未得分的任务时创建新运行，任务范围和来源明确。
- 修改方案或团队默认后按原配置重跑，`config_digest` 不变；修改后运行展示差异。
- 已准入的冷缓存任务可由成员 / experiment PAT 提交和重跑，不另扣额度；内容不可得的拒绝发生在受理前，不扣额度。
