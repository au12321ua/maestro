## 一、审查结论

这份需求足够做第一版设计，但还不能直接动工：领域概念没有统一，"固定配置"和"计分规则"没有定义，首期范围也没有划线。

强项很明显。数据集、实验、结果三条主线完整闭环；"人与 agent 对等"写得具体，覆盖了结构化结果、长任务、幂等和来源追溯；"有效零分与缺失""执行、产物、清理分别记录"这类细节已经有意识。

弱项集中在三层：

- **概念层**：同一个词多义（"任务""方案""实验"），四种"一组实验"并存；后补的 7 条与前面的故事没有合并。
- **语义层**：几条决定数据模型的规则只写了目标，没写规则本身。
- **范围层**：没有优先级、非目标、验收标准和规模假设，无法判断"做完了没有"。

动工前必须定下的 9 项：

| 编号 | 问题 | 为什么必须先定 |
| --- | --- | --- |
| A1 | 统一术语与领域模型 | 名字会变成表名、API 资源和 SDK 类型，上线后改名代价最大 |
| A2 | "固定配置"固定到什么粒度 | 只记名字或标签，重跑就不是同一个实验 |
| A3 | 试次的结果状态与计分规则 | 超时、基础设施故障算零分还是缺失，直接决定评分能否被信任 |
| A4 | 后续操作语义（已定：重跑与修改后运行） | 决定运行能否追加试次，以及结果如何聚合 |
| A5 | 进程拓扑与重启行为 | 决定服务重启时在途实验的命运，以及"为多机做准备"是否落地 |
| A6 | 配置分层与生效规则 | 决定配置对象、校验接口和重跑语义 |
| A7 | 首期范围、非目标与验收标准 | 优先级与非目标已定，验收场景待补 |
| A8 | 规模与非功能假设（已定） | 决定数据库、存储和队列选型 |
| A9 | 版本准入与准备缓存分开（已定） | 不分开，缓存回收就会让数据集突然失去使用资格 |

其余意见见第九节，分为"应补充"（B 类）和"可直接写进约定"（C 类）。

**阅读说明**：第二至八节是按主题重排后的需求，原文条目全部保留，后补的 7 条和 5 个边界已并入对应位置。【审查 A3】这类标记指向第九节；标【建议】的内容是本次审查新增，不是原文要求。

## 二、术语与领域模型

【建议】系统对象一律使用下表中的名字；"实验"只作为界面和口语里的总称，对应对象是"运行"。

原文有三处多义，后续需求、API 和界面都会被它们拖累：

- \*\*"任务"\*\*同时指数据集中的测试项目，和 worker 领取的工作单元（"Worker 负责领取任务"）。
- \*\*"方案"\*\*同时指模型方案、harness 方案和实验方案，三者生命周期不同。
- \*\*"实验"\*\*在核心故事里是"一组配置及其执行"，到补充 1 又被拆成"方案"和"运行"。

| 建议术语 | 定义 | 原文中的说法 |
| --- | --- | --- |
| 数据集来源 | 提供数据集的外部系统，经适配器接入；首期只有 Harbor Hub | 数据集来源（架构边界） |
| 数据集 | 某个来源中的一套测试，身份为"来源 + 作者/数据集名"；首期即 Harbor Hub 上的数据集 | 数据集 |
| 数据集版本 | 数据集的一个不可变版本，加入系统后有独立记录 | 版本 |
| 任务 | 数据集版本中的一个测试项目；只此一义 | 任务 |
| 准备记录 | 某数据集版本按某准备配置、在某位置持有的准备成果（镜像、构建、依赖）及其过程；可被回收，按内容标识恢复 | 准备记录 |
| 版本准入 | 某数据集版本的各任务是否已被平台接受并确认可用；管理员首次准备成功后确立，不因缓存回收而失效 | 原文未区分（见 A9） |
| 模型配置 | 提供商与接入方式、模型标识、调用参数、凭据引用；同一模型经不同提供商调用，视为不同配置 | 模型方案 |
| Harness 配置 | 驱动模型完成任务的程序、版本和参数 | harness 方案 |
| 附件版本 | 临时扩展 agent 能力的扩展包的一个不可变版本，可选包含 SDK、skill、tools、bootstrap.sh | 附件及其版本 |
| 实验方案 | 可保存、可修改的配置模板：数据集版本、任务范围、模型、harness、附件、资源 | 实验方案 |
| 运行 | 一次受理后的执行，持有不可变的配置快照 | 实验 / 运行 |
| 试次 | 某个任务在某次运行中的一次执行；评分、日志、产物挂在这一层 | "执行多次""尝试次数" |
| 提交批次 | 一次成组提交产生的一组运行 | 成组提交 |
| 实验集合 | 事后挑选、可持续增加的运行引用，有名称和用途 | 实验集合 |
| 分析快照 | 冻结的运行清单加比较设置 | "保存某一次分析所使用的实验清单与比较设置" |
| 操作记录 | 任何长时间操作受理后返回、可持续查询的记录 | 操作记录 |

&#91;embedded content: 领域模型 · 10 个对象\]

数据集侧提供任务和环境，配置经方案发起运行；评分、日志和产物都挂在试次上，提交批次和实验集合是运行的两种分组方式。

Worker 领取的单位建议直接叫"运行"（或运行的一部分），不再用"任务"。Harbor 自身有 task、trial、job、agent 等概念，适配器文档应写明与上表的映射。

## 三、故事一：数据集添加与环境准备

用户从 Harbor Hub 选定一个明确的数据集版本加入系统，系统生成数据集配置并完成环境准备，就绪后进入可选目录。

**查找与添加**

1. 通过"作者/数据集名"在 Hub 中查找，查看说明、可用版本和任务列表，选定一个明确版本加入。
2. 系统读取该版本的作者定义，生成数据集配置：
   - 参数与环境变量：说明、默认值、必填项，预填作者预设值。
   - 各任务的资源要求：时间、存储、CPU、内存（首期不含 GPU）。
   - 测试与验证所需的环境、镜像、依赖及准备方式。
3. 参数和环境变量通过统一表单呈现。可直接采用作者预设，也可补充必要配置；团队凭据通过凭据引用填写。

**环境准备**

4. 加入后开始准备：下载任务内容，预拉已有镜像，按作者定义完成构建和依赖准备。
5. 用户可查看准备进度，以及哪些任务已就绪、哪些失败。
6. 准备记录关联数据集版本、准备配置、执行位置和准备结果。
7. 失败部分可重试；已完成的准备成果可复用；能否复用按内容标识判断（A2），准入与缓存分开记录（A9）。
8. 实际运行使用已准备的资源创建独立运行环境。环境预加载与实际执行共用同一套准备能力。

**版本与基准**

9. 就绪后进入可选目录。首次准备失败的任务不可选，由管理员重试成功后才能用于运行；已准入任务的缓存被回收，不影响可选（A9）。版本只要有就绪任务即可进入目录，并标明就绪与失败的任务数；按整个 bench 汇报的结果需注明因准备失败而排除的任务。
10. 添加新版本形成独立记录，已有运行继续关联原版本。
11. 作者预设保留为基准；单次运行调整参数和资源约束，不改写基准。

**Agent 能完成的工作**：搜索数据集，读取版本和任务目录、作者参数及资源要求，查看准备进度和各任务是否就绪。添加数据集与发起、重试准备由管理员完成（见 B2）。

## 四、故事二：实验提交与执行

用户基于方案或直接填写配置提交运行；系统校验后冻结配置快照，排队分配给 worker 执行，并分别记录结果、产物和清理情况。

**实验目的**（决定比较时允许哪些因素变化）

- RSI 迭代：观察修改前后的变化。
- 在某个 bench 上评估模型能力。
- 固定模型等条件，比较插件或附件的影响。
- 重复运行同一配置，观察稳定性。

**配置组成**

1. 数据集版本与任务范围。
2. 模型配置：提供商、模型及其调用配置。
3. Harness 配置：如何驱动模型完成任务。
4. 附件及其版本：临时扩展 agent 能力的扩展包，可选包含 SDK、skill、tools、bootstrap.sh；加载方式明确。
5. 资源与运行参数：尝试次数、并发、时间、计算资源。系统预填作者参数和资源约束。

**附件的作用**（补充 3）

6. 用户能看清每个附件包含哪些部分（SDK、skill、tools、bootstrap.sh），以及它影响模型调用、工具能力、测试环境还是验证过程。
7. 系统记录实际加载了什么，以及改变了哪些实验条件。影响评分规则的内容，在结果和比较中明确标出。

**实验方案**（补充 1）

8. 可把上述配置保存为可复用的方案，再据此发起运行。修改方案不影响已有运行；"准备做什么"与"某一次实际做了什么"分别记录。

**提交与受理**

9. 提交前展示最终生效配置，以及相对作者预设的变化。【审查 A6：还应展示每项值的来源】
10. 提交时检查配置完整性、引用资源可用性、运行条件。
11. 受理后生成运行记录，固定数据集、模型、harness、附件和资源配置；之后修改团队配置不影响它。【审查 A2】

**成组提交**（补充 2）

12. 可一次提交一组运行（例如多个模型或插件组合），提交前查看展开后的配置和预计任务数。
13. 组内各运行独立记录结果；可查看整体进度、取消未完成部分、选择失败项重新运行。【审查 A4】
14. "一次成组提交"（提交批次）与"事后选取的一批结果"（实验集合）分别表达，后者可跨多个批次。

**额度与停止条件**（补充 4）

15. 开始一轮前可设定允许范围：任务数量、尝试次数、并发、总运行时间、连续迭代次数。【审查 B3】
16. 达到限制后停止新增工作，给出停止原因和已完成结果。
17. 费用和 token 按实际可得的信息记录，无法准确掌握的标为未知。金额预算若要成为强制限制，需另行定义它能保证到什么程度。

**排队与执行**

18. 运行进入队列，系统按资源需求和可用容量分配给 worker。【审查 B4】
19. Worker 载入执行器，准备运行环境，按约定加载插件和附件，依次完成测试与验证。
20. 复用已有准备成果；本机缓存缺失时按原内容标识自动恢复，并显示在进度中。恢复失败记为该试次的错因，不影响版本准入（A9）。
21. 执行中可实时查看准备、排队、测试、验证和结果收集各阶段，查看各任务进度与日志，也可以取消。

**结果收集与清理**

22. 执行器收集评分、验证结果、日志、会话记录和输出文件，保存为所属运行的结果与产物。
23. 系统汇总任务完成情况、配置、实际执行信息和失败原因，随后清理临时环境。
24. 执行结果、产物保存情况、环境清理情况分别记录，用户能看出运行完成到哪一步。
25. 部分失败或取消时保留已生成的有效结果；未执行、执行失败、正常完成分别展示；有效零分与缺少评分分别表达。【审查 A3】

**后续操作**

26. 按原配置重跑：复用原运行的固定配置，创建新运行；提交前做与新提交相同的运行条件检查，原内容已无法取得则拒绝（A9）。
27. 修改后运行：把原配置带入编辑界面，可改模型、harness、附件、任务范围或资源约束，再提交新运行；记录配置差异。
28. 中断或部分失败后接续（补充 5）：原运行中已完成、未开始、执行中断的任务分别保留；接续一律按原配置重跑，可只选未完成或失败的任务。首期不支持在原运行内续跑。
29. 所有后续操作保留来源关系。

**Agent 能完成的工作**：查询模型、harness 和附件，生成配置，检查运行条件，提交，观察执行，取消、重跑或修改后运行。

## 五、故事三：结果查询、比较与组织

用户能按多种条件找到运行、下载产物，把运行组织成集合做按任务对齐的比较，并从比较结果直接发起下一轮。

**查询与下载**

1. 查询单个运行，或按数据集版本、模型、harness、附件、提交者、时间、执行状态筛选一批运行。
2. 每个运行提供完整配置、执行摘要、任务明细、评分和产物目录。
3. 可查看单项结果、下载指定产物，也可批量查询和下载多个运行的结果。
4. 批量导出保留运行与任务的对应关系，并标明缺失或不可用的项目。【建议】定义导出格式：目录结构加一份机器可读的清单文件。

**实验集合**

5. 把一批运行组织成有名称和用途的集合，例如"某模型在某 bench 上的评估""插件 A/B 对比""一轮 RSI 迭代"。
6. 集合只引用运行；一个运行可属于多个集合，结果与产物只有一份来源。
7. 集合可逐步加入新的运行，用于展示多轮迭代。
8. 可保存某次分析使用的运行清单与比较设置（分析快照），之后回到当时的结果范围。

**统一视图**

9. 每个运行的主要配置、完成情况和汇总指标。
10. 按任务对齐的评分、成功情况和结果差异。
11. 运行之间的模型、harness、附件和资源配置差异。
12. 从汇总结果进入具体任务日志与产物。

**比较规则**

13. 用户明确本次关注的变化因素。插件比较允许附件不同，模型、数据集版本、资源条件应一致；模型评估允许模型不同，核对其他条件。
14. 系统据此展示可比较的范围和其他条件差异。
15. 任务缺失、执行失败、尝试次数不同在比较中明确呈现；汇总说明实际覆盖范围，不把未完成的测试当成零分。【审查 B8】

**产物保留与回收**（补充 6）

16. "收集产物"和"回收存储空间"各有业务规则。用户能知道哪些结果长期保留、哪些大文件可能过期、删除会影响什么。
17. 原始产物被清理后，运行配置、评分摘要和操作记录按既定策略继续保留，并标注哪些证据已不可获取。
18. 批量下载和 agent 查询都能识别"已清理"状态。

**闭环**

19. 从比较结果中选中某个运行，沿用或修改其配置发起下一轮，新结果继续加入对应集合。

**Agent 能完成的工作**：筛选和批量查询运行，下载产物，创建和维护集合，执行比较，读取差异与结论，发起下一轮。【审查 B9】

## 六、贯穿要求

所有实验相关的业务能力同时面向人（网页）和 agent（SDK），管理能力只面向管理员（网页），两者共享同一套服务端能力、权限、数据、队列和操作记录；整个流程可以由人完成、由 agent 完成，或由两者接续。

**PAT 与权限**

1. 用户为 agent 创建 PAT，指定允许的操作范围和有效期，可查看使用记录、随时撤销。
2. PAT 代表授权用户执行操作；实际权限 = 用户自身权限 ∩ PAT 授权范围。
3. Agent 只做实验相关的工作。添加数据集、准备环境、管理团队配置、账户和凭据只由管理员在网页上完成，不经 PAT（B2 已定，原文此处已改）。
4. 系统记录每次操作所属的用户及使用的 PAT。

**归属与管理权**（补充 7）

5. 结果全团队共享，提交保留个人身份。
6. 成员管理自己的运行，管理员管理团队资源。
7. 实验方案、提交批次、实验集合有明确的创建者与修改权限，方便多人接续同一项工作。【建议】写出权限矩阵，见 C7。

**操作前：能力可发现**

8. 系统提供可读取的能力说明、参数定义、默认值、可选值、约束和权限要求。
9. Agent 能判断当前账户能做什么、某个数据集是否已准备好、提交运行还缺哪些配置。

**操作后：结果结构化**

10. 每次操作按类型返回：
    - 对象身份、版本、关联关系、实际生效的配置；
    - 是否成功、是否已受理、当前进度和最终结果；
    - 错误类型、失败阶段、相关字段，能否重试或需要补充什么；
    - 结果、日志和产物的查询与下载入口；
    - 当前可以执行的后续操作。
11. 结构化字段与面向人的说明一起提供：agent 依靠稳定字段判断，借助说明理解原因。

**长任务与接续**

12. 长时间操作受理后返回可持续查询的操作记录；断线重连后能找到先前的工作，判断它在执行、已完成还是需要处理。
13. 重试提交能识别重复请求，避免意外启动重复运行。【审查 C1】
14. 用户重新进入或 agent 更换会话后，能找到先前的方案、运行、结果和待处理事项（补充 5）。【建议】定义"待处理事项"对应什么对象。

**分析材料**

15. 评分携带任务身份、指标含义、尝试次数、完成情况和来源。
16. 比较结果携带运行配置差异、对齐范围、缺失项目和比较依据。

18. 相应权限下可获取完整的业务信息和分析材料，凭据明文始终受保护。【审查 B6】

**配置生效规则**（边界 2）

19. 作者预设、团队默认、单次覆盖与团队强制上限之间有明确关系。例如可以覆盖默认运行时间，但必须满足团队上限。【审查 A6】

**系统能解释自己当前能做什么**（边界 5）

## 八、交付、部署与配置

首期交付一个由 systemd 管理的 Linux 服务，加上网页和 SDK 两个正式入口。

**两个入口**

1. 网页由服务端提供，成员打开浏览器即可使用。
2. SDK 通过 PAT 使用实验相关的全部能力；管理操作不经 PAT（见 B2）。
3. SDK 提供结构化的输入、结果、错误和进度，支持能力发现、配置检查、长任务跟踪、批量操作和产物下载。
4. 调用方只需服务地址与凭据，不需要访问服务器目录或安装服务端执行环境。
5. API 契约、SDK 类型与文档保持一致；服务端报告自身版本和能力，SDK 对不支持的操作给出明确说明。【审查 C5、C6】

**生命周期管理**

6. 安装：检查运行条件，安装程序与依赖，创建实例目录和配置文件，注册 systemd 服务，提供首次设置入口。
7. 启动与维护：启动、停止、重启、状态查询、日志查看。进程异常退出由 systemd 重启，业务层根据持久记录恢复管理状态。【审查 A5】
8. 更新：从配置的更新源检查并拉取明确版本，准备好后切换。更新前处理在途运行并检查数据兼容性；失败时保留恢复所需的信息与材料。【审查 B10】
9. 卸载：停止并移除本实例的服务和程序。默认保留业务数据与配置；提供彻底删除选项，并展示删除范围。
10. 安装、更新、卸载由独立的服务管理入口负责。管理员可在网页上发起支持的维护操作，进度持久可查，不依赖客户端保持连接。
11. 普通重启使用当前已安装版本；检查更新、下载更新、切换版本都是显式操作。

**配置分类**

| 类别 | 内容 | 管理方式 |
| --- | --- | --- |
| 部署配置 | 监听地址、端口、数据与日志目录、代理、更新源、Worker 连接、适配器启用情况 | 服务配置文件 |
| 团队业务配置 | 数据集、模型与 harness 配置、附件、成员、配额、保留策略 | 网页或 SDK 管理，存数据库 |
| 敏感配置 | 主密钥、模型凭据、Hub 凭据、更新源凭据 | 受保护的文件或凭据存储，普通配置只存引用 |

12. 每项配置有明确的默认值、校验规则和生效方式。
13. 管理员能查看脱敏后的实际生效配置，以及修改后是否需要重启。
14. 已受理的运行继续使用其固定配置。
15. 程序版本、部署配置、业务数据、凭据、缓存与日志各有明确的存放边界；安装、更新、卸载都按这些边界操作。
16. 备份与恢复覆盖业务数据及配套的配置和凭据材料，能在另一台符合条件的 Linux 主机上重建服务。【审查 B11】

**版本关系**（边界 4）

17. SDK、服务端、数据集适配器、执行器、持久数据各有版本；每个发布版本说明支持的组合。
18. 发现不匹配时，给出升级、迁移或重新准备的提示；不承诺无限期兼容旧版本。

## 九、审查意见明细

共 31 条：A 类 9 条影响数据模型或核心语义，动工前必须定；B 类 14 条是明显遗漏，应补充；C 类 8 条可以直接写进技术约定。

### A 类：动工前必须定下

**A1 统一术语与领域模型**

- 问题："任务""方案""实验"多义；提交批次、实验集合、分析快照、"一批实验"四个分组概念只在文字里区分。
- 影响：这些名字会直接成为表名、API 资源和 SDK 类型。对 agent 而言，字段名就是它理解系统的依据。
- 建议：采纳或修订第二节的术语表后冻结；需求、API、界面只用一套名字。

**A2 "固定配置"要固定到内容，而不只是名字**

- 问题：原文要求受理时固定数据集、模型、harness、附件和资源配置，但没说固定的是引用还是内容。
- 影响：只记名字时，镜像标签可能已指向新镜像，附件同一版本号可能被覆盖。"按原配置重跑"就不再是同一个实验，RSI 前后对比也失去意义。
- 建议：
  - 快照记录可校验的内容标识：数据集版本的内容摘要（Harbor Hub 数据集可按 digest 引用）、镜像 digest、harness 与附件的版本加内容哈希。
  - Harness 和附件版本一经发布不可变，修改只能发新版本。
  - 凭据只记引用；重跑时使用当前值，这一点写明。
  - 模型本身无法冻结：记录请求的模型标识，以及接口返回的实际模型版本（如有）。
  - "已完成且仍然有效的准备"用同一组内容标识判定。

**A3 试次的结果状态与计分规则**

- 问题：原文区分了"有效零分"和"缺少评分"，但没有规定每种失败归哪一类。
- 影响：这是评测结果能否被信任的核心。超时算 0 分还是缺失，平均分可能差很多；基础设施故障若算 0 分，会把环境问题误判为模型退步。
- 建议：只有验证器真正给出评分才算"已评分"（含有效零分）。其他结果一律记为错误状态，状态本身就是错因，既不算 0 分也不算缺失，便于定位。每种错因还要规定是否自动重试。错因至少包括：
  - 被取消或额度耗尽而未开始；
  - 环境失败（镜像拉取、容器启动、依赖安装）；
  - Harness 自身出错；
  - Agent 超时，以及超时后是否仍运行验证；
  - 验证器出错；
  - 模型接口失败（限流、服务端错误）；
- 汇总口径：状态与口径分开定义。每种错因要规定汇总时是计入分母（按未通过计），还是排除并降低覆盖率。超时、harness 出错这类可能由模型行为引起的错因若一律排除，常超时的模型分数反而偏高。建议基础设施类错因默认排除并报告覆盖率；模型相关类错因按数据集作者的约定计入；所用口径写进比较依据。
- 【建议】Harbor 已有一套错误分类：每种异常对应一个错因，并规定是否重试、是否仍运行验证、奖励是否有效（例如 agent 超时的奖励仍有效，沙箱故障的无效）。首期直接以它作为错因表和汇总口径的基线，业务层只补充平台自身的错因，如"中断：服务重启"。
- 同时定义：自动重试的上限、重试是否计入尝试次数、多次试次如何聚合（均值、pass@k、全部通过），以及指标含义由数据集作者还是团队定义。

**A4 后续操作的语义（已定：重跑与修改后运行）**

- 问题：核心故事只有"重跑"和"修改后运行"；补充 5 又引入"恢复原工作"，补充 2 引入"选择失败项重新运行"。四者关系未定。
- 影响：决定运行受理后能否追加试次，一个运行能否混合不同时间、不同 worker 的执行，以及比较和导出时怎么计数。
- 结论：首期只有两种后续操作，都创建新运行；不支持在原运行内续跑。
  - **重跑**：新运行，复制原快照，记录来源。"恢复原工作"和"选择失败项重新运行"都属于重跑，只是任务范围收窄为未完成或失败的任务，并记录这一范围。
  - **修改后运行**：新运行，从原快照出发修改，记录来源和配置差异。
- 重跑前复用提交时的运行条件检查。只有快照引用的内容已无法取得，或只能取得内容标识不同的替代物时才拒绝，并指出无法满足的内容标识；本机缓存缺失但原内容仍可取得时，自动恢复后照常重跑（A9）；用户可改用修改后运行。
- 【建议】部分重跑后，原运行与重跑运行各自独立。需要合并结果时，由集合视图按任务取同配置运行中最新的已评分试次，并标明每条结果来自哪个运行。

**A5 进程拓扑与重启时的在途运行**

- 问题：原文定了"单实例管理多个 worker"，但没说 worker 是进程内线程、独立进程还是独立 systemd 单元；也没说服务重启时正在执行的容器怎么办。部署配置里还出现了"Worker 连接"。
- 影响：worker 若在服务进程内，重启会杀掉所有在途试次，这在首期可以接受，前提是重启后状态如实记录、临时资源清理干净。孤儿容器和临时目录的清理也取决于此。
- 建议首期沿用原版"进程内 worker"的简单做法，但把接口和状态规则定清楚，为多机留好位置：
  - **worker 留在服务进程内**，但只通过 worker 接口与业务层交互：领取、心跳、上报进度与结果、接收取消；不直接读写业务对象或数据库。
  - 产物通过存储接口上传，不依赖与服务端共享目录。
  - 每个容器和临时目录都打上所属运行与试次的标签，清理时按标签查找。
  - **意外重启**：启动时把仍记为执行中的试次标为错因"中断：服务重启"，已评分结果保留，按标签清理无主容器；用户按需重跑未完成的任务。首期"按持久记录恢复管理状态"即指恢复对状态的掌握，不恢复执行。
  - **计划内维护**（更新、重启）：先进入排空模式，停止派发新运行；管理员选择等待在途运行结束（可设期限）或立即取消。立即取消就是原版行为。
  - 调度考虑准备记录所在位置。
  - 以后若长时间运行常被重启打断，再把 worker 拆成同机独立进程：接口已在，只换通信方式，届时再加心跳对账。

**A6 配置分层与生效规则**

- 问题：原文已列为边界 2，但还没有规则本身。另有两点未覆盖：团队默认介入后，提交前展示的差异以谁为基准；实验方案作为新的一层放在哪里。
- 影响：决定配置对象、校验接口、重跑语义，也决定结果是否"偏离作者基准"。
- 建议：
  - 顺序：作者预设 → 团队默认 → 实验方案 → 单次覆盖。团队上限和作者硬性要求作为约束，不作为一层。
  - 每个生效值带来源；快照同时保存生效值和来源。
  - 允许低于作者要求的覆盖（如缩短超时、减少内存），但在运行上标记"偏离作者基准"，比较时显示为条件差异。

**A7 首期范围、非目标与验收标准（部分已定）**

- 影响：无法判断首期是否完成，工期紧时也无法取舍。

**已定的首期量级**

**由此得出的设计取向**

- 主机：10 个试次满载约需 10 核、20 GB 内存，另需为服务本身和镜像构建留余量。
- 【建议】数据库：这个量级用 SQLite（WAL 模式）足够，安装和备份最简单。按 A5，worker 不直接访问数据库，以后多机也不受影响；保留迁移工具，需要时再换 PostgreSQL。
- 存储：一周内的产物占用约为"一周试次数 × 平均产物大小"，按上限 100 MB 计，1000 个试次即 100 GB。【建议】磁盘可用空间低于阈值时暂停受理新运行，并在能力状态中报告（第六节第 21 条）。
- 【建议】镜像和准备成果通常比产物更占空间，保留策略也要覆盖：磁盘紧张时按最近使用时间清理；被清理的缓存下次使用时按原内容标识自动恢复，不影响版本准入（A9）。
- 队列：2 到 3 人、10 个槽位，首期先到先得即可。
- 保留：产物 1 周后清理，配置、评分摘要、操作记录继续保留（补充 6）。【建议】到期前在运行页和 SDK 中提示，避免来不及导出。

**A9 版本准入与准备缓存分开（已定）**

- 问题：第三节"准备失败的任务不可选"、B2"只有管理员发起和重试准备"、第四节"运行时重新准备缺失部分"、A8"缓存回收后重新准备"放在一起会冲突。管理员准备好数据集、成员用了几天后，系统清掉了镜像缓存：成员还能不能直接提交？
- 结论：区分两件事。
  - **版本准入**：某数据集版本的各任务及其准备方式，是否已被平台接受并确认可用。管理员首次准备成功后确立，按内容标识记录。
  - **准备缓存**：当前机器是否持有可复用的镜像、构建和依赖。可以被回收，不影响准入。
- 缓存不存在不等于失去使用资格。A4 的"资源失效"也据此明确：本机删了镜像、但同一 digest 仍可下载，属于可恢复；只能取得另一个 digest，才是原配置无法满足。

| 情况 | 系统行为 | 由谁处理 |
| --- | --- | --- |
| 首次准备尚未成功，或必要配置不完整 | 任务不可选，显示阻塞原因 | 管理员 |
| 已准入的版本，本机缓存被清理 | 运行时按原内容标识自动恢复；同一缓存只恢复一次，等待它的运行共享结果 | 系统，随运行进行 |
| 原内容仍可取得，但本次下载或构建失败 | 记为该试次的错因，按规则自动重试；不影响准入 | 系统；提交者可重跑 |
| 原内容已无法取得，或只能取得内容标识不同的替代物 | 相应任务标为"内容不可得"，新提交和原配置重跑都被拒绝，并指出无法满足的内容标识 | 管理员决定弃用或添加新版本 |

**附件沿用同样的区分**。成员和 PAT 可以上传附件，附件的 bootstrap.sh 可能要在安装阶段装依赖。这属于已授权运行的一部分，由提交者的运行触发，不需要管理员，限制如下：

- 只在该试次的容器内执行，不挂载宿主机目录。
- 在安装阶段进行，可访问外网；进入执行和验证阶段后仍只能访问模型提供商（B6）。
- 受安装超时和运行总时长上限约束。
- 失败记为该试次的错因，不影响其他试次和版本准入。
- 【建议】首期每个试次各自安装；以后可按"附件内容哈希 + 基础镜像 digest"缓存安装结果。

### B 类：应补充

**B1 身份认证与团队模型**。已定：一个实例只服务一个团队；只有管理员和成员两种角色；管理员在初始化时配置，其余成员由管理员邀请加入，不开放自注册。【建议】首期用本地账号，成员通过邀请链接设置密码；OIDC 与 SSO 列为非目标。

**B2 Agent 的权限边界（已定）。**

原则：agent 帮人做实验，不管理平台和账户。PAT 永远不具备管理员能力，即使创建它的是管理员。

| 能力 | 成员 | 管理员 | PAT |
| --- | --- | --- | --- |
| 读取数据集、运行、结果、产物 | ✓ | ✓ | ✓ |
| 创建方案；提交、取消、重跑自己的运行 | ✓ | ✓ | ✓ |
| 管理自己的批次和集合 | ✓ | ✓ | ✓ |
| 上传附件新版本 | ✓ | ✓ | ✓ |
| 取消他人的运行 | — | ✓ | — |
| 添加数据集；首次准备及其重试 | — | ✓ | — |
| 管理模型与 harness 配置、配额、保留策略 | — | ✓ | — |
| 管理凭据 | — | ✓ | — |
| 邀请与移除成员 | — | ✓ | — |
| 创建、撤销自己的 PAT | ✓ | ✓ | — |
| 维护操作（更新、重启） | — | ✓ | — |

- PAT 只有两种范围：**只读**（读取全部业务信息，不含凭据明文）；**实验**（只读加上表中 PAT 一列打勾的操作）。
- PAT 只能由本人在网页上创建和撤销，PAT 不能创建 PAT。
- 凭据只写不读：任何接口、导出和备份查看都不返回明文。
- 每个 PAT 设有效期和可提交运行总数上限（见 B3），防止无人值守的 agent 循环占满队列。
- 运行中自动恢复缓存、安装附件依赖，属于已授权运行的一部分，由系统随运行进行，不需要管理员（A9）。

**B3 额度挂在哪个对象上**。补充 4 的"连续迭代次数"在服务端没有对应对象：agent 每轮提交的都是独立运行，服务端并不知道它们属于同一轮迭代。首期最简单的做法是挂在 PAT 上：PAT 可提交的运行总数上限加上 PAT 有效期，就能限住无人值守的迭代，不必新增对象；受理时由服务端检查；单个运行内的额度（任务数、时长）挂在运行上。

**B4 调度与配额**。队列是先到先得还是按成员公平分配，是否有优先级，单个成员或 PAT 的并发上限是多少；团队配置中的"配额"没有定义。按 A8 的规模，首期先到先得即可，公平调度可放到 P1。并发还应同时受模型提供方限速约束，否则大量试次会因限流失败（与 A3 相关）。

**B5 资源模型是否包括 GPU**。已定：首期不考虑 GPU。

**B6 执行环境中的凭据与日志泄露**。已定：执行和验证期间，容器只能访问模型提供商；日志脱敏首期从宽，只做基本处理。【建议】环境准备（拉镜像、装依赖、构建）需要外网，网络策略按阶段区分；附件的 bootstrap.sh 若要下载依赖，应放到准备阶段完成。Harbor 的 Docker 环境已支持按阶段设置白名单（agent 运行与验证阶段可分别限制，安装阶段不受限），依赖宿主机的 nftables 支持，无需自建代理；网络策略由任务作者在任务配置中声明，作业配置能否强制收紧需实测确认。harness 与任务代码同在一个容器时，模型凭据对任务代码可见，可信团队前提下接受。

**B7 RSI 场景下的评测隔离**。做 RSI 的 agent 若能通过接口读取任务答案和验证脚本，就可能对测试集过拟合。建议 PAT 范围能排除"读取验证器与参考答案"，或支持留出集（只返回聚合分、不返回明细）。已定：RSI 不是首期目标，权限模型留出位置即可。

**B8 比较的统计口径**。"重复运行观察稳定性"需要统计支持：多次试次的均值、方差或置信区间、pass@k，以及两组结果的差异是否超出噪声。已定：首期只提供基本统计（样本量、均值、标准差、通过率），比较视图显示每项的样本量。

**B9 "结论"由谁产生**。故事三的 agent 能力中有"读取差异与结论"。建议首期系统只提供可计算的差异；集合和分析快照另设"结论"字段，由人或 agent 写入并记录作者。

**B10 更新与在途运行**。"更新前处理在途实验"按 A5 的排空模式处理：等待完成或立即取消；首期不支持暂停后续跑。数据库迁移通常不可逆，建议更新前自动备份；回滚即恢复备份加旧版本程序。

**B11 主密钥与备份**。要在另一台主机重建，备份必须能恢复主密钥；但主密钥和加密凭据放在同一份备份里，等于明文备份。已定：主密钥单独存放在本机文件中，仅服务账号可读；备份时与数据分开保存和转移。

**B12 旧系统的数据与功能迁移**。推倒重来后，旧系统的历史结果是否导入、哪些旧功能有意不再提供，原文没有提到。已定：不迁移，旧数据都是测试用例。

**B13 数据集来源范围**。首期只有 Hub 适配器。RSI 常用自建任务，团队是否需要本地或私有数据集？若需要，首期加一个"本地目录"来源，也能顺带验证数据集来源边界确实可替换。

**B14 事件通知**。目前 agent 观察执行只能轮询。已定：优先级低。【建议】首期只用轮询：长操作都有统一的操作记录（C2），SDK 提供"等待完成"的辅助方法；事件流和 webhook 列为 P2。

### C 类：可直接写进约定

| 编号 | 约定 | 内容 |
| --- | --- | --- |
| C1 | 幂等提交 | 客户端提供幂等键；同键同内容返回原操作记录，同键不同内容报冲突；写明键的有效期 |
| C2 | 统一的操作记录 | 数据集准备、运行、成组提交、批量导出、维护操作共用一种操作记录：状态、阶段、进度、错误、结果入口、可执行的后续操作。SDK 只需一套跟踪逻辑 |

## 十、技术栈建议

技术栈主要由三条约束决定，而不是开发便利：Harbor 是迭代很快的 Python 框架，次版本升级可能带来破坏性变更；首期是单机、两三人、约 10 个并发试次；网页与 SDK 必须共用同一份 API 契约。

**选型**

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 服务端 | Python + FastAPI + Pydantic | worker 在服务进程内（A5），语言须与执行器一致；自动生成 OpenAPI，满足 C6；Harbor 的结果模型也是 Pydantic |
| Harbor 接入 | 独立虚拟环境，精确锁定版本，以子进程运行 | 见下文 |
| 数据库 | SQLite（WAL）+ SQLAlchemy 2 + Alembic | A8 的量级足够；Alembic 管理迁移，需要时可换 PostgreSQL |
| 队列 | 数据库中的队列表 + asyncio 调度 | 试次耗时长，需要取消和按容量调度；不引入 Celery 与 Redis |
| 产物 | 本地文件系统，按运行和试次分目录，经存储接口访问 | 满足 A5 为多机留位置的约束 |
| 前端 | React + TypeScript（Vite），构建为静态文件由服务端托管；API 客户端由 OpenAPI 生成 | 网页只能走公开 API，从结构上保证与 SDK 能力一致；运行时不需要 Node |
| SDK 与 CLI | Python，基于 httpx 的薄客户端；CLI 用 Typer，输出 JSON | 不依赖服务端内部代码（C5） |
| 鉴权与凭据 | 密码用 argon2；网页用会话 cookie；PAT 只存哈希；凭据用主密钥做 AES-GCM 加密 | 对应 B1、B2、B11 |
| 部署 | 每个版本一个 uv 环境，用 `current` 软链接切换；systemd 管理 | 更新与回滚就是切换软链接，对应第八节的存放边界 |

**Harbor 的接入方式**

在服务端代码里直接引入 Harbor 最省事，但会把服务端的依赖版本和 Harbor 绑在一起。建议写一个很小的"执行器运行程序"，装在锁定版本的 Harbor 环境里，由 worker 以子进程启动：输入是生成好的作业配置，输出是进度事件和结果文件。

- 升级 Harbor 不牵动服务端，必要时可让多个 Harbor 版本并存（第八节"版本关系"）。
- Harbor 出错不会拖垮服务进程；取消运行就是结束对应的进程组。
- 生成的作业配置先用 Harbor 提供的 JSON Schema 和只检查不运行的模式校验，再提交执行。
- 扩展包可映射到 Harbor 的 agent 配置：skill、MCP 服务、环境变量都有对应字段；bootstrap.sh 可能需要一个自定义 agent 包装。

**目录布局**

```
/opt/<app>/versions/<版本>/       程序与依赖，每个版本一个 uv 环境
/opt/<app>/current -> versions/<版本>
/opt/<app>/harbor/<Harbor 版本>/  锁定版本的 Harbor 与执行器运行程序
/etc/<app>/config.toml            部署配置
/etc/<app>/secrets/master.key     主密钥，仅服务账号可读
/var/lib/<app>/app.db             业务数据（SQLite）
/var/lib/<app>/artifacts/         产物
/var/cache/<app>/                 任务内容与准备缓存
journald                          服务日志
```

**看似方便、但不合适的选择**

- Celery、Redis、Kubernetes、微服务：单机两三人用不上，只增加运维面。
- 在服务端同一环境里直接引入 Harbor：版本耦合，见上文。
- 服务端模板渲染页面并绕过 API：开发快，但网页会逐渐长出 SDK 没有的能力。
- 把日志和产物存进数据库。

**测试**

- 单元与集成测试用 pytest，四个边界都用测试替身适配器（C4）。
- 端到端测试在装有 Docker 的 Linux 主机或虚拟机上进行：用管理脚本安装，再跑真实任务。agent 选 Harbor 默认的 oracle，它执行任务自带的参考解法，不调用模型。
- 在持续集成中检查前端客户端、SDK 类型与服务端 OpenAPI 是否一致。

**待验证的技术风险**（建议首周用最小原型验证）

1. 以子进程接入 Harbor 时，如何实时获取试次进度。
2. Harbor Docker 环境的网络白名单在目标主机上可用（依赖 nftables），以及作业配置能否强制收紧任务声明的网络策略。
3. 准备阶段能否单独调用 Harbor 的环境构建与镜像拉取，供预加载复用。
4. 扩展包中 bootstrap.sh 的执行时机与 Harbor 的 agent 安装阶段如何衔接。
