## 1. 问题

### 1.1 工作流靠 Agent 现场发挥

现在只有一种“适配”：`maestro-package` skill 加通用 SDK，其余由 Agent 现场发挥。2026-11-04 用 Codex 跑了首轮 Mesh2CAD 附件改进（服务与 SDK `0.4.1.dev0`，一个基线加两个候选，共 18 个试次），暴露出两类问题：

- **流程没讲到的判断，Agent 会漏掉。** 它没有读 SDK 已经提供的题面；改进类别也没分清，执行可靠性改进（C1）和交付诊断（C2）都容易被说成建模能力提高；数事件时按正则给多行命令分类，结果漏计。
- **工作流需要的机械活，Agent 每次从头写。** 它写了一个 300 行的脚本和 32 KB 的本地状态文件，自己管快照、运行、幂等键和授权的试次数；证据定位写在正文里；报告逐份手写。这些对下一轮、下一个附件都一样。

Agent 换一个工作流（比如比较模型、调 Harness 参数、复现论文结果），还会遇到同样的问题。所以要解决的是“为一种工作流配齐 skill 和 SDK”这件事本身。首轮实验发现的平台问题记在 `Gitea#18`，不在本提案（U-75）。

### 1.2 留出集与“任务天然可见”矛盾

改进附件、提示词或任何会根据结果迭代的东西（RSI），都应该留一组验证集：改进者只在开发集上看细节，最后在没看过的题上确认效果。平台现在的设计与此矛盾：

1. **所有任务天然可见。** 团队成员互相信任，数据集、题面和产物对所有成员开放，PAT 也能读，包括参考解与验证代码（U-10、U-31，[09](../design/09-identity-security.md) 第 6 节）。
2. **实际测试会暴露验证集内容。** 在验证集上跑一次，被测 Agent 就会在容器里读到题面，trace、日志和产物都会把它带出来，而这些证据按“证据从宽”对团队开放。
3. **现在只能靠自觉。** 首轮 Mesh2CAD 实验为了让留出集独立，从全集里删掉留出题另建了数据集，再手写清单。题目是否泄露，完全取决于 Agent 是否遵守 skill 和工作区说明。

### 1.3 外部 benchmark 进不来

团队想测的 benchmark（目前主要是 CAD 领域）多数发布在 Hugging Face 上，提供方没有做 Harbor 适配，格式也各不相同；平台的数据源只有 Harbor Hub。

以 [CADGenBench](https://huggingface.co/datasets/HuggingAI4Engineering/cadgenbench-data) 为例（2026-11-03 读数据集卡片所见，评测代码尚未核对）：

- 公开 81 道题，其中 49 道根据工程图生成、32 道编辑 STEP，每题要求输出一个 `output.step`。
- 参考实体放在私有仓库里，作者明确规定只在服务器端评分。
- 评测代码（CAD Score：先过有效性门槛，再对形状、接口、拓扑三项加权）在 GitHub 公开。
- 提交方式是把产物和 `meta.json` 打成 zip，上传到排行榜 Space。

答案是私有的，在本地重新评分本来就做不到。这个例子真正要的是“在平台上执行、导出提交包”，本地最多给出有效性门槛的结果。

## 2. 设计原则

- **平台只保存别人要依赖的事实**（U-59）。工作流记录、留出标记、读取汇总都是事实；“读过算不算用掉了”“这个候选值不值得保留”是判断，留给 skill 和写结论的人。
- **记下发生了什么，不拦截。** 留出集首先是实验有效性问题，不是保密问题。机器学习里的测试集通常不加密，靠的是约定，以及事后能说清楚调参时没有碰过。平台不设拦截或审计门，“证据从宽”不变（U-78）。
- **只做眼下真实需要的。** 评测拆分与可替换的执行器暂缓，写明什么情况下再启动（第 6 节）。

## 3. 工作流适配（U-73～U-76）

### 3.1 三层分工

判断一条规则放在哪一层，沿用 U-59 的标准：它保护的是谁要依赖的哪个事实。

| 层 | 放什么 | 例子 |
| --- | --- | --- |
| 平台 | 团队或用户要依赖、要复查的事实 | 快照、运行、比较、分析快照；工作流记录与当前最优指针；留出标记与读取汇总 |
| SDK 工作流模块 | 这种工作流的机械活，只输出事实、不下结论 | 整理题面、准备候选、收集证据并建索引、生成报告 |
| skill | 流程和判断方法，只给建议、不强制格式 | 先读题、给假设分类、预先写下证据标准、何时停下 |

“这个事件是不是解释器错误”“这个候选值不值得保留”属于判断，不进 SDK。

### 3.2 工作流包

一个工作流由三部分组成，放在 SDK 内部、随 SDK 同版本发布，数量多了再考虑拆成单独安装的扩展（U-76）：

- skill：放在 `skills/<名称>/`，由 `maestro_sdk.skills.install` 安装（已有机制）。
- SDK 模块：放在 `maestro_sdk.workflows.<名称>`，只组合公开 API，不访问服务器文件系统。
- 记录类型：这个工作流在平台上留下的记录长什么样（第 3.3 节）。

`maestro_sdk.workspace.init(dir, workflow="<名称>")` 在工作区模板里写入这个工作流的说明；不指定工作流时保持现状。

### 3.3 工作流记录

平台不为每种工作流建专门的表，而是提供一种通用记录，像评论一样挂在集合、运行或附件（可以指定到某个快照）上（U-73、U-76）：

- 类型（如 `attachment-candidate`）、标题、正文（JSON）、作者、时间与修改历史，规则与集合的修改记录相同（U-46）。
- 第三部分起也可以挂在数据集版本上，用来记上传数据集的来源说明（第 5.1 节，U-89）。
- 除了挂靠的对象，正文还可以引用其他运行、附件快照、试次与产物。平台只核对被引用的对象存在且可读，不解释正文的含义。
- 正文可以带证据摘录（几行日志或 trace）。原始产物 7 天后过期，摘录随记录保留，这样决定的理由以后还能读懂。摘录有大小上限，入库前按基本规则脱敏（U-10）。
- 网页在集合、运行与附件的详情页列出挂在上面的记录、显示原文，像评论区一样。不按类型做专门的展示（U-74）。

正文的结构由工作流包定义，SDK 模块负责读写，平台不做 schema 校验。

### 3.4 适配新工作流的路径

用户描述想要的工作流后：

1. Agent 在工作区里先写这个工作流的 skill 和脚本，只用公开的 SDK；需要留在平台上的，就用通用记录。
2. 跑过一两次、证明可以复用后，把稳定、通用的部分整理成工作流包，合入 SDK 发布。
3. 只有通用记录也装不下、确实需要平台理解的事实，才另开提案改平台。

这样一轮实验里的临时做法不会直接固化成平台功能。

### 3.5 例子：附件改进

**skill。** 修订 `maestro-package`：

1. 改进前先读开发题的题面和允许读的检查说明，写清输入、交付物、评分目标与未知项。
2. 先给假设分类，比如安装可用、执行可靠性、有效交付率、建模质量，每类用对应的指标判断，不从可靠性改进推出质量结论（U-74）。
3. 提交前写下什么证据支持什么决定：机制确实发生、暂留使用、已证明整体改善。父版本缺评分时只报告机制证据，不为补齐自动追加试次。
4. 平台已有的事实不在笔记里重抄；附件 A/B 集合已经保证固定维度，不必再比对配置。
5. 统计 trace 中的事件时，先用事件索引定位，逐条核对后再计数，并记下计数方法。
6. 建集合时标出留出题；迭代只在开发题上提交，不打开留出题的内容；报告附上留出题的读取汇总与运行次数，由写结论的人判断留出集是否仍然有效（第 4 节完成后加入）。

**SDK 模块 `maestro_sdk.workflows.attachments`（U-89）。**

- **题面整理**：把指定任务的题面和公开元数据写成本地文件。
- **准备候选**：从集合和父候选出发解析新快照，列出计划试次、与父候选的附件差异，以及安装验收能否复用的提示。提示依据是 `bootstrap.sh` 未变、父候选在同一 Harness 上安装成功；复不复用由 Agent 决定。
- **收集证据**：按范围增量下载并校验摘要、生成清单；为 trace 生成事件索引（行号、命令、退出码、输出位置）。只建索引，不分类。
- **生成报告**：从比较结果和候选记录生成 JSON 与 Markdown，包括覆盖率、按原因的失败、逐题结果、计分口径、已知与未知的费用；第 4 节完成后加上开发题与留出题分开的成绩和留出题的读取汇总。
- **候选记录的读写**：见下。

**记录类型 `attachment-candidate`。** 一个候选是集合中的一份附件快照，正文包括：

- 父候选，假设（要改什么、为什么、怎样算无效），以及改进类别（自由文本）。
- 来源证据：引用加摘录。
- 关联的运行，按附件自动查出，不手填。
- 决定：未决 / 保留 / 放弃 / 证据不足，加理由与证据等级；每次决定都保留。
- 改进 Agent 自报的信息（可选）：模型与费用。

**当前最优**是集合上的一个指针（U-76），与基线类似：指向集合中的一个候选，改指向时记作者、时间与理由，进集合的修改记录。之后的比较可以默认以当前最优为起点。它取代 U-61 的做法（在分析快照的结论里写明谁最优）；分析快照照旧用于冻结比较。

### 3.6 其余已定的取舍（U-76）

- 改进 Agent 自己的 trace 暂不存进平台。
- 暂不找第二个工作流来检验通用性，等有了实际需求再说。
- 不单独做验证：实现完成后，用户重新跑一遍附件改进实验，从实际使用中发现问题。

## 4. 留出集（U-87）

### 4.1 集合里的留出标记

- 建集合时可以从集合的数据集版本中标出一组题目作为留出题，其余为开发题。标记写进集合规格，建好后不能改；要改就复制成新集合，原集合与它的快照不变（U-47）。留出集的意义在于“看结果之前就定好”，所以建时固定。
- 集合仍然只对应一个数据集（U-47）。同一个数据集里标出留出题即可，不必像首轮 Mesh2CAD 那样从全集里删掉留出题、另建数据集。
- 标记不限制运行：加入集合的运行可以包含任何题，从集合提交时照常选题。建议网页从集合新建运行时默认只选开发题，留出题要显式勾选。
- 同一批题可以在多个集合里标为留出；读取记录落在题目上（第 4.2 节），所以各集合看到的是同一份读取情况。

### 4.2 读取记录落在题目上

同一道题可以从集合、数据集页面、运行详情或 SDK 读到。只在集合的入口记录，绕一下就漏了，所以读取记录落在题目上（U-78）。

- **只有能看到任务内容的读取才算**（U-79）：题面、参考解与验证代码、跑这道题的试次产物（含 trace 与日志，它们会带出题面），包括打包下载与导出。汇总分数、逐题分数、失败原因码、列表中的题名都不算；“在上面跑过几次”从运行记录查，不另记。
- 记录谁、通过网页会话还是哪个 PAT、读了哪一类、什么时间。现有的审计只记写操作（[09](../design/09-identity-security.md) 第 4 节），读取记录是新增的；每个返回上述内容的接口都要接入。
- **只存汇总行**（U-80）：每个“题目 × 读取者（账户，及 PAT 或网页会话）× 读取类别”一行，记首次时间、最后时间与次数，永久保留。行数上限是题目数 × 成员数 × 类别数，不设保留期与配置项。
- SDK 可以按一组题目查询读取汇总，不限于集合里标出的留出题。

### 4.3 集合页与比较

- **集合页**显示留出题的读取汇总，并标出集合建立之后是否有人读过；另列留出题上的运行次数（建议按全团队、自集合建立起统计）。
- **比较**在有留出标记的集合里，把开发题与留出题分成两组统计：各自按现有规则对齐、剔除、算均值与差值（[08](../design/08-collections-comparison.md) 第 3、4 节），不混成一个均分；逐任务表标出留出题。分析快照保存两组结果。临时比较不受影响。

## 5. 外部 benchmark：上传数据集与导出提交包

### 5.1 只接受已转换好的数据，平台只检查（U-89）

每个 Hugging Face benchmark 基本都要单独写转换器，所以平台不读取原始数据，也不在服务器上运行转换代码。使用者在本地把 benchmark 转换成 Harbor task（可以参考 Harbor adapter），用 SDK 上传；平台只检查上传的内容是合格的 Harbor task，然后作为一种新的数据集来源。之后与 Hub 数据集走同一套首次准备与准入（U-89），提交、比较也相同。这取代 U-68 中“增加 Hugging Face 等数据源与转换配方”。

- **上传内容**：直接是 Harbor task 目录，不另加清单（U-89）。
- **版本身份**：上传内容的 digest。
- **来源说明**：上游仓库、revision、转换器版本等，先用挂在数据集版本上的工作流记录记下（第 3.3 节），平台不核实；确实需要平台理解时再加字段。
- **上传通道**：倾向复用附件的内容寻址快照与增量上传（[03](../design/03-configuration-attachments.md) 第 6 节）。权限归 N-29 的 `datasets` 权限组（U-69）。
- **代价**：平台无法“检查上游更新”，转换能否复现由使用者负责。

N-19 计划的“本地目录来源”可以与此合并考虑。

### 5.2 评分仍由题目自带的 verifier 完成

- 转换出的题目自带 verifier，只做本地能做的检查，例如 STEP 有效性门槛；什么都不能检查时可以不评分，结果显示为缺评分。
- Harbor 在 agent 结束、开始验证时才把题目的 `tests/` 目录（验证代码与参考答案）上传进容器（2026-11-05 核对 Runner 锁定的 Harbor 0.24.0，`harbor/verifier/verifier.py`），所以被测 Agent 在执行中读不到参考答案。前提是转换时不把答案放进环境镜像。

### 5.3 导出提交包

- 题目把交付物（如 `output.step`）写进 Harbor 的产物目录，按约定的目录，不在 `task.toml` 中另行声明（U-89）；平台随试次保存。要确认这些文件完整进入产物，不被产物上限截断，也不被当成文本脱敏。
- 提交包（如 CADGenBench 的 zip 与 `meta.json`）由 SDK 或使用者的脚本，从现有的打包下载（[07](../design/07-artifacts-export.md) 第 5 节）拼出，平台不定义结果包格式。产物 7 天后过期，要在过期前导出。

### 5.4 CADGenBench 手动验证

先于本部分的实现，在独立的验证会话中进行：

1. 手动把少量题目转换成 Harbor task，verifier 只做 STEP 有效性门槛，交付物写进产物目录。
2. 在全新的 state 上运行，确认 `output.step` 完整进入产物，不被截断或脱敏。
3. 在平台外用 CADGenBench 的评测代码确认：有效性门槛能否容器化放进 verifier，是否需要 GPU。
4. 从打包下载拼出提交 zip，核对格式。
5. 根据结果写出上传检查与交付物目录约定的草案，回填本提案。

真实模型请求需要用户确认预算后再发；没有确认时，用固定脚本生成 STEP 来代替 agent。

## 6. 暂缓与以后的方向

### 6.1 评测拆分（暂缓，U-86）

即在平台里给已有产物换一种评测重新打分、导入外部结果包只做评测。它要求分数挂在独立的评测记录上，一个试次可以有多份评测，比较按评测身份分组，还要有评测器、评测任务的排队与资源、参考答案与评测方案对象、输出文件的长期保留等；设计见本文件在 Git 历史中的第一版。

- **启动条件**：出现第一个需要在平台里重新评分的真实案例，例如评测器修正后要给旧产物重新打分。
- **第一步**：先考虑平台只接收外部上传的分数，每条带评测器的名称与版本，比较时选用哪一种分数来源。计算在使用者那边完成，符合 U-59。只有“评测器必须在服务器上运行”成为真实需求时，才做评测器与评测任务。
- **暂缓期间的替代做法**：在本地下载产物评分，把结果写进工作流记录或报告。
- 检查环境状态的题（如 Terminal-Bench）容器结束后就无法事后评测，与执行器无关。

### 6.2 可替换的执行器（想法，U-88）

Harbor 限制了执行器能做的事：任务格式、每个试次一个容器、只能跑单机 Docker 里的任务。但它也提供了最难重做的部分：Agent 接入、隔离、超时、日志，以及 Hub 与 adapter 的生态。现在不取代它。服务进程不 import harbor，只经带版本的 Runner 协议与独立的 Runner 子进程交接（[15](../design/15-stack-harbor.md) 第 2、3 节），以后可以在同一协议后面加自己的执行器，队列、记录、比较、SDK 与网页不用动；和 Harbor 绑得比较紧的是数据集与准备。启动条件，任一成立即可：

- 出现 Harbor task 表达不了的任务，例如需要 GPU、远程环境或非容器执行；
- 每个试次一个容器的开销成为瓶颈（与 N-15 一起看）；
- Harbor 的方向与团队需求分道扬镳。

## 7. 实施

三部分各自从 `dev` 建短期分支，照常保持可运行、照常迁移；每部分合入时改写受影响的系统说明，并在本提案中标注已完成。三部分都完成后本提案归档；第三部分若长期不启动，就把它拆成单独的提案后归档其余部分。

## 9. 验收

- **工作流适配**：用户重新跑一遍附件改进实验（U-76）。
- **留出集**：建集合时标出留出题，之后不能修改，只能复制；只有能看到任务内容的读取进入汇总，汇总分数与题名不算；集合页显示建立后的读取；比较分开统计开发题与留出题，快照保存两组结果。
- **外部 benchmark**：CADGenBench 的题目能上传、执行，并从产物导出可提交的 zip，本地给出有效性门槛的结果。

## 10. 已回答的问题（U-89）

5. 不再逐个核对其他 CAD benchmark。
