# N-36 工作流记录：给人读写的文字与可跳转的引用

状态：完成（范围 U-95，确认实施 U-97） · 优先级：二 · 2026-11-07 · 相关：[01](../../design/01-domain-model.md)、[10](../../design/10-api-sdk-cli.md)、[11](../../design/11-web-ui.md) 第 3 节、[N-35](N-35-web-dataset-upload.md)、U-74、U-95、U-97

## 问题

工作流记录（N-31 起，现挂在集合、运行、附件名与数据集版本上）的正文只能是 JSON 对象，网页把它原样格式化显示，引用列成“类型 · 标识”，不能点开。结果是：

- 人写的内容也得写成键值对。数据集版本的来源说明本来是一段话，网页却预填 `upstream_repo`、`revision`、`converter_version` 的 JSON 模板。
- SDK 写的结构化记录（如 `attachment-candidate`）里，假设、理由这些段落埋在 JSON 字符串里，读起来费劲。
- 引用只显示标识，要自己复制去找对应页面。

“正文为 JSON”出自 N-31 第 3 节的提案原文，引用不做链接是实现时的选择，两者都不是用户专门定过的边界。

## 方案

保留 JSON 正文给程序用，另加一个给人读写的文字字段；同一个事实只写在一处，不做两份互相同步。

### 1. 记录新增 `text`

- 记录和每份修订都多一个 `text`：Markdown，可以为空，上限与正文相同（64 KB），随修订历史保存。
- 不做脱敏，与正文一样处理；脱敏仍只作用于证据摘录（U-95）。
- 正文 `body` 改为可以为空（不填时存 `{}`），纯文字记录不必硬塞 JSON。
- 平台照旧不解释 `text` 与 `body` 的含义。约定：`text` 写给人，`body` 写给程序，SDK 工作流不把 `body` 里的事实再抄一份到 `text`，网页也不从一边生成另一边。
- 接口与 SDK：`records.create`、`records.update` 多一个 `text` 参数，`get`、`list`、`history` 返回它。旧记录的 `text` 为空，不迁移内容（U-31 不承诺向后兼容）。

### 2. 网页显示

- `text` 按 Markdown 渲染，关闭原始 HTML。
- `body` 不再显示 JSON 原文，改成通用的可读显示：对象的键作标签、值在下面，数组作列表，字符串按 Markdown 渲染，数字、布尔值、空值直接显示；空对象不显示。原文放在“查看 JSON”折叠里。显示规则对所有类型相同，不按记录类型专门展示（U-74）。
- `text` 里可以写站内链接，例如 `[那次运行](/runs/<id>)`，按普通链接打开；这类链接平台不核对对象是否存在，需要核对的仍放进引用（U-95）。

### 3. 引用可以跳转

引用与摘录的来源都显示成链接：

| 引用类型 | 跳到 |
| --- | --- |
| 运行 | `/runs/<id>` |
| 试次 | 所属运行页并选中该试次 |
| 产物 | 所属运行页的产物标签，定位到该试次 |
| 集合 | `/collections/<id>` |
| 分析快照 | `/snapshots/<id>` |
| 附件快照 | 附件页，展开该附件并定位到这个快照 |

试次和产物的引用只存了自己的标识，接口在返回记录时附上所属运行的标识，供网页拼链接；附件页还没有按快照定位的地址时一并补上。被引用对象进了回收站或已物理删除时，链接照常显示，打开后由目标页说明状态。

### 4. 网页添加与编辑

- 表单主要是类型、标题和文字（`text`）。正文 JSON 放进折叠的“高级”区，默认为空；有内容时提交前检查格式（现有逻辑）。
- 数据集版本页不再预填 JSON 模板，改为在文字里给出来源说明的提示（上游仓库、修订、转换器版本），由人照着写一段话。
- 编辑、删除、修订冲突与历史的规则不变。

### 5. SDK 工作流

`maestro_sdk.workflows.attachments` 的候选记录：`hypothesis` 和决定的 `reason` 等结构照旧存在 `body`，`candidates()` 照旧读 `body`。可选地让调用方另写一段 `text` 作为给人看的说明，但不自动从 `body` 生成。skill 中关于记录的建议同步一句：给人看的话写 `text`，程序要读的写 `body`。

### 放弃的做法

- 只把 `text` 当作 `body` 里的一个约定键：后端不用改，但网页编辑时要从 JSON 里拆出这个键再拼回去，平台也要特殊对待正文里的一个键；省下的后端改动不多。
- 正文整体改成 Markdown、结构化数据另设字段并迁移旧记录：附件改进的 SDK 与现有记录都要改，现有问题用不着。
- 结构化记录不再修改，人的补充改用回复：要新增“回复”概念，暂时没有具体需要。

## 影响

- 数据库：`workflow_records` 与 `workflow_record_revisions` 各加 `text` 列（默认空串），新增一个迁移。
- 接口与 SDK：记录的创建、修改与返回多出 `text`，`body` 可省略；返回的试次、产物引用带所属运行。OpenAPI、SDK 模型与网页类型随之生成。
- 网页：`WorkflowRecords` 组件的显示、表单与引用链接；附件页按快照定位的地址；新增一个 Markdown 渲染依赖（第三方许可证清单随之更新）。
- 系统说明：[01](../../design/01-domain-model.md) 工作流记录一行、[10](../../design/10-api-sdk-cli.md) 记录一段、[11](../../design/11-web-ui.md) 第 3 节记录区与第 1 节数据集上传中“来源说明”的写法、[13](../../design/13-testing-plan.md) E2E-OUT-05。
- skill：`maestro-package` 中关于候选记录的建议加一句 `text` 与 `body` 的分工。

## 验收

- 网页能只填类型、标题和一段 Markdown 添加记录；正文 JSON 可以不填。Markdown 渲染正确，原始 HTML 不生效。
- 已有的 `attachment-candidate` 记录显示为可读的标签与列表，不再是 JSON 原文，原文仍可展开；SDK 的 `candidates()` 与 `decide_candidate` 行为不变。
- 六种引用都能点开到对应页面与位置；被引用对象在回收站时打开后有说明。
- 编辑 `text` 保留修订历史，冲突检查照旧。
- 网页冒烟（E2E-OUT-05）覆盖文字记录的添加、编辑与引用跳转，在全新 state 上走一遍。

## 待定问题

已答（U-95）：`text` 不脱敏；上限 64 KB；`text` 里允许写站内链接。

## 结果

2026-11-07 按本提案实现，结论已并入 [01](../../design/01-domain-model.md)、[02](../../design/02-datasets-preparation.md)、[08](../../design/08-collections-comparison.md)、[10](../../design/10-api-sdk-cli.md)、[11](../../design/11-web-ui.md) 第 1、3 节与 [13](../../design/13-testing-plan.md) E2E-OUT-05。与方案的差别：

- 试次与产物引用的所属运行放在记录的 `reference_locations` 里返回，而不是加进引用对象：SDK 的 `decide_candidate` 会把读到的引用与摘录原样写回，引用对象多出字段会被修改接口拒绝。
- 附件页已有 `?snapshot=<id>` 地址，只补了滚到该快照，以及快照不在列表中（回收站或已删除）时的说明。
- Markdown 渲染用 `react-markdown` 与 `remark-gfm`（MIT），网页脚本因此增大约 170 KB（未压缩）。
