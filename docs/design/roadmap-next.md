## 1. 现场与仓库的差异

讨论时核对到的事实（2026-10-27）：

- 远端分支 `fix/separate-verifier`（基于 `1fdef62`）未合入 `dev`，部署现场运行过其构建 `0.3.0-bfe288595f25`。其中 `bfe2885`（准备独立验证器与 Compose 辅助服务镜像）与 `34a1293`（修 `!reset` override 与操作列表 500）是正式修复；`e21d4d8`、`8d717d1` 是 CAD 演示用的 Terminus-KIRA 适配。
- 本机分支 `feature/ci-package`（`c45704a`）让 CI 在检查通过后构建发布包，未合入 `dev`。
- `dev` 上每个任务的主环境已可各不相同（按任务的 `spec_digest` 准备与缓存），缺的是独立验证环境与辅助服务。

## 2. 第一优先：收拢现场与明显的体验问题

| 编号 | 想法 | 要点 |
| --- | --- | --- |
| N-01 | 合入独立验证环境 | 只取 `fix/separate-verifier` 中验证器相关的两个提交，KIRA 丢弃（已定）。分支里标为“待用户确认”的三条规则（辅助服务须声明 CPU 与内存；构建参数只接受带非秘密默认值的写法并冻结；对带辅助服务的任务更严格）在合入前确认 |
| N-02 | CD：推送即发布，不自动部署（已定） | 推送到 GitHub 或 Gitea 的 `dev` / `master` 后，CI 检查通过即构建发布包：`dev` 为带提交标识的预发布版本，`master` 的版本 tag 为正式版本；SDK wheel 一并发布。部署仍由管理员执行 `maestroctl update`（U-29 不变）。发布凭据只给发布步骤，CI 主机与真实实例同机时保持现有隔离 |
| N-03 | 网页改为侧边栏导航 | 统一顶层与管理页的布局 |
| N-04 | 长任务名不破坏排版 | 截断加悬停显示全名、可复制；有共同前缀时省略中间；修正 flex / grid 子项与表格的宽度约束 |
| N-05 | 产物按层级打包下载 | 运行页按 任务 → 试次 → 执行尝试 显示目录树，每层可下载 zip。只对已结束、已取消或已中断的运行提供，点击时生成并流式返回，不预先存放（已定）。复用导出模块的大小上限与脱敏 |
| N-06 | 附件下载与网页预览 | 附件包的目录树、整包下载、文本文件预览（有大小上限，`bootstrap.sh` 高亮） |
| N-07 | 数据集版本操作 | 三处缺口都补（已定）：(a) 已有数据集上直接“添加新版本 / 检查上游更新”，不必重新搜索；(b) 已选的运行配置或方案中切换到同一数据集的另一个版本；(c) 新建运行页先选数据集再选版本，不再平铺所有“数据集 @ 版本” |

## 3. 第二优先：核心能力

| 编号 | 想法 | 要点 |
| --- | --- | --- |
| N-08 | 准备阶段的网络在本机配置解决（已定方向） | 准备代理（开关、地址、`no_proxy`）从 `config.toml` 移到管理员网页，作为团队策略的修订，新的准备立即生效，并记入准备记录；`maestroctl check` 报告 Docker 的 registry 镜像源配置，不代为修改系统 Docker。不改写作者的 Dockerfile；按 digest 拉取时镜像源不影响内容身份，不进入缓存键 |
| N-09 | 常规 Harness：至少 Codex 与 Claude Code（已定） | 把 OpenCode 的做法抽成通用的“容器内 Harness”模板：密钥只以临时文件进容器、Agent 阶段只放行模型地址、版本钉死。Claude Code 需要 Anthropic 协议，Codex 需要 OpenAI Responses；协议不匹配在受理时拒绝。Harbor 自带的这两个 agent 在锁定版本中的安装方式与参数须实测；考虑与 Harbor 升级一起做 |
| N-10 | Harness 安装缓存：先做本机包缓存代理（已定） | 本机运行 npm / pip 等包的缓存代理，容器 setup 阶段的安装请求经它取包，首次下载后留存本机。镜像与容器不变，不涉及 C-07 的挂载约束；仍然每试次执行安装，只是不再下载；不经包管理器下载的 Harness 不受益，需另行处理。代理作为部署的可选组件，由 `maestroctl` 安装或指向已有服务 |
| N-11 | P1：实验集合、对齐比较与分析快照（已定纳入） | 按 [08](08-collections-comparison.md)。新增 Harness 之后，“同一数据集上比较不同模型与 Harness”是主要用途 |
| N-12 | P1：带排空的更新与维护模式（已定纳入） | 按 [12](12-operations.md) 第 5 节。CD 让更新变频繁，现在有运行在跑时更新会被拒绝 |

## 4. 第三优先：技术验证与后续

| 编号 | 想法 | 要点 |
| --- | --- | --- |
| N-13 | 试次粒度调度的技术验证 | 撤销 D-020 等于平台接管 Harbor Job 层的调度（并发、排队、重试），单个试次仍由 Harbor 执行。收益：每任务不同试次数、单试次取消与补跑、按试次精确预留容量、多个运行穿插、每次重试是独立的执行尝试。先实测：Runner 每次启动的开销、绕过 Job 直接调用单试次的接口在锁定版本中是否可用、10 个试次并发的资源占用，再决定是否在之后的版本实施 |
| N-14 | 跨任务共享镜像 | 现在缓存按整个任务计算，内容相同的验证器或辅助服务镜像在任务间各存一份。改为按单个镜像内容做缓存键并引用计数。只合并内容完全相同的镜像，相似的 Dockerfile 交给 Docker 层缓存，不做 Dockerfile 语义比对。存储暂时不是瓶颈，排在 N-01 之后 |
| N-15 | Docker 开销 | 每个试次的容器、网络、出口控制 sidecar 开销以后会成为瓶颈。先测量各部分占比，再考虑同运行内复用容器或远程执行环境；后者涉及自托管定位，需重新讨论 |

各实施记录中仍未完成、与上面相关的条目：共享构建不计入主机 CPU / 内存（M4、M8）；Harbor schema 导出、`--dry-run` 与 `compatibility.json` 未接入（15 第 4、6 节），升级 Harbor 前宜补上；10 试次并行压测未做（M8）；数据集版本没有独立的网页地址、“停用但仍在使用的对象”未进待处理（M7）。

## 6. 不做或暂缓

- 自动部署（N-02）。
- 改写作者 Dockerfile 换源：只在本机代理与镜像源都无法解决时，作为显式的准备方法选项再讨论，且须计入准备规格。
- Harness 缓存的另两种做法：每试次复制宿主缓存的安装包、按“任务镜像 × Harness 版本”预构建派生镜像（用户不倾向）；只读卷挂载 Harness 需先改 C-07 / U-16。
- 公平调度：2～3 名活跃成员时意义不大。
- 异机备份恢复：保留为 P1，本阶段不纳入。

## 7. 产品定位与开源

用户决定（2026-10-27，U-31）：在内部团队使用之外，同时尝试两个方向，二者不冲突：

- **A. 开源的自托管平台**：其他团队或实验室在自己的机器上安装 Maestro，以可复现、可比较的方式评测“模型 × Harness × 数据集”，人和 agent 都能操作。可复现（内容按 digest 固定、配置摘要、按原快照重跑）、以 Harness 为一等公民的比较、agent 可操作（PAT、SDK、skill、幂等提交）是主要差异。
- **C. 公开评测结果**：用平台跑标准化评测并对外发布结果。每个公开结果附带数据集 digest、Harness 版本与模型配置，便于他人重现；模型调用费用与团队内部实验分开预算。

**多租户 SaaS 不做。** 现有安全边界建立在成员互相信任上（Docker 组约等于 root、附件可运行任意 `bootstrap.sh`、证据只做基本脱敏），改为多租户相当于重做产品。
