# N-11 集合、比较与分析快照

状态：已确认 · 优先级：二（0.4.0 的主要功能） · 2026-10-28 · 相关：[领域模型](../design/01-domain-model.md)、[方案与提交](../design/04-plans-submission.md)、[评分](../design/06-results-scoring.md)、[权限](../design/09-identity-security.md)、[API](../design/10-api-sdk-cli.md)、[网页](../design/11-web-ui.md)、U-46、U-47

## 问题

现在每个运行只有自己的结果汇总（[06](../design/06-results-scoring.md) 第 5 节），跨运行比较要自己导出再对齐。有了 Codex、Claude Code、OpenCode 等 Harness 之后，最主要的用法是在同一数据集上比较不同的模型与 Harness：要把几个运行并排放好、按任务对齐、核对除了想比的东西之外是否都一样，把不是被测对象造成的失败排除掉，并把某一时刻的结论存下来。

已有基础：

- 运行快照里的比较视图（`src/maestro/services/configuration.py` 的 `comparison_view`）已经去掉运行身份、凭据、任务子集与调度字段，逐字段比较它就知道两个运行除了什么之外都相同。
- 分数在运行结束后不再改变（06 第 7 节），所以已结束运行的计算结果可以直接冻结，不需要“结果修订”。
- 每个试次的结果记有错因与 Harbor 原始异常类型（`trial_results.failure_cause`、`exception_type`），可以按原因归类。

## 方案

四个概念：

- **比较**：任意勾几个运行即可现算的一张表。不保存，设置记在链接里，可分享。平台检测哪些维度不同，有意外差别时警告，但不拒绝。
- **集合**：用户自己维护的一组运行引用，例如“TB2 各家模型”。平台不替用户挑运行。
- **集合规格**：建集合时选定的场景，规定哪些维度可以变、其余维度固定为什么值。只有符合规格的运行能加入；规格决定集合的摆法，也可以直接当方案用来提交新运行。
- **快照**：把某一刻的比较（运行清单、设置、摆法与算好的整张表）冻结下来，附上人或 Agent 写的结论。

### 维度

比较视图的字段归成以下维度，条件核对、集合规格与表格摆法都以维度为单位：

| 维度 | 包括 | 在集合中 |
| --- | --- | --- |
| 数据集 | 数据集内容摘要 | 永远固定 |
| 计分规则 | 指标、单位、方向、阈值、聚合规则 | 永远固定 |
| 模型 | 提供商、协议、地址、模型名、模型参数 | 可选为可变 |
| Harness | 名称、版本、上游版本、内容摘要、参数 | 可选为可变 |
| 附件 | 附件列表、版本与参数、加载顺序 | 可选为可变 |
| 资源与时限 | CPU、内存、Agent / 验证 / 附件安装时限 | 可选为可变 |
| 重复次数 | 每任务计划试次 | 可选为可变 |
| 作者参数 | 任务作者定义的参数值（秘密参数既不比值，也不比用的是哪个凭据） | 可选为可变 |
| 其他运行设置 | 比较视图里不属于以上的字段 | 永远固定 |

任务范围、并发、运行总时限、凭据、运行身份不是维度：它们不进比较视图，任务范围的差别由“共同任务 / 全部任务”处理（见故事 7）。“固定”是严格的：维度内任何字段不同都算不同，例如同一模型换了中转地址或改了一个模型参数，就是模型维度变了。

### 集合规格与预设场景

| 预设场景 | 可变维度 | 默认摆法 |
| --- | --- | --- |
| 比较模型 | 模型 | 排行榜 |
| 比较 Harness | Harness | 排行榜 |
| 模型 × Harness | 模型、Harness | 矩阵（行模型、列 Harness） |
| 附件 A/B | 附件 | 排行榜 |
| 重复稳定性 | 无（同一配置多次运行） | 排行榜，每次运行一行 |
| 自定义 | 从可选维度中任意勾选 | 正好两个可变维度时为矩阵，否则排行榜 |

- **数据集和计分规则不能设为可变**，Oracle 运行不能加入集合：跨数据集或跨计分规则的集合建不出来。
- **固定维度的值**从三个入口之一得到：从一个已有运行取；像新建运行一样逐项填写（可变维度留空）；在批次页或临时比较页点“建成集合”，平台把检测出的不同维度作为可变维度、其余作为固定维度预填，用户确认。规格保存固定维度的内容值（用于核对），以及取得这些值的请求引用（数据集版本、模型配置修订、Harness 版本、附件版本，用于预填新建运行的表单）。
- **加入运行时核对**：运行的固定维度逐字段与规格比较，有一处不同就拒绝并列出不同的字段。
- **规格建好后不能改。** 要改就“复制成新集合并修改规格”：符合新规格的运行自动带过去，不符合的列出来；原集合与它的快照保持原样。
- **集合就是方案**：在集合页点“新建运行”（或在新建运行页选择集合），固定维度已填好且锁住，只需选可变维度、任务范围与并发；也可以放进批次草稿，一次补齐矩阵里的几个格子。受理时在同一事务里加入集合，受理时的核对与加入运行时相同。不另存一份方案，避免两份配置各自漂移。

### 摆法

- **排行榜（默认）**：每个运行一行；每个可变维度一列，后面是分数列（参与任务数、有效 / 计划试次、均分、样本标准差、通过率、计为 0 分的失败数、剔除数、已知费用与 tokens），可以按任一列排序。顶部“相同条件”一栏列出所有固定维度的值。
- **矩阵**：正好两个维度在变时可用，一个维度放在行上、另一个放在列上，格子里是均分，点格子看该运行的汇总。同一配置有多次运行时，同一格并列显示各次的值（如“0.62 / 0.60”），不平均、不合并；没有运行的格子显示“—”。
- **逐任务表**：每行一个任务，每列一个运行，列标题用可变维度的值（如“gpt-6 · Codex 0.165”），可以在集合里给某一列起名。
- **基准与差值**：排行榜选一行作为基准（默认第一行），其他行显示与基准的差值；差值规则见“统计口径”。
- **保存方式**：集合保存摆法（排行榜或矩阵、行列放哪个维度、排序、基准），团队里谁都能改；它不属于规格。快照冻结当时的摆法；临时比较的摆法记在链接里。

### 用户故事

**1. 先看一眼。** 小王在新建运行页把 Codex、Claude Code、OpenCode 三种组合放进一个批次提交。跑完后在批次页点“比较这一批”（也可以在运行列表多选后点“比较”），打开临时比较：

- 条件核对写着“数据集内容、计分规则、资源、重复次数相同；不同的是模型、Harness”。不需要事先声明任何东西。
- 默认是排行榜，因为正好两个维度在变，可以切成“模型 × Harness”矩阵。
- 逐任务表可筛选“结果不一致”“都没通过”“只有某列通过”等。点格子跳到那个运行、那个试次的执行页。
- 可以导出整张表为 CSV。链接贴到群里，别人看到同一张表、同一种摆法。

**2. 剔除不是被测对象造成的失败。** Claude Code 那一列有 9 个试次失败：7 个是中转站限流，2 个是服务重启被中断。小王点“剔除外部原因”，旁边列出将剔除的类别与各自数量，也可以逐类勾选。表格立即重算，页面注明“已剔除 9 个试次（限流 7、服务重启 2）”。这只影响这次比较，不改运行记录；集合记住当前的剔除设置，快照冻结它。SDK 用一个参数做到同样的事。

- 没剔除的执行失败在比较里**算 0 分、未通过**，否则一个总把环境弄崩的 Harness 会显得比实际好。单个运行详情页的汇总保持现状（失败不计分母）。
- 剔除后某个任务在某一列已经没有有效试次，这一行从**所有列**一起去掉，保证比的是同一批任务；页面写明“因剔除少比了 N 个任务”。只剔除了部分重复试次时，用剩下的试次求均值，这一行保留。
- Agent 超时、拒绝任务本来就是有效分数，不在剔除范围内。

**3. 建成排行榜。** 小王觉得这张表值得长期维护，在比较页点“建成集合”。平台预填场景“模型 × Harness”：可变的是模型和 Harness，固定的是 TB2 2.0、1 核 2 GB、Agent 900 秒、重复 3 次、无附件。小王确认，起名“TB2 模型 × Harness”，写上用途。集合默认以矩阵显示。

**4. 别人往里加。** 两周后小李想把 sonnet-5.5 加进来。他在集合页点“新建运行”，表单里数据集、资源、重复次数都已填好且锁住，只需选模型和 Harness，再把三个 Harness 放进批次草稿一起提交，三个运行受理时就进了集合，矩阵多出一行。另一次小李想把一个 2 核 4 GB 的运行加进来，被拒绝：“资源与时限不同：CPU 1 → 2，内存 2 GB → 4 GB”。集合保留“谁在什么时候加了什么、删了什么”的记录。

**5. 重复实验。** 小王想让结果更可信，把一个已有运行再重跑一次。重跑就是一个独立的运行，符合规格就能加入；排行榜里是单独一行，矩阵里同一格并列两个数。平台不合并、不做额外处理。

**6. 想换个比法。** 后来团队想固定用 OpenCode，专门比各家模型在 2 核下的表现。原集合规格不能改，小王点“复制成新集合并修改规格”，选场景“比较模型”，固定 Harness 为 OpenCode 2.2、资源改为 2 核 4 GB。符合的运行自动带过去，其余列出不符合的原因。原集合和它的快照不变。

**7. 写结论、留存档。** 月底小王在集合页（临时比较也可以）点“保存快照”，写一段结论。快照冻结运行清单、规格、剔除设置、摆法、任务范围设置和算好的整张表，此后集合怎么变它都不变。三个月后原始日志过期被清理，快照里的数字仍在，格子标明“原始证据已不可用”，不给失效的链接；有运行被删进回收站或被物理删除，快照里这一行显示“已删除”，数字保留。

**8. Agent 自己做实验、写分析。** Agent 用 SDK 读集合规格 → 按规格提交运行（自动进集合）→ 等结束 → 读比较结果（与网页同一份数据）→ 保存快照并写分析。结论标明是谁、用哪个 PAT 写的，与平台算出的数字分开存放。

**9. 会被拦下或警告的情况。**

| 情况 | 临时比较 | 集合 |
| --- | --- | --- |
| Oracle 测试运行 | 不允许 | 不允许 |
| 数据集内容不同（同名数据集的不同版本内容也算） | 只并排列出各运行自己的原始汇总，不对齐任务、不给差值，说明原因 | 规格不允许，加入时拒绝 |
| 计分规则不同 | 同上 | 同上 |
| 其他维度出现意料之外的不同 | 照常比较，顶部警告并列出差别 | 固定维度不同则拒绝加入 |
| 观察到的模型实际版本不同 | 警告 | 警告 |
| 任务范围不同（一边 89 个、一边 80 个） | 默认只比共同的 80 个，可切到“全部任务”，缺的格子显示“未包含”；“全部任务”下不给差值 | 同左 |
| 运行还没结束 | 能看，标明“进行中，数字会变”；不能保存快照 | 同左 |
| 运行在回收站中 | — | 灰显、不参与计算，恢复后回来；物理删除后从集合移除并记入修改记录 |

### 失败原因分组

剔除按“原因类别”勾选。类别由原始异常类型与平台的停止原因归类，比现有错因细，例如把“环境失败”拆成“镜像构建 / 启动失败”（外部）和“运行中内存超限”（可能是 Agent 造成的）。分组规则带版本，写在代码里并记入快照。初版：

| 预设剔除：外部或平台原因 | 预设保留（算 0 分）：可能与被测对象有关 |
| --- | --- |
| 模型接口暂时故障：限流、断连、过载、响应停滞 | 运行中内存超限 |
| 认证失败、模型不存在、用量额度耗尽 | 验证器没有产出分数（超时、奖励缺失或无法解析） |
| 镜像构建、环境启动、健康检查、Harness 安装超时 | 附件安装失败或超时 |
| 准备缓存恢复失败、附件原件缺失或传输失败 | 模型接口的其他永久错误（多为请求参数或 Harness 配置） |
| 执行框架不支持 | 未归类的错误 |
| 未开始、取消、中断、服务重启、Runner 无响应、运行总时限停止 | |

### 统计口径

- 任务内先对有效试次求均值，运行的均分是参与任务的宏平均（与 06 第 5 节一致）；“有效试次”= 已评分 + 计为 0 分的失败。
- 差值只在数据集内容与计分规则相同、且只看共同任务时给出。只给样本量、均值、样本标准差、通过率与差值；不断言“显著”“提升”，不做置信区间、显著性检验和 pass@k。
- 不假设不同运行的第 1 次重复相互配对。

### 放弃的做法

- 每次比较前先声明“关注因素”：临时比较由平台自动检测维度即可；需要约束的是长期维护、多人加入的集合，所以声明放在集合规格上，只声明一次。
- 规格可以直接修改：会让集合里出现不合规的运行，旧快照与集合的含义也对不上；改为复制成新集合。
- 规格之外再另存一份方案：两份配置会各自漂移；集合规格本身就能用来提交。
- 合成重跑结果（原 D-008 的合成分析）：用户重跑常常是为了多一组样本，不应被当成“补齐”合并；失败不公平的问题改由按原因剔除解决。
- 按任务名跨数据集版本对齐：同名不等于同内容。以后若做显式映射，须保存映射版本与任务内容差异。
- 集合只许创建者改、他人复制：团队小且互相信任，同一个排行榜被复制成多份更糟；加错运行由规格挡住。

## 影响

- 数据结构（追加迁移）：集合（名称、用途、规格：场景、可变维度、固定维度内容值与请求引用；摆法与剔除设置）、集合成员（`collection_id + run_id` 唯一，可带列名）、集合修改记录；快照（运行清单与各运行的名称和比较视图副本、规格、设置、摆法、分组规则版本、聚合版本、计算出的整张表、创建时的证据可用性、创建者与 PAT）；快照结论（作者、PAT、正文、修改时间）。快照不依赖运行行仍然存在。
- 计算：维度划分、规格核对与比较放在 `src/maestro/domain/` 新模块，复用 `scoring.py` 的统计函数；“保留的失败算 0 分”对应汇总里现有的 `count_as_failure` 口径（单运行汇总里它仍恒为 0）。
- 提交（[04](../design/04-plans-submission.md)）：运行请求与批次成员可带 `collection_id`；受理事务内核对规格并加入集合，不符合时整个请求（或整批）不受理。从集合预填的固定字段与方案一样记录来源层。
- 接口：比较（只计算、不保存，参数为运行列表、剔除类别、摆法、任务范围）、集合（列表、创建、复制并修改规格、改名与说明、改摆法与剔除设置、增删运行、修改记录、删除）、快照（创建、读取、列表、删除）、快照结论（写、改）；SDK 增加对应资源与方法，登记到 `test_sdk.py`。
- 权限（[09](../design/09-identity-security.md) 第 3 节加行）：所有身份可读；成员网页会话与 experiment PAT 可创建与复制集合、增删任何集合的运行、改摆法、创建快照、写结论；read PAT 只读；结论只有作者能改；集合与快照由创建者或管理员删除，进回收站（U-08）。
- 网页（[11](../design/11-web-ui.md)）：侧边栏“实验”下增加“集合”；比较页（`/compare?runs=…` 与 `/collections/:id`，排行榜 / 矩阵 / 逐任务）；新建集合（场景、基准、规格确认）；运行列表多选“比较”、批次页“比较这一批”、比较页“建成集合”、运行详情“加入集合”、集合页与新建运行页“从集合新建运行”；快照页。
- 系统说明：[01](../design/01-domain-model.md) 增加集合、规格与快照对象，[04](../design/04-plans-submission.md) 增加从集合提交，[06](../design/06-results-scoring.md) 增加维度、比较口径与失败分组，[13](../design/13-testing-plan.md) 的 E2E-OUT-02、E2E-OUT-03 用下面的场景替换；决策记录中 D-008 的合成分析注明由 U-46 取代。

## 验收

- 临时比较：两个数据集内容不同的运行不对齐、不给差值，并说明原因；计分规则不同时同样处理；其他维度不同时警告。
- 集合：不能把数据集或计分规则设为可变；固定维度任一字段不同的运行加入被拒并列出字段；Oracle 运行加入被拒；规格不能修改，复制并修改规格时符合的运行带过去、不符合的列出原因。
- 从集合新建运行：固定字段已填且不能改；受理后运行在集合里；规格不符时整个请求或整批不受理、不扣额度。
- 摆法：正好两个可变维度时矩阵可用；同一配置多次运行在矩阵同一格并列显示、不平均。
- 一边缺任务时，“共同任务”与“全部任务”都显示实际覆盖与被排除的范围。
- 剔除外部原因后：被剔除的试次不计入；保留的失败按 0 分计入；某任务在某运行没有有效试次时整行从所有运行去掉并计数；运行详情页的汇总不变。
- 重跑运行是独立的一行，没有任何合并。
- 新运行加入集合后，旧快照的运行清单、规格、摆法与数值不变；运行进回收站、物理删除或产物过期后，快照仍显示原数值并标明证据不可用，不显示下载入口。
- read PAT 不能改集合、建快照或写结论；成员能往别人创建的集合加运行，修改记录写明是谁。
- 网页与 SDK 对同一组运行、同一设置得到相同的比较结果。

场景（替换 13 中的 E2E-OUT-02、E2E-OUT-03）：

- **E2E-OUT-02 比较、剔除与集合**。步骤：用假执行器提交一批四个运行（2 模型 × 2 Harness），其中一个构造限流失败和内存超限失败，另一个少一个任务 → 打开比较 → 剔除外部原因 → 建成集合 → 从集合新建一个运行 → 尝试加入一个资源不同的运行 → 再提交一个重跑并加入。预期：条件核对列出模型与 Harness 不同；限流失败被剔除、内存超限计为 0 分；默认只比共同任务；规格预填为“模型 × Harness”，矩阵可用；从集合提交的运行自动加入；资源不同的运行被拒并列出字段；重跑在矩阵同一格并列显示；集合修改记录有加入者。
