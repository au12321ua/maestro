# N-13 试次粒度调度（撤销 D-020）

状态：想法 · 优先级：三 · 2026-10-27 · 相关：[05](../design/05-scheduling-execution.md)、[06](../design/06-results-scoring.md) 第 4 节、[15](../design/15-stack-harbor.md) 第 4、6 节、[14](../design/14-decisions.md) U-05、D-020、V-12

## 问题

现在按运行调度（D-020）：一个运行由一个 Runner 进程执行一个 Harbor Job，`n_attempts` 为每任务计划试次数，`n_concurrent_trials` 为运行并发，重试在 Job 内进行。由此带来的限制：

- 同一运行内每个任务的试次数必须相同。
- 只能取消整个运行；不能取消或补跑单个试次。
- 容量在领取时按“并发 × 单试次资源”整体预留，等待缓存恢复和运行末尾并发下降时仍全额占用。
- 一个运行占住自己的宽度，多个运行的试次不能穿插执行。
- Job 内重试对平台不透明：重试由 Harbor 发起，平台只能事后从结果目录和事件识别每次尝试（V-12）。

## 方案

工作单元改为试次：每个执行尝试对应一个 Runner 进程和一个 Harbor 试次，平台决定是否创建下一次尝试。

- **领取**：按受理顺序扫描试次级工作项（`work_items` 已按试次建立），跳过已停止或到期的运行；检查准入、已知内容阻塞与本机能力；冷缓存交给准备协调器，等待恢复期间不预占执行 CPU / 内存与提供商名额，实际恢复构建只预留一份独立容量。
- **预留**：缓存就绪后，在一个短事务中原子预留一个试次槽位、该试次的容器 CPU / 内存和一个提供商名额，再启动容器；放不下则显示等待原因，不能超额启动。准备与执行共用主机 CPU / 内存总账。每运行的活动试次数受其并发限制，可选每成员 / PAT 限制。
- **Runner 输入**：一个任务、一个 Agent，`n_attempts=1`、`n_concurrent_trials=1`、`retry.max_retries=0`；可重试的失败由平台按错误策略和退避创建新的 ExecutionAttempt。
- **租约**：每次尝试有 attempt_id 与独立租约；心跳过期先进入 suspect，按本机进程与容器标签确认旧执行已停止后才允许重试，无法确认则隔离资源并阻塞重试，避免同一试次同时调用模型。
- **取消**：可取消单个试次或整个运行；等待共享缓存的试次只解除自身等待。
- **标签**：执行资源带实例 / 运行 / 试次 / 尝试标签，按尝试清理。

表结构保持不变，只改领取规则、容量预留和 Runner 输入（D-020“以后的切换”）。

将来 Worker 拆为独立进程或多机时，可把进程内接口换成以下 RPC，业务语义不变（不在本提案范围内实现）：register（worker_id、location_id、容量、能力）、claim（返回工作项、快照、attempt_id、lease_token）、heartbeat（更新存活与取消指令）、report_progress（序号单调可去重）、append_log（有界批次、脱敏后保存）、commit_result（有效租约，同摘要幂等）、complete_cleanup（独立于评分终态）、upload_artifact（经存储接口校验归属与摘要）。

### 收益

- 每个任务可以有不同的试次数。
- 单试次取消与补跑。
- 按试次精确预留容量，等待缓存时不占执行容量。
- 多个运行的试次可以穿插执行。
- 重试成为平台可见、独立记录的执行尝试，不再依赖从 Job 结果中识别。

### 代价

- 每个试次都要启动一次 Runner（独立 uv 环境中导入 Harbor），启动开销按试次累计。
- 绕过 Job、直接调用单试次接口依赖 Harbor 内部 API，升级 Harbor 时更容易破坏。
- 网络收紧（出口控制 sidecar）与 Docker 清理从每运行一次变为每试次一次。
- 取消、重启对账与容量相关的验收（[13](../design/13-testing-plan.md) 中的竞争、满载、取消、重启场景）要按试次重做。

## 影响

- 05：第 2、3、6、7、8 节改为试次领取、按试次预留、尝试租约与 suspect、单试次取消；EXE-02、EXE-06 的“未满足”可去掉。
- 06 第 4 节：Job 内重试改为平台创建新尝试。
- 15 第 4、6 节：一个执行尝试对应一个 Runner 进程和一个 Harbor 试次。
- 14：撤销 D-020，记录新的技术决定。
- 数据结构不变；Runner 协议的请求与事件需要按尝试调整（attempt_id、租约）。
- 网页与 SDK：提交时允许按任务设定试次数，增加单试次取消与补跑入口。

## 验收

- 同时竞争的试次只领取一次；满载时不超槽位、CPU、内存和提供商上限。
- 等待缓存恢复的试次不占执行容量。
- 取消单个试次不影响同运行其他试次；取消与评分并发保持单一终态。
- 可重试失败形成新的 ExecutionAttempt，次数与退避符合错误策略；Runner 不再自行重试。
- 杀死服务后不继续原试次执行，孤儿资源按尝试标签清理。

## 待定问题

先做技术验证，再决定是否实施：

- 测量单个 Runner 启动（导入 Harbor、建立环境）的开销，判断按试次启动是否可接受。
- 在锁定的 Harbor 版本上确认可用的单试次接口及其稳定性。
- 测量 10 个试次并发（10 个 Runner 进程与对应容器、sidecar）的资源占用。
