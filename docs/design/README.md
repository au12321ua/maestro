# 重写目标设计

本目录是重写（`feature/rewrite`，2026-10-24 已替换 `dev`）的目标设计，来源是原 Maestro 设计稿（v0.3，2026-10-22）。基线代码已全部移除，`src/maestro` 是重写的实现；本目录的设计不等于都已实现，差异见各模块的“现状”说明与 [实施记录](records/README.md)。

## 文档地位

1. **[需求整理与审查](requirements-review.md)（审计稿）是需求基线。** 原稿完整保留，不随实现改写；其中“已定”的条目是约束，【建议】和【审查】是待落地的意见。
2. **00～15 模块文档是审计稿的延伸设计。** 它们把审计稿展开成表结构、协议和流程，属于“设计建议”或“本轮设计基线”，不是用户逐条确认的约束。与审计稿冲突时以审计稿为准。
3. **实践优先。** 实现中发现更好的做法或设计本身有问题时，按实践调整：在 [14 决策记录](14-decisions.md) 记录日期、原设计、新做法和依据，再同步修改相关模块文档。不要求代码迁就文档。
4. 用户当前明确指令优先于以上全部；用户决定写入 14 的“用户决定”一节并注明日期。

文档状态标记沿用原稿约定：

- **原稿已定**：审计稿明确写为“已定”“结论”或明确要求的内容。
- **设计建议**：模块文档为落地补充的规则和数值，尚未经用户确认。
- **本轮设计基线**：已采用的技术路线，仍需接入验证。
- **待验证**：依赖 Harbor、Hub 或部署环境的实际行为。
- **P0 / P1 / P2**：首个可用闭环 / 首期后续完善 / 后续扩展。阶段与决策状态是两个维度。

## 当前阶段的调整

以下是 2026-10-22 用户对本设计的调整，细节见 [14 决策记录](14-decisions.md) 第 0 节：

- **调度单位暂不改。** 一个运行仍对应一个 Harbor Job，由 Harbor 在 Job 内展开试次。试次和执行尝试仍作为持久记录保存，供状态、评分和比较使用；按试次领取的 WorkItem 推迟。00、01、02、05、06、15 中按试次领取、等待或重试的描述在本阶段按 D-020 解释：领取与租约在运行上，恢复的等待者是运行，重试在 Job 内进行。
- **重写过程可以破坏可运行性**，只要求最终完整替换现有实现。
- 原设计中准备缓存的共享恢复、租约与等待者、PAT 两种范围等机制保留，不做简化。
- **项目改名为 Maestro**，新代码使用 `maestro` 包。
- **P0 入口收敛为网页与 SDK**，CLI 与 MCP 为后续范围。
- **删除**：除主密钥外都可删除，回收站两步（07 第 8 节）。**证据从宽**，不设审计门。
- **部署**采用 12 的系统级布局。
- **Harbor 跟进最新稳定版，错误策略由平台自定**，执行器适配器负责与 Harbor 对接，保持执行器可替换。
- **容器挂载**只允许本试次输出目录这一例外；**准备成果另存原件**，回收本机缓存后载入原件恢复。

## 版本记录

- **并入重写分支（2026-10-22）**：设计稿移入仓库 `docs/design/`，文件名改为英文，审计稿正文未改。增加文档地位、实践优先规则和当前阶段调整；13 第 2 节改为在本仓库内的重写路线。
- **v0.3**：版本准入与本机缓存分开：已准入任务的缓存被清理后，成员和 experiment PAT 仍可直接提交，由系统按原摘要恢复；相同缓存的并发等待共享恢复，取消互不误伤。首次准备失败、暂态恢复失败与确切内容不可得分别处理；只有确认原内容无法满足时才阻止新提交和原配置重跑。附件 bootstrap 属于运行内准备，P0 每试次在容器独立安装，无宿主目录挂载。
- **v0.2**：补充 FastAPI / React / SQLite 等具体选型；将 Harbor 放入独立环境、通过 Runner 子进程接入；计分与错误分类以锁定 Harbor 策略为基线；网络优先复用 Harbor 的分阶段白名单；采用 Hub digest 固定内容；增加 Oracle 真实链路测试与 Hosted Harbor 定位比较。
