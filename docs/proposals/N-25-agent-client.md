# N-25 Agent 客户端

状态：实施中（U-60） · 优先级：待定 · 2026-10-30 · 相关：[03](../design/03-configuration-attachments.md) 第 6、7 节、[08](../design/08-collections-comparison.md)、[10](../design/10-api-sdk-cli.md)、[14](../design/14-decisions.md) U-11、U-46、U-50、U-51、U-59、U-60

## 问题

Maestro 的使用者多半是成员交代任务的 Agent。对 Agent 来说，产品不只是 API：怎样装上 SDK 与 skill、工作时手边有什么上下文、遇到常见任务有没有现成的做法，都决定它能不能用好平台。这部分现在几乎是空的：

- skill 放在本仓库的 `skills/`，要使用者自己复制；SDK 只能从仓库目录安装，两者的版本要人去对齐。
- 没有推荐的工作环境：服务地址、令牌放在哪、真实模型运行的授权与预算、团队的命名习惯，每次都要在对话里重新交代。
- 最主要的用法之一是让 Agent 改进一个附件（skill 与工具），用实验判断改动是否有效。怎样从已有材料做出合格的附件、源文件放哪、怎样判断“更好”、会话中断后怎样接着做，都要 Agent 每次自己摸索。

此前在独立项目 rsi-workbench 中试过另做一个工作台：它靠不上平台，只好自己记账、维护一份附件规则、规定尝试与记录的格式。N-06（附件快照与父快照）和 N-11（集合、分析快照与结论）完成后，这些事实已经由平台保存，Agent 一侧真正缺的只是很少几样东西。rsi-workbench 不再单独开发。

## 原则（U-59）

- **平台保存别人要依赖的事实**：测的是哪份内容（按内容寻址的快照）、跑出了什么（运行与试次）、凭哪组数字下结论（分析快照与结论）。这些规则严格。
- **Agent 的工作过程是自由的**：笔记、推理、证据摘录、改进方法因任务而异，也会随经验改变。skill 只给建议，SDK 不规定格式、不做校验。
- 判断一条规则该不该有，问它保护的是谁要依赖的哪个事实。客户端代码只针对 Agent 已知的失误，例如发布的内容与测试的不一致、重复提交、丢了运行 ID。

## 方案

### Agent 的工作区

推荐（不强制）每个使用者或每项长期目标有一个本地工作区，做法类似部署者的 `maestro-site`：私人的、可以是 git 仓库，内容自由。

```
<工作区>/
  AGENTS.md          给 Agent 的上下文（模板见下）
  .agents/skills/    由 SDK 安装的 skill（.claude/skills/ 同）
  notes/             自由记录：假设、证据摘录、做过什么、什么无效
  <附件名>/          附件仓库（独立的 git 仓库，工作区的 .gitignore 忽略它）
```

SDK 提供 `maestro_sdk.workspace.init(目录)` 生成这个骨架：写入 `AGENTS.md` 模板、`notes/` 与 `.gitignore`，并安装 skill；已有的文件不覆盖，重复调用只补缺的部分并更新 skill。`AGENTS.md` 模板写 Agent 每次都需要、又不该在对话里重复的东西：服务地址、令牌文件的位置（不写令牌本身）、真实模型运行的授权范围与预算、团队的命名习惯（`client_request_id`、附件标签）、指向已安装的 skill，由 Agent 与使用者一起填写。

### 附件仓库：git 只管附件

一个附件一个 git 仓库，仓库根目录就是附件根目录，受跟踪的文件就是附件的全部内容。修改历史、分支、回退由 git 负责；实验记录与经验不进这个仓库，放在工作区。

SDK 增加**从 git 提交发布**：读取指定提交的文件树（不读工作目录），可执行位取自 git 的文件模式，拒绝符号链接与子模块，本地算出的摘要在发布后与快照的 `content_digest` 核对；工作目录有未提交的修改时给出提醒。这解决按目录发布时的两个失误：把未跟踪的杂物（缓存、虚拟环境）一起发布，以及可执行位因文件系统不同而变化。按目录发布照旧保留，适合快速试验。平台不记录提交（U-51），快照与提交的对应由 Agent 自己记在笔记里或用作标签。

### skill 与 SDK 一起分发

- `skills/` 下的 skill 打进 SDK wheel，`maestro_sdk.skills.install(目录)` 复制到 `.agents/skills/` 与 `.claude/skills/`，并写下 SDK 版本。升级 SDK 后重新安装即同步。
- 发布流程在发 Gitea Release 的同时用 `uv publish` 把 SDK 推到 Gitea 的 Python 包仓库（正式版本与 `dev` 预发布），工作区可以按版本安装，不依赖本仓库目录。
- 新增 `maestro-package` skill；`maestro-sdk` skill 的安装说明改为从包仓库安装。

### `maestro-package` skill 的内容

都是建议，不是规则：

- **做出合格的附件**：只放 skill 与工具，数据、答案、凭据、大文件不进；`manifest.json` 的写法；`bootstrap.sh` 不给定死的模板，由 Agent 按附件与所用 Harness 的需要自己写（例如先在冒烟运行里查清该 Harness 从哪里读 skill）；从本地目录、线上仓库或平台上已有的附件开始。用一个任务做一次模型运行（Oracle 运行不能带附件，[03](../design/03-configuration-attachments.md) 第 7 节），从产物确认 `bootstrap.sh` 成功、Agent 读到了 skill。
- **改进与判断**：以当前版本为基准建“附件 A/B”集合；用 `task_selection` 固定任务（平台暂不核对固定任务列表，U-60）、在集合里固定重复次数；从出发点的快照发布，`parent` 指向它。下结论时用“不剔除 + 全部任务”的比较设置，出现未评分或执行失败就补跑或说明证据不足，不当作 0 分、也不只看共同任务；逐题对照并阅读轨迹。
- **版本**：认定更好的快照打 `vN` 标签，并为集合建分析快照，结论里写清依据。团队其他人不看笔记，从平台就能知道当前最好的是哪个快照、为什么。
- **记录**：产物会按保留期回收（[07](../design/07-artifacts-export.md) 第 2 节），判断所依据的关键事件建议摘录进笔记；需要完整证据时用导出。
- **恢复**：会话中断后从平台推出进度，不依赖笔记的格式：附件的快照、父快照与标签，集合里的运行，以及按可推断的 `client_request_id`（如 `<附件名>-<出发点>-<序号>`）用 `runs.find` 找回的运行。

### 放弃的做法

- **独立的工作台项目**：只对接 Maestro，却要另行维护附件规则、SDK 与 skill 的版本，并自己保存运行状态。
- **包仓库同时装附件、评测定义与结构化记录，由 SDK 生成和校验**（本提案的上一稿）：把改进方法固化成格式与校验，限制了最该灵活的部分；校验的多半是 Agent 自己读的笔记，或者重复平台已有的保证。
- **客户端另算“严格口径”决定晋升**：晋升依据与分析快照里的数字会是两套。改用服务端比较的设置，再由 Agent 检查有无未评分与失败。
- **在服务端新增“改进线 / 轮次”对象与页面**：版本线由父快照表达，比较由集合承担，结论由分析快照承担。
- **客户端账本**：为了不受产物回收影响在本机保存全部产物。改为摘录关键证据，需要时导出。

## 影响

- [10](../design/10-api-sdk-cli.md)：从 git 提交发布、skill 安装、工作区骨架；SDK 的分发与安装方式。
- [03](../design/03-configuration-attachments.md) 第 6 节：说明从 git 提交发布的可执行位与拒绝项。
- [12](../design/12-operations.md) 第 1 节与[开发流程](../guides/development-workflow.md)：发布流程增加 SDK 推送到 Gitea 包仓库。
- `skills/`：新增 `maestro-package`，修改 `maestro-sdk` 的安装说明。
- 数据库、服务端接口与网页不变。

## 验收

- 从 git 提交发布：平台的 `content_digest` 等于本地摘要；未跟踪、被忽略与未提交的内容不进入；可执行位来自文件模式；符号链接与子模块被拒绝；工作目录有修改时提醒。
- `skills.install` 写入两个目录并记下 SDK 版本；升级后重装替换旧文件；skill 的内容仍由现有测试核对。
- `workspace.init` 在空目录生成骨架；再次调用不覆盖已有的 `AGENTS.md` 与笔记，只更新 skill。
- 能从 Gitea 包仓库按版本安装 SDK，包括 `dev` 预发布。
- 一次端到端演练（真实模型，按当次授权与预算）：从一个本地 skill 目录建附件仓库，冒烟运行确认安装与读取；做一轮改进并建分析快照；删掉笔记后只凭平台恢复进度。

## 已定问题（U-60）

1. **SDK 包仓库**不拆成单独的提案，由另一个分支并行实现后合并。推送账号与令牌、使用者的只读凭据、`dev` 预发布的版本号形式在实现时确定，写进开发流程与部署指南。
2. **`bootstrap.sh`** 不给定死的模板，由 Agent 按需要编写；skill 只说明它的执行方式与限制（[03](../design/03-configuration-attachments.md) 第 7 节）。
3. **工作区**：附件仓库放在工作区里、被工作区忽略；SDK 提供生成骨架的函数。
4. **固定任务列表**暂时不做，靠 `task_selection` 与 Agent 检查。
5. **证据保留**：以后是否让被分析快照引用的运行产物不随保留期回收，另行讨论。
6. **已有材料**：rsi-workbench 中 scan-to-cad 的 v0–v2 包仓库，把 `journal/` 移到工作区笔记、仓库只留附件即可，不在本仓库实施。
