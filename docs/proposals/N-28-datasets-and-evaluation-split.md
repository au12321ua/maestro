# N-28 数据集拓展与执行 / 评测拆分

状态：设计中 · 优先级：待定 · 2026-11-03 · 相关：[01](../design/01-domain-model.md)、[02](../design/02-datasets-preparation.md)、[06](../design/06-results-scoring.md)、[07](../design/07-artifacts-export.md)、[15](../design/15-stack-harbor.md)、U-31、U-68

本提案只确定方向与概念，留有大量待定问题，后续讨论后再拆成实施提案。

## 问题

1. **数据源只有 Harbor Hub。** 团队想测的 benchmark（目前主要是 CAD 领域）多数发布在 Hugging Face 上，提供方没有做 Harbor 适配，格式也各不相同。
2. **高质量评测集常常隐藏答案。** 例如 [CADGenBench](https://huggingface.co/datasets/HuggingAI4Engineering/cadgenbench-data)：81 道题（49 道根据工程图生成，32 道编辑 STEP）公开，每题需要输出一个 `output.step`；参考实体放在私有仓库，作者明确规定只能在服务器端评分；评测代码（CAD Score：先过有效性门槛，再取形状、接口、拓扑三项加权）在 GitHub 公开；提交方式是把产物和 `meta.json` 打成 zip，上传到排行榜 Space。（2026-11-03 查看数据集卡片所见，未核对代码。）
3. **执行和评测绑在一起。** 现在每次运行都是 agent 先执行、Harbor verifier 随后判分。因此没法只生成结果、交给外部评测，也没法只对已有或外部的结果评分；判分逻辑一改，也只能重跑 agent。

## 方案（方向）

### 1. 数据集拆成三个概念（名字待定）

| 概念 | 内容 | CADGenBench 中的对应 |
| --- | --- | --- |
| 题目集 | 输入与题面；可执行环境（Harbor task） | `cadgenbench-data`（公开） |
| 参考集 | 标准答案或参考产物 | `cadgenbench-data-gt`（私有，拿不到） |
| 评测方案 | 评测镜像、指标和判分代码 | `huggingface/cadgenbench`（公开） |

三者都有就是“完整数据集”，等同于现在的 Harbor task 加 verifier。评测方案和参考集可以分别组合：同一套评测方案，既可以配外部的私有答案，也可以配团队自建的答案。只有题目集时，不需要答案的那部分评测（例如 STEP 有效性门槛）仍然可以在本地运行。

### 2. 数据源与转换配方

- 增加通用的 Hugging Face 数据源，用数据集仓库的 commit SHA 固定版本，凭据用团队的 HF token。沿用现有的 `DatasetSource` 边界与五类错误。
- 原始数据要经过**转换配方**才能变成 Harbor task。配方基本是每个 benchmark 一份，分两档：声明式模板，覆盖问答、选择、精确匹配等简单题型；代码配方，参考 Harbor adapter，在 Runner 子进程中运行。
- 版本身份由“上游 revision + 配方 digest”组成。改配方或者上游更新，都会形成新版本，与现有的固定内容规则一致。

### 3. 执行与评测拆开

```
执行（Harbor）：题目集 + 实验配置           ──> 产物包
评测（自研）  ：产物包 + 评测方案 (+ 参考集) ──> 分数
完整运行      = 执行 → 评测 自动串联
```

- **只执行**：生成产物包，可以按 benchmark 的格式导出提交文件（例如 CADGenBench 的 zip 加 `meta.json`）。结果记为缺评分，或者只有本地的部分评分。
- **只评测**：导入符合格式的产物包，用评测方案判分并输出结果。也可以对平台里已有运行的产物重新评分。
- 执行继续使用 Harbor。评测器由平台自己实现：把评测镜像、产物和参考集放进容器运行，读取分数文件。这样能复用现有的镜像准备、容器执行和产物存储，也不依赖 Harbor 是否支持单独运行 verifier。不打算自己实现替代 Harbor 的 agent 运行器。

### 放弃的做法

- 在服务进程内加载第三方 Python 插件：插件代码能接触主密钥和数据库，接口也会和内部实现绑死。
- 只开放“上传 Harbor task 包”：HF 上的数据大多不是可执行任务，转换工作仍要有人做，而且没有地方记录版本身份。
- 把执行和评测都改为自研：Harbor 已经处理好 agent 接入、隔离、超时和日志，重写成本高。

## 影响（初步）

- 领域模型（01）：增加题目集、参考集、评测方案、产物包、评测记录，并定义它们与运行和试次的关系。
- 02：增加 HF 数据源、转换配方、配方版本和许可证记录。
- 06：分数要标明来源（本地完整评测 / 本地部分评测 / 外部回填）；评测要能独立重做，可能出现一次运行对应多份评测的情况。
- 07：产物包的格式、导出转换器和导入校验。
- 08：比较页要区分来源，导入的产物没有 agent 配置。
- 网页与 SDK：增加导入导出、只评测的入口；权限沿用“导入数据集只限管理员”（U-20）是否合适，待定。

## 待定问题

**概念与命名**

1. 三个概念的正式名称，以及它们在网页上怎么呈现。
2. 现有 Harbor 数据集（题目里自带 verifier）怎样映射到新模型：直接算作“完整数据集”，还是拆出一个内置的评测方案？
3. 参考集是独立的对象，并且有自己的版本吗？如何防止成员在日志或产物里看到答案（现在的原则是证据从宽，U-10）？

**数据源与配方**

4. 配方由谁编写，放在哪里：网页编辑、Git 仓库，还是内置常用 benchmark？
5. 声明式模板要覆盖哪些题型和内置判分器？要不要支持 LLM judge（判分本身会产生模型费用）？
6. 多个 config 和 split 怎样选择；许可证与 gated 数据集怎样记录。
7. 是否同时做 N-19 里提到的本地目录与 Git 数据源。

**执行与评测**

8. 产物包的格式：按 `task_key` 组织，manifest 记录数据集版本、内容 digest 和来源。是否按 benchmark 提供导出和导入转换器？
9. 评测方案的契约：评测镜像的输入目录、输出的分数文件格式、资源与时限。它和现有 Harbor verifier 的奖励格式是什么关系？
10. 完整运行是继续用 Harbor 自带的 verifier，还是统一改为“执行后再交给自研评测器”？
11. 同一运行重新评测后，比较页默认显示哪一份分数？
12. 外部回填的分数（例如在排行榜上拿到的成绩）是否录入平台？如果录入，怎样标注它不可复现？
13. 导入产物包的信任与限制：大小、格式校验、谁有权导入。

**范围与顺序**

14. 拆分成几个实施提案、按什么顺序：先做 HF 数据源和配方，还是先验证“自研评测器加产物包”？
15. CADGenBench 的评测代码能否直接容器化，在本地跑有效性门槛和三项指标（需要实测）。
16. 团队还想测哪些 CAD benchmark？要逐个确认数据形态、答案是否公开、评测代码是否公开。
