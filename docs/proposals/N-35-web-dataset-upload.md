# N-35 补齐 N-33 的网页一侧：数据集上传与版本管理、工作流记录读写、交付物导出

状态：实施中（U-93；第 1、2、4 步已完成，剩第 3 步版本管理）· 优先级：二 · 2026-11-06 · 相关：[N-33](N-33-held-out-benchmarks-workflows.md) 第 3.3、4、5 节、[01](../design/01-domain-model.md)、[02](../design/02-datasets-preparation.md)、[03](../design/03-configuration-attachments.md) 第 6 节、[07](../design/07-artifacts-export.md)、[08](../design/08-collections-comparison.md)、[09](../design/09-identity-security.md)、[11](../design/11-web-ui.md)、U-20、U-69、U-74、U-89

N-33 的数据模型与后端已经实现，但网页一侧漏了几块，版本管理也没有考虑。本提案补上，不改 N-33 的核心模型：上传内容的检查与准入、工作流记录的数据结构都不变。标“已定”的是用户已确认范围的部分（决定记录见 U-92），界面细节由实现时按现有页面风格定；标“用户已答”的是用户在对话中的回答。

## 1. 问题

### 1.1 上传没有网页入口

N-33 第三部分让管理员能把转换好的 Harbor task 目录上传成数据集，但只做了 API 与 SDK。网页的数据集页只会展示上传来的版本（来源、版本页的工作流记录、“没有上游检查”的提示），添加数据集的来源列表里还主动去掉了 `upload`，[11](../design/11-web-ui.md) 也明确写着“网页没有上传表单”。

这是实现时的选择：N-33 与 U-89 都没有说网页不做。结果是管理员要传一个数据集，必须装 SDK、建管理员 PAT、写脚本，和“管理员日常配置也在网页完成”不一致；同样是“选本地文件夹”，附件早就能在网页上发布了。

### 1.2 上传版本没有版本管理

Hub 的版本由上游管理，有标签，上游差异也能预览。上传的数据集没有上游，版本一多就会出现附件当初遇到的问题。已核对的现状：

- **版本没有名字，也没有来源。** 上传版本的名称就是内容摘要（`sha256:…`），没有标签，也没有“从哪个版本改来”。
- **只能比 Hub 预览，不能比两个本地版本。** 现有的任务差异（新增、删除、内容变化）只在添加 Hub 版本前，把上游版本和某个本地版本比。上传版本没有上游，两个本地版本之间也不能比。
- **新版本里，读取记录和留出标记接不上。** 新版本的任务是新的记录：留出标记存的是任务记录的 id（`held_out_task_ids_json`），读取记录也落在任务记录上（`task_reads` 以 `task_id` 为键）。上传一个只改了一道题的新版本后，其余没改的题在新版本里“从没被读过”，集合换到新版本时也不能沿用留出标记（[08](../design/08-collections-comparison.md) 第 5 节规定复制时拒绝并要求重新提供）。N-33 第 4 节只考虑了同一个版本之内的情形。这会让“改进者没碰过留出题”的记录出现一个洞：修一道开发题、上传新版本，之前的读取就不算了。
- **好消息：准备的缓存跨版本共用。** 缓存键是准备规格加位置，不含版本，内容相同的任务共用缓存（[02](../design/02-datasets-preparation.md) 第 6 节）。改一道题，只会重新准备那一道。新版本的任务准入仍照常重新进行。
- **版本文件取不回来。** 平台其实留着上传时的原始文件（`dataset_files`，和附件共用同一个内容仓库），但网页和 API 都不能下载，附件的整包下载与“基于此发布”没有对应物，使用者必须自己保存转换器的输出。

### 1.3 数据集的来源边界没有写明

数据集按（来源，命名空间，名称）识别（`datasets` 表的 `source_kind`，`live_dataset` 按这三项查找）。Hub 导入拒绝 `upload` 来源，上传只会进入 `upload` 数据集，所以实际上两种来源不会混着加版本，但这是实现碰巧形成的，没有写进系统说明，也有漏洞：同一个命名空间和名称，可以同时有一个 Hub 数据集和一个上传数据集，列表里分不清；文档没有说“哪种数据集怎么得到新版本”。

### 1.4 工作流记录，网页能看不能写

- **读：** 运行详情、集合页、附件历史（按附件名）和数据集版本页都有记录区，空的时候显示“暂无记录。通过 API 或 SDK 编写记录。”用户在已更新到最新版的 `localhost:8420` 上没有看到记录区。核对结果：该实例提供的前端包里四处都挂了记录区；用 Playwright 加载这个包、把 `/api/v1/**` 全部拦截成固定数据（不碰实例的数据与账户），记录区渲染正常，但在运行页排在页面最底部，距顶 951 px，而一屏只有 720 px。其余三处也排在后面：集合页在快照卡片之后，数据集在长长的任务表之下，附件要先展开某个附件名。所以不是没更新，而是位置太靠后、没有入口，加上空状态把用户指去了网页做不到的事。没有用真实运行的数据验证，也没有排除浏览器缓存了旧页面。网页冒烟测试和 N-33 的可用性检查原先都没有覆盖记录区。
- **写：** 没有。[11](../design/11-web-ui.md) 写的是“网页只读，写入使用 API / SDK”，这是实现时的选择；N-33 第 3.3 节写的是“像评论区一样”。创建、编辑（只有作者，带 `expected_revision` 检查）、删除（走回收站）的接口都已有，要写记录只能用 SDK。
- 这也是“来源说明”在网页里无处可写的原因（见 5.1 第 2 条）。

### 1.5 交付物的网页导出只有半套

网页已经有四层打包下载（运行、任务、试次、尝试）和批量导出，交付物在其中保持原字节，不丢也不改。缺的是整理：包里交付物夹在日志中间，路径是 `…/artifacts/logs/artifacts/…`；SDK 的 `runs.download_deliverables` 才会只取各试次最终结果所属尝试的交付物，按 `<任务>/<重复序号>/<文件>` 摆好，供使用者拼提交 zip。网页没有对应的入口。

## 2. 方案

### 2.1 上传（已定）

放在 `/datasets`，只有管理员看得到，服务端的权限校验不变（管理员会话或带 `datasets` 权限的管理员 PAT）。两个入口：页面顶部的“上传数据集”（新数据集，填命名空间与名称），和上传来源数据集卡片上的“上传新版本”（名称固定，见 2.2）。

1. 选一个文件夹，里面是各任务子目录；可选填标签，以及“基于哪个版本”（见 2.3，默认该数据集最新的版本）。
2. 预览：任务数、文件数、总大小，较所基于版本新增、删除、内容变化的任务数，以及会被标为可执行的文件（见 2.4）。校验与 SDK 一致：必须是任务子目录、任务目录不能为空、不含链接；超过部署配置的文件数或大小上限时提示改用 SDK。
3. 提交：在浏览器里算每个文件的 SHA-256，询问缺失的内容，只上传缺失的，再提交文件清单。
4. 之后是已有的导入操作：用数据集页现成的操作进度组件显示导入与首次准备；任何一道题无效就不登记版本，逐题显示错误。

**共用一套程序，只换检查，不复制。** 后端已经是这样：内容仓库 `AttachmentStore`（`src/maestro/execution/attachments.py`）按内容摘要存文件，`check` 用一个开关切换路径规则和是否要求 `manifest.json`；上传内容的接口 `/attachment-contents/…` 两边共用，请求体的文件项也是同一种结构。实施时把前端也收成同一段：选文件夹、算摘要、问缺失、上传缺失内容、整包下载、两版文件差异，附件页与数据集页一起用；后端的“把一组文件写成 zip”“两组文件求差异”也从附件服务里抽出来共用。

两边真正不同的只有两处：**检查**（附件校验 `manifest.json`，数据集由 Runner 用 Harbor 逐题解析）和**登记**（附件同步登记快照，数据集是异步的导入操作，全部通过才有版本）。所以共用的部分到“内容已就位”为止，之后各走各的。

**附件页的上传入口顺带改进（用户观察，不属于已定范围）。** 用户在检查时觉得附件页现在的上传按钮比较简陋，认为问题不大，但最好前端也改进一下。共用组件做出来后，附件页一起换用，界面随之改进；具体怎么改，实现时先给草图让用户看，再动手。

### 2.2 来源边界（已定，用户提出要写明）

用户原话：“边界要更明确一些，只有只有个人上传的模型支持之后再上传新的版本，harbor hub上的只支持获取harbor hub上的更新？”（“模型”按“数据集”理解。）下面把它写成规则：

1. **来源在创建数据集时定下，之后不变，也不混用。** Hub 数据集的版本只来自 Hub，上传数据集的版本只来自上传。
2. **Hub 数据集**：新版本只通过现有流程得到，即卡片上的“检查上游更新”，或按标签、修订添加；不接受上传，也没有“基于”与自定义标签（标签就是上游标签）。
3. **上传数据集**：新版本只通过上传得到（网页或 SDK）；没有上游检查，也不用 Hub 凭据。“基于”只能选同一个数据集里的版本；想做一个变体，就用新名称上传成新数据集。
4. **同名不同来源，新增时拒绝。** 在没有物理删除的数据集里（回收站里的也算），同一个（命名空间，名称）只属于一个来源。往 Hub 数据集的名称上传，或把 Hub 数据集添加成已有上传数据集的名称，都返回明确的错误并说明名称已属于另一种来源；已经存在的同名数据集不处理。
5. **网页按来源只给对应的操作**：Hub 卡片只有“检查上游更新”，上传卡片只有“上传新版本”；页面顶部是“添加数据集（检索 Hub）”和“上传数据集”两个入口。

### 2.3 版本管理（已定）

规则尽量与附件一致，使用者不用学第二套。

- **标签与基于哪个版本，规则与附件一致。** 标签可选，格式同附件（字母、数字与 `._+-`，最长 64），在同一数据集内、没有物理删除的版本中不重复，打上之后不再改动。“基于”可选，只能选同一个上传数据集里没有删除的版本，只表示来源，不影响内容与身份。内容摘要仍是版本身份：同一内容重复上传返回已有的版本，这次带来的标签与“基于”不生效，网页和 SDK 都会说明；同一内容的版本在回收站里时报错并提示恢复。SDK 的 `upload` 加这两个可选参数。数据集版本表加这两列，迁移只追加。
- **版本列表按“基于”关系排列。** 上传来源的数据集，版本像附件那样连成线或树，每个版本标出时间、上传者，以及较所基于版本新增、删除、内容变化的任务数。没有“基于”的版本各自一条线。Hub 数据集的版本列表照旧。
- **任意两个本地版本可以比较。** 复用现有的任务差异组件，数据取自两个版本的任务列表（任务键与内容摘要都已存）。比较结果只显示，不保存。
- **同一道题跨版本的身份（用户已答：可以）。** 在同一个数据集里，任务键相同且内容摘要相同，就算同一道题：
  - 读取汇总按这个身份合并显示：版本一里被读过的题，在版本二中内容不变就仍显示被读过；内容变了的按新题算，并注明“内容已变”。合并范围是同一个数据集里没有物理删除的所有版本（回收站里的也算）。留出视图里“全团队包含该题的受理运行数”按同一身份合并，否则读取与运行两个数字口径不一致。查询时合并，不改写已存的读取记录，时间口径（集合建立后是否被读过）不变。上传任务的内容摘要由平台按路径、内容与可执行位计算（`files_digest`），所以只改了权限位的任务也算“内容已变”，与 2.4 一致。
  - 复制集合并换到新版本时，留出标记按这个身份自动沿用不变的题；内容变了或已删除的题不沿用，列出来让使用者重选。这取代 08 中“沿用的任务身份不属于新版本则整体拒绝”的规则。
  - 这对 Hub 数据集同样成立，不是上传专用。
- **整体下载上传版本。** 与附件的整包下载一样，一个版本一个 zip，路径与可执行位按上传时保存的样子还原，可以直接当作“基于此版本上传”的起点：下载、本地修改、重新上传。只对上传来源的版本提供，因为平台只持有它们的原始文件；Hub 版本的内容在上游，不提供（接口说明原因）。不提供单个文件或单个任务的下载，也不在线编辑。大小受上传时的文件数与大小上限约束。
- **下载记入留出集的读取。** 整个版本的 zip 里有每道题的题面、参考解与验证代码，所以下载时对版本里的每道题记一次读取，沿用现有机制：记谁、网页还是哪个 PAT、什么时间，汇总行永久保留，不拦截。读取类别新增一类 `task_files`，与现有的 `instruction`（题面）、`trial_artifacts`（试次产物）并列。这正是 N-33 第 4.2 节所列“参考解与验证代码”的读取；现有接口里没有返回它们的（读取记录只接在题面与试次产物上），所以此前没有这个类别。只有整体下载这一个入口，接入点只有一处，改动范围小。沿用现有打包下载的顺序：先提交读取汇总再发送，记录失败就不发送。
  - **要知道的后果**：下载整个版本的人，会显示读过这个版本里的所有题，包括之后被某个集合标为留出的题；配合上面的跨版本合并，之后上传的新版本里不变的题也仍显示被这个人读过。这是“记录而非拦截”的本意；不想留下记录，就用本地保存的转换器输出，不下载。

### 2.4 可执行位（已核对，已定 A）

浏览器拿不到文件权限，而版本摘要包含每个文件的可执行位。同一个目录，SDK 读到真实权限，网页只能猜，两边可能得到两个不同的版本。

**核对结果**（Runner 锁定的 Harbor 0.24.0，读 `runner/.venv` 中的源码与本仓库代码）：

- verifier 与 oracle 都在执行前自己对 `.sh` 脚本 `chmod +x`（`harbor.utils.scripts.needs_chmod`），所以 `tests/` 与 `solution/` 里的 `.sh` 不依赖上传时的权限位。
- 但 `environment/` 是 Docker 的构建上下文（`context_dir` 就是该目录）。`COPY` 保留文件权限，Dockerfile 里被复制后直接执行、又没有 `chmod` 的脚本或二进制，会依赖权限位。没有逐个任务核对真实 benchmark 里有没有这种写法，只能说“可能有”。
- 平台还原上传文件时，按保存的可执行位设为 755 或 644（`src/maestro/execution/uploads.py`），Hub 任务的材料摘要同样含权限位（`src/maestro/execution/materials.py`）。权限位是内容身份的一部分，会影响构建结果。

**结论：** 不选“摘要里去掉可执行位、统一把脚本设为可执行”（原 B）：分不清哪些文件需要，会改变构建结果。建议 **A，并补足**：网页按下面的顺序确定权限位——

1. 与所基于版本中同路径、同内容的文件，沿用它的权限位（附件页也是这样做的）。配合整体下载保留的权限位，“下载、改、重新上传”不会让权限位漂移。
2. 新文件按开头判断：`#!` 或 ELF 头视为可执行。
3. 预览里列出被标为可执行的文件，逐个可改。

仍有残留：同一个目录经网页与 SDK 上传，若猜的权限与磁盘上的真实权限不同，会得到两个版本。SDK 读真实权限，仍是权威做法。

另外两点已核对：

- 上传任务的内容摘要由平台计算，含权限位，所以只差权限位的任务，在版本比较与跨版本合并里算“内容已变”。Harbor 自己的任务摘要（`Packager.compute_content_hash`，只含路径与文件内容）不含权限位，但上传版本不用它。
- 浏览器算摘要时把整个文件读进内存（`frontend/src/lib/sha256.ts`），而上传上限与附件相同：1 GiB、10000 个文件。所以网页对单个过大的文件提示改用 SDK，阈值实施时按浏览器实测来定。

### 2.5 工作流记录的网页读写（已定）

保持现有记录区的位置与显示，补三件事，让它真的“像评论区一样”：

1. **添加记录。** 记录区里的“添加记录”：类型（文本，已有类型作候选）、标题、正文（JSON 对象，提交前检查格式）。引用与证据摘录不在网页里填，它们要核对被引用的对象，仍用 SDK。对象是数据集版本时，预填来源说明的正文模板（`upstream_repo`、`revision`、`converter_version`，键名只是约定，平台不解释），这样来源说明可以在版本页写，不必放进上传表单。
2. **编辑与删除。** 只有作者本人能改（接口规则，带 `expected_revision`，冲突时提示刷新）；删除走现有的回收站两步。
3. **修改历史。** 展开查看各修订（接口 `/records/{id}/history` 已有）。

**入口与位置**（解决“看不到”）：

- 运行详情：标签页里新增“记录（n）”，与执行、结果汇总、配置快照、产物并列，标签上显示条数。
- 集合页、数据集版本页：页面顶部的操作行加“记录（n）”按钮，点击滚动到记录区；记录区的位置不变。
- 附件：展开某个附件名后，记录区在文件树之下（现状），标题带条数。
- 空状态改成“还没有记录”加“添加记录”按钮，不再把人指去 API 或 SDK。

写入需要实验权限；网页会话是成员或管理员，都能写，只读 PAT 只在 SDK 一侧受限。冒烟测试补上记录区的读、写、编辑、删除，并在全新实例上走一遍；如果发现现在的显示有问题，一并修。

### 2.6 交付物导出（用户已答：加）

给现有的打包下载增加一种“只要交付物”：范围和布局与 SDK 的 `download_deliverables` 相同，在运行详情的产物页与现有 zip 按钮并列。

- 实现方式：给现有的 `GET /runs/{id}/artifacts/archive` 加一个参数，不新建 Operation，沿用它的规则：运行未结束返回 409；超过大小上限在传输前返回 413；按包内实际包含的试次文件记录任务读取汇总；过期或被删的文件列入包内 manifest。
- 提交用的 zip、`meta.json` 等基准格式仍由使用者自己拼，平台不定义（N-33 第 5.3 节）。
- SDK 的 `download_deliverables` 保留：它会逐份校验索引摘要，脚本化使用更合适。

### 2.7 不做

- **不在网页或服务器上转换 benchmark**，这是 U-89 的范围，使用者在本地转换。
- **不做单个文件或单个任务的下载，不做平台内在线编辑，Hub 版本不提供下载。** 只做上传版本的整体下载（2.3）；“基于”只记录来源，改的内容仍来自使用者本地。
- **不在上传表单里填来源说明**（用户已答）；改用 2.5 的通用记录。
- 记录区不按类型做专门展示（U-74），也不做跨对象的“全部记录”总览页，只在对象页面里看；网页里不填引用与摘录。
- 不动 Hub 数据集的添加流程；不给版本加启用 / 停用开关（已有撤销准入与回收站）；不做“默认版本”指针。

## 4. 验收

- 管理员在网页选一个含两道题的目录并上传：看到导入与首次准备的进度；故意放一道坏题时按题名报错，且不登记版本。
- 同一个目录在网页上重复上传得到同一个版本；与 SDK 上传同一目录的结果按 2.4 验证。
- 非管理员看不到入口，直接调用接口仍被拒绝。
- 上传版本二，标签为新名字、基于版本一，只改其中一道题：版本列表显示两者的关系与“1 个内容变化”；两个版本可以在网页里比较；除改动的那道题外，其余题沿用缓存，不重新准备。
- 来源边界：往 Hub 数据集的名称上传被拒绝，Hub 卡片上没有上传入口；上传卡片上没有“检查上游更新”；同名跨来源的新增在两个方向上都被拒绝并说明原因。
- 版本一里读过的留出题，在版本二中内容不变仍显示被读过，内容变了的显示为新题；把集合复制并换到版本二，不变的留出标记自动沿用，变了的列出来让使用者重选。
- 下载上传版本的整体 zip：路径与可执行位和上传时一致，解开后用 SDK 重新上传得到同一个版本；版本里每道题都出现在读取汇总里，类别为 `task_files`；Hub 版本没有下载入口，接口说明原因。
- 工作流记录：运行页有“记录”标签页，集合页与数据集版本页的顶部有跳转按钮，打开页面不用滚动就能找到入口；成员能添加记录并在页面上看到；作者能编辑（冲突时提示刷新）和删除；非作者没有编辑、删除按钮；数据集版本页有来源说明的模板；空状态不再把人指去 API 或 SDK。
- 运行结束后下载“只要交付物”，文件字节和布局与 SDK 下载的一致；运行未结束时按钮不可用并说明原因。

## 6. 实施顺序（建议）

分四个短期分支，各自从 `dev` 建，各自带系统说明的改写与测试；数据库迁移只追加。

| 顺序 | 内容 | 规模与风险 |
| --- | --- | --- |
| 1 | 工作流记录的网页读写与入口位置（2.5），以及记录区的冒烟测试 | 小。只动前端，接口已有；先解决“看不到、写不了” |
| 2 | 数据集的网页上传与来源边界（2.1、2.2、2.4）；附件与数据集共用选文件夹和内容上传的前端，后端抽出共用的 zip 与差异 | 中。附件页要改成用共用部分，需回归附件发布 |
| 3 | 版本管理（2.3）：标签与基于、版本关系与两版比较、跨版本合并读取与沿用留出标记、整体下载与 `task_files` | 大。有迁移，并改 08 中留出集的规则；依赖第 2 步的上传表单 |
| 4 | “只要交付物”打包（2.6） | 小。给现有 archive 加参数，可插在任何位置 |

验证：每步在全新 state 上走网页冒烟；第 3 步另做一次“上传两个版本、改一道题”的真实 Docker 走查。第 1 步顺带验证 `localhost:8420` 上看不到记录区的现象是否消失。
