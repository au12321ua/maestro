本提案是总设计稿，覆盖四件事：数据集拓展、执行与评测拆分、留出集与任务清单、工作流适配。它取代 N-28、N-31、N-32（U-85）；三份原稿已归档，只作出处，之后的讨论和修改都在本提案上进行。

标了 U 编号的是用户已定的取舍，标“建议”的是 Agent 的方案，其余列在第 14 节待定。N-31 原来的确认（U-77）随原稿一起失效，它的取舍（U-73～U-76）照常有效。整体确认后按第 12 节分阶段实施。

## 1. 问题

现在一个运行就是“一个数据集版本上的执行，加上当场判分”：任务范围由运行自带，分数由 Harbor verifier 在执行时给出，每个试次只有一条结果，集合固定一个数据集。下面四个需求都要把这个整体拆开，而且共用同一套数据模型（U-80），所以放在一起设计。

### 1.1 数据源只有 Harbor Hub

团队想测的 benchmark（目前主要是 CAD 领域）多数发布在 Hugging Face 上，提供方没有做 Harbor 适配，格式也各不相同。

### 1.2 高质量评测集常常隐藏答案

以 [CADGenBench](https://huggingface.co/datasets/HuggingAI4Engineering/cadgenbench-data) 为例：

- 公开 81 道题，其中 49 道根据工程图生成、32 道编辑 STEP，每题要求输出一个 `output.step`。
- 参考实体放在私有仓库里，作者明确规定只在服务器端评分。
- 评测代码（CAD Score：先过有效性门槛，再对形状、接口、拓扑三项加权）在 GitHub 公开。
- 提交方式是把产物和 `meta.json` 打成 zip，上传到排行榜 Space。

以上是 2026-11-03 读数据集卡片所见，评测代码尚未核对。

### 1.3 执行和评测绑在一起

agent 执行完由 Harbor verifier 立即判分，带来三个限制：

- 不能只生成结果、交给外部评测；
- 不能复用已经跑出的昂贵结果，只换评测方案或参考答案重新评分（用户 2026-11-03：“实验本身很贵，如果一个旗舰模型跑了一个结果，我很想复用”）；
- 判分逻辑一改，就只能重跑 agent。

### 1.4 留出集与“任务天然可见”矛盾

改进附件、提示词或任何会根据结果迭代的东西（RSI），都应该留一组验证集：改进者只在开发集上看细节，最后在没看过的题上确认效果。平台现在的设计与此矛盾：

1. **所有任务天然可见。** 团队成员互相信任，数据集、题面和产物对所有成员开放，PAT 也能读，包括参考解与验证代码（U-10、U-31，[09](../design/09-identity-security.md) 第 6 节）。
2. **实际测试会暴露验证集内容。** 在验证集上跑一次，被测 Agent 就会在容器里读到题面，trace、日志和产物都会把它带出来，而这些证据按“证据从宽”对团队开放。
3. **现在只能靠自觉。** 首轮 Mesh2CAD 实验（2026-11-04）手写了一份清单，固定 smoke 的两道开发题，并从另一个数据集按固定规则选出两道留出题。题目是否泄露，完全取决于 Agent 是否遵守 skill 和工作区说明。

### 1.5 工作流靠 Agent 现场发挥

现在只有一种“适配”：`maestro-package` skill 加通用 SDK，其余由 Agent 现场发挥。2026-11-04 用 Codex 跑了首轮 Mesh2CAD 附件改进（服务与 SDK `0.4.1.dev0`，一个基线加两个候选，共 18 个试次），暴露出两类问题：

- **流程没讲到的判断，Agent 会漏掉。** 它没有读 SDK 已经提供的题面；改进类别也没分清，执行可靠性改进（C1）和交付诊断（C2）都容易被说成建模能力提高；数事件时按正则给多行命令分类，结果漏计。
- **工作流需要的机械活，Agent 每次从头写。** 它写了一个 300 行的脚本和 32 KB 的本地状态文件，自己管快照、运行、幂等键和授权的试次数；证据定位写在正文里；报告逐份手写。这些对下一轮、下一个附件都一样。

Agent 换一个工作流（比如比较模型、调 Harness 参数、复现论文结果），还会遇到同样的问题。所以要解决的是“为一种工作流配齐 skill 和 SDK”这件事本身。首轮实验发现的平台问题记在 `Gitea#18`，不在本提案（U-75）。

## 2. 整体框架

```
供题      数据集版本 ──题目──┐        参考答案 · 评测方案
                            │              │
选题      任务清单（跨数据集、不可改）       │
                            │              │
执行      运行 → 试次 → 产物（按输出契约）   │
                            │              │
评测      评测记录 = 试次产物 × 评测身份 → 分数
                            │
组织比较  集合 = 任务清单 + 固定配置 + 用哪种评测
          比较按评测身份分组；分析快照；当前最优指针
过程记录  题目上的读取汇总 · 挂在对象上的工作流记录 · 审计
```

| 层 | 回答的问题 | 对象 | 现状 |
| --- | --- | --- | --- |
| 供题 | 题是什么、可以怎么判 | 数据集版本（题目内容）、参考答案、评测方案、输出契约 | 只有 Hub 数据集，判分方式在题目内部 |
| 选题 | 挑哪些题 | 任务清单 | 没有；运行自带任务范围 |
| 执行 | Agent 交出了什么 | 运行、试次、执行尝试、产物 | 已有 |
| 评测 | 怎么判、得几分 | 评测任务、评测记录 | 与执行合在一起，每个试次一条结果 |
| 组织比较 | 怎么比 | 集合、比较、分析快照、当前最优指针 | 集合固定一个数据集 |
| 过程记录 | 过程中发生了什么 | 读取汇总、工作流记录、审计 | 只有写操作的审计 |

## 3. 统一数据模型

### 3.1 基本规则（方向已定，U-82）

1. **数据集版本只固定题目内容。** 题目内容是 Agent 能看到的东西：题面、输入、可执行环境和输出契约。参考答案与评测方案是另外带版本的对象，声明自己适用于哪个数据集版本。
   - 原因：如果三者打包成一个版本，换一份答案就是新版本，按 U-53 任务清单和集合都要复制，旧运行也对不上新版本，与“只换答案重新评分”直接冲突。
   - Harbor 数据集的 verifier 和参考解本来就在题目内容里，它的内置评测随数据集版本走，不受影响。
2. **分数挂在评测记录上。** 一个试次可以有多条评测记录，每条带一个评测身份。Harbor verifier 的结果是一条“内置评测”记录，在执行中产生。
   - 原因：复用旗舰模型的产物换一种评测重新打分，新分数应该落在原来的运行上，比较表里还是那一行，而不是多出一个“只评测的运行”。
3. **评测身份 = 评测方案版本 + 参考答案版本 + 计分规则。** 内置评测的身份是“数据集版本 + 计分规则”，正好是现在比较页的分组依据，所以现状是这个模型的特例。
4. **运行只表示执行。** 外部评测是另一种排队的工作（评测任务），共用队列、容量和取消，产出的评测记录挂回原来的试次。导入的结果包是一个来源为“导入”的运行：有产物，没有执行过程，不能重跑。
   - 这修改了 N-28 原稿“一个运行由执行、评测阶段组成”的写法。实现上可以借用运行的调度机制，但评测结果写回原试次，比较页不把评测任务当成新的一行。
5. **任务清单只管选题，集合把三件事放在一起。** 任务清单的成员是“数据集版本 + 题目 + `spec_digest`”，在规则 1 之下这就是题目内容的身份，不受评测拆分影响。集合 = 任务清单（哪些题）+ 固定的配置维度（测的是什么）+ 每个分组用哪种评测（怎么判）；比较按评测身份分组。

### 3.2 对象

现有对象（[01](../design/01-domain-model.md) 第 1 节）照旧，下表只列新增或含义改变的。名称是暂定的。

| 对象 | 身份与职责 | 可变性 | 阶段 |
| --- | --- | --- | --- |
| 数据集版本 DatasetVersion | 改为只固定题目内容；Hub 来源照旧，上传来源以内容 digest 为身份，上游与转换器只作来源说明 | 内容固定 | 1（含义）、4（上传） |
| 输出契约 OutputContract | 题目内容的一部分：Agent 必须交出哪些文件、放在哪里 | 随题目内容固定 | 4 |
| 参考答案 ReferenceSet | 按任务组织的标准答案或参考产物，声明适用的数据集版本 | 版本固定 | 4 |
| 评测方案 EvaluationScheme | 评测镜像、入口、指标与分数格式、资源与时限 | 版本固定 | 4 |
| 评测身份 EvaluationIdentity | 评测方案版本 + 参考答案版本 + 计分规则；内置评测为数据集版本 + 计分规则 | 派生，不单独建表（建议） | 1 |

## 4. 供题：数据集的组成部分

### 4.1 只接受已转换好的数据（建议，待确认）

每个 Hugging Face benchmark 基本都要单独写转换器，所以平台不读取原始数据，也不在服务器上运行转换代码。转换由使用者在自己那边完成（可以参考 Harbor adapter），平台只按格式契约接收结果。

- **版本身份**：上传内容的 digest。上游仓库、revision 和转换器版本作为来源说明保存，只用于展示，平台不核实。
- **上传通道**：倾向复用附件的内容寻址快照与增量上传（[03](../design/03-configuration-attachments.md) 第 6 节），由 SDK 发起。
- **代价**：平台无法“检查上游更新”，转换能否复现由使用者负责。

U-68 原来写的是“增加 Hugging Face 等数据源与转换配方”，这一条与它不同，需要用户确认（第 14 节问题 1）。

### 4.2 三个组成部分

| 组成部分 | 内容 | CADGenBench 中的对应 |
| --- | --- | --- |
| 题目内容 | 输入、题面、可执行环境（Harbor task）和输出契约 | `cadgenbench-data`（公开） |
| 参考答案 | 按任务组织的标准答案或参考产物 | `cadgenbench-data-gt`（私有，拿不到） |
| 评测方案 | 评测镜像、入口、指标与分数格式 | `huggingface/cadgenbench`（公开） |

这里拆的是一道题由哪几部分组成，不是挑选题目；挑题是任务清单（第 6 节，U-78）。名称避免叫“某某集”，以免与任务清单混淆。

评测方案和参考答案可以自由组合。只有题目内容时，不需要答案的评测（例如 STEP 有效性门槛）仍可以运行。

### 4.3 输出契约

Harbor 的 verifier 判分的对象是环境，不是产物：它在 agent 结束后、容器还在时进入同一环境检查状态。平台保存的产物只是 Runner 按上限复制的工作目录和日志，不保存容器的最终状态。

- 因此只有声明了输出契约、并且平台确实保存了这些文件的任务，才能做只执行、只评测和复用。
- Terminal-Bench 这类检查整个环境状态的任务做不到事后评测，只有内置评测。
- 要确认产物上限、脱敏等现有规则不会损坏这些输出，例如 STEP 文件会不会被当成文本脱敏。

### 4.4 参考答案的可见性

参考答案放进平台后就不再保密：现有设计中 read PAT 能看到参考答案和验证代码（[09](../design/09-identity-security.md) 第 6 节），证据也从宽开放（U-10）。拆开执行和评测之后，执行容器可以完全不挂载参考答案，被测 Agent 读不到答案。答案对成员和 PAT 是否可见，由用户决定（第 14 节问题 5）。

### 4.5 上传与准入的权限

N-29 已经完成（U-69）：带 `datasets` 权限的 PAT 可以检索、导入和准入。上传数据集、上传参考答案与评测方案、发起评测、导入结果包要新增的权限，扩展权限组时与用户确认（N-29 的结论）。

## 5. 执行与评测

### 5.1 三种用法

三种用法共用同一套队列、容量、取消、记录、产物、比较和 SDK，只是组合不同：

```
完整运行：运行（Harbor 执行，内置评测随之产生）→ 按集合或请求排外部评测
只执行  ：运行 → 导出结果包（可按 benchmark 格式导出提交文件）
只评测  ：已有运行的试次 / 导入的结果包 → 评测任务 → 评测记录挂回试次
```

“只评测”预计会经常用，所以不做成独立的小工具。现有 Harbor 数据集的 verifier 继续在 Harbor 里运行，记为内置评测，这次不迁移。

### 5.2 评测器

评测器只做一件事：在容器里运行评测镜像，挂载产物与参考答案，读取分数文件。它复用现有的镜像准备、容器执行和产物存储。平台不自己实现替代 Harbor 的 agent 运行器。

### 5.3 评测任务的排队与资源

评测本身也有成本：CADGenBench 另有 `cadgenbench-eval-gpu` Space，评测可能需要 GPU，平台目前不支持 GPU 任务；LLM judge 也会消耗模型额度。评测任务纳入容量管理、资源限制和取消，与运行共用调度。

### 5.4 输出的长期保留

原始产物 7 天后过期。复用旗舰模型的结果重新评分，要求输出契约规定的文件长期保留，不随日志一起过期。这些文件可能很大（STEP、网格），需要单独的保留规则与存储上限（第 14 节问题 13）。

### 5.5 结果状态与错误策略

现在的错误表（[06](../design/06-results-scoring.md) 第 3 节）里，`verifier_failed` 和“继续验证”一列属于评测，不属于执行。拆开后：

- 执行的结果只回答“Agent 有没有正常交出东西”，评测记录回答“这份东西得几分”。“有效零分 / 缺评分 / 执行失败”的区分按每种评测分别成立。
- 运行的结果完整度、`RunCounts` 与比较页的失败分组都要说明是针对哪种评测；分组规则的版本号随之提升。

### 5.6 导入的结果与外部分数

导入的外部结果有产物，但没有可复现的执行，可以参与评测和比较，但不能重跑，要明确标识。结果包的格式、大小、校验与权限待定（第 14 节问题 4、9）；排行榜成绩等外部回填的分数是否录入待定（问题 8）。

## 6. 选题：任务清单

### 6.1 思路：记下发生了什么，不拦截（U-78）

留出集首先是实验有效性问题，不是保密问题。机器学习里的测试集通常不加密，靠的是约定，以及事后能说清楚调参时没有碰过。所以平台不必把题藏起来，只需要能回答：这些题被谁、在什么时候读过，在上面跑过几次。

平台只记事实；“读过算不算用掉了”“用掉以后怎么办”在写结论时判断（U-59），由工作流的 skill 建议怎么报告（第 9 节），由写结论的人或 Agent 说明。平台不为此另设拦截或审计门，“证据从宽”不变。

### 6.2 任务清单（U-78、U-79）

任务清单（英文 `task set`，接口与代码用 `task_set`）是一份题目清单，可以来自不同的数据集，是和集合同一级的管理单元：

- **不是执行对象**：不复制题目内容，自己不执行，不改变运行、比较和计分的语义。
- **成员固定到版本**：每个成员是“数据集版本 + 题目”，并带上 `spec_digest`。同名的题在不同版本里内容可能不同，所以不按名字对应。
- **建好后不能改**：要改就复制成一个新的（复制时可增删成员），与集合规格的做法相同（U-47）。这样“这批题被读过几次”始终指向同一个对象。
- **用途**：开发集、留出集、日常 smoke 清单都是任务清单；首轮实验手写的那份清单，就是一个跨两个数据集的任务清单。

在任务清单上提交时，按数据集版本拆成多个运行，用现有的批量提交一次受理。

### 6.3 成员不可用（U-79）

成员所在的数据集版本进回收站或被物理删除、题目不再可提交时，成员显示为缺失（missing）并注明原因，清单整体变为不可用：不能再提交，已有运行、比较和读取记录照常可看。从回收站恢复后清单恢复可用。

### 6.4 网页（U-79）

任务清单有自己的列表与详情页：从数据集选题或从已有运行的任务新建、复制、在上面提交、查看成员状态与读取汇总。集合页显示它绑定的清单。

## 7. 集合与比较

### 7.1 集合绑定一个固定的任务清单（U-79、U-80）

集合建立时绑定一个任务清单，补上 U-60 暂缓的“集合的固定任务列表”。清单可以跨数据集：集合不再固定“数据集”这一维度，题目由清单决定（部分取代 U-47 中“数据集不能设为可变”）。

- 从集合提交一种配置时，按清单涉及的数据集版本拆成一组运行，一次受理；加入集合的运行，任务必须与清单在该数据集版本上的成员一致。
- 现有集合按基准运行的任务生成任务清单。现场数据不保留（U-84），这一条只在测试数据和迁移逻辑中用到；是否还需要，实施时再看。

清单不可改带来的情况，都按“复制”处理，与 U-53“换版本相当于换了实验对象”一致：

| 情况 | 处理 |
| --- | --- |
| 数据集出了新版本 | 题目内容可能变了，复制成新清单、新集合；旧集合与它的结果不变 |
| 想加题提高样本量 | 复制成新清单与新集合；带过去的旧运行在新题上没有结果，比较照常标为不完整 |
| 成员不可用 | 原清单与集合不能再提交，复制时去掉缺失的成员 |
| 建错了 | 复制或删除，删除进回收站 |

### 7.2 按评测身份分组（U-80、U-82）

比较按“计分分组”分开列出，分组键就是评测身份。同一组的运行照常对齐、给差值；不同组之间只并排，不合并、不给差值。[08](../design/08-collections-comparison.md) 第 2 节的规则不变，只是同一个集合里可以有多组，分组键从“数据集内容 + 计分规则”换成评测身份（内置评测下两者相同）。

### 7.3 集合怎么定“用哪种评测”

一道题可以有多种评测时，集合要定每个分组用哪一种。待定：它算规格（换评测就复制集合，运行带过去，还没有该评测记录的显示“未评测”），还是设置（像剔除分组一样可以随时切换）。Agent 倾向规格：计分规则现在就是“永远固定”的维度，评测身份是它的扩展，这样“同一个集合里的分数一定可比”的保证还在；代价是复用旧产物重新评分时会经常复制集合（第 14 节问题 6）。

不建集合的临时比较里，同一运行有多份评测时默认显示哪一份，也待定（问题 7）。

## 8. 读取记录

同一道题可以从任务清单、数据集页面、运行详情或 SDK 读到。只在任务清单的入口记录，绕一下就漏了，所以读取记录落在题目上，清单只负责汇总成员的记录（U-78）。

- **只有能看到任务内容的读取才算**（U-79）：题面、参考答案、评测代码（Harbor 任务里的验证代码与参考解）、跑这道题的试次产物（含 trace 与日志，它们会带出题面），包括打包下载与导出。汇总分数、逐题分数、失败原因码、列表中的题名都不算；“在上面跑过几次”从运行记录查，不另记。参考答案独立后（第 4 节），“读参考答案”是单独的一类。
- 记录谁、通过网页会话还是哪个 PAT、读了哪一类、什么时间。清单汇总成员的记录，比如“某个时间点之后，谁读过哪些成员”。
- 现有的审计只记写操作（[09](../design/09-identity-security.md) 第 4 节），读取记录是新增的；每个返回上述内容的接口都要接入。
- **只存汇总行**（U-80）：每个“题目 × 读取者（账户，及 PAT 或网页会话）× 读取类别”一行，记首次时间、最后时间与次数，永久保留。行数上限是题目数 × 成员数 × 类别数，不设保留期与配置项；“冻结后有没有人读过”看最后时间。
- 评测日志可能带出参考答案的内容，查看评测日志归哪一类，待定（第 14 节问题 10）。

## 9. 工作流适配

### 9.1 三层分工（U-73～U-75）

判断一条规则放在哪一层，沿用 U-59 的标准：它保护的是谁要依赖的哪个事实。

| 层 | 放什么 | 例子 |
| --- | --- | --- |
| 平台 | 团队或用户要依赖、要复查的事实 | 快照、运行、比较、分析快照；工作流记录与当前最优指针 |
| SDK 工作流模块 | 这种工作流的机械活，只输出事实、不下结论 | 整理题面、准备候选、收集证据并建索引、生成报告 |
| skill | 流程和判断方法，只给建议、不强制格式 | 先读题、给假设分类、预先写下证据标准、何时停下 |

“这个事件是不是解释器错误”“这个候选值不值得保留”属于判断，不进 SDK。

### 9.2 工作流包（U-76）

一个工作流由三部分组成，放在 SDK 内部、随 SDK 同版本发布，数量多了再考虑拆成单独安装的扩展：

- skill：放在 `skills/<名称>/`，由 `maestro_sdk.skills.install` 安装（已有机制）。
- SDK 模块：放在 `maestro_sdk.workflows.<名称>`，只组合公开 API，不访问服务器文件系统。
- 记录类型：这个工作流在平台上留下的记录长什么样（第 9.3 节）。

`maestro_sdk.workspace.init(dir, workflow="<名称>")` 在工作区模板里写入这个工作流的说明；不指定工作流时保持现状。

### 9.3 工作流记录（U-73、U-76）

平台不为每种工作流建专门的表，而是提供一种通用记录，像评论一样挂在集合、运行或附件（可以指定到某个快照）上：

- 类型（如 `attachment-candidate`）、标题、正文（JSON）、作者、时间与修改历史，规则与集合的修改记录相同（U-46）。
- 除了挂靠的对象，正文还可以引用其他运行、附件快照、试次、产物与任务清单。平台只核对被引用的对象存在且可读，不解释正文的含义。
- 正文可以带证据摘录（几行日志或 trace）。原始产物 7 天后过期，摘录随记录保留，这样决定的理由以后还能读懂。摘录有大小上限，入库前按基本规则脱敏（U-10）。
- 网页在集合、运行与附件的详情页列出挂在上面的记录、显示原文，像评论区一样。不按类型做专门的展示（U-74）。

正文的结构由工作流包定义，SDK 模块负责读写，平台不做 schema 校验。记录能否也挂在任务清单上（例如声明“这个清单从某时起冻结为留出集”），待定（第 14 节问题 11）。

### 9.4 适配新工作流的路径

用户描述想要的工作流后：

1. Agent 在工作区里先写这个工作流的 skill 和脚本，只用公开的 SDK；需要留在平台上的，就用通用记录。
2. 跑过一两次、证明可以复用后，把稳定、通用的部分整理成工作流包，合入 SDK 发布。
3. 只有通用记录也装不下、确实需要平台理解的事实，才另开提案改平台。

这样一轮实验里的临时做法不会直接固化成平台功能。

### 9.5 例子：附件改进

**skill。** 修订 `maestro-package`：

1. 改进前先读开发集的题面和允许读的检查说明，写清输入、交付物、评分目标与未知项。
2. 先给假设分类，比如安装可用、执行可靠性、有效交付率、建模质量，每类用对应的指标判断，不从可靠性改进推出质量结论（U-74）。
3. 提交前写下什么证据支持什么决定：机制确实发生、暂留使用、已证明整体改善。父版本缺评分时只报告机制证据，不为补齐自动追加试次。
4. 平台已有的事实不在笔记里重抄；附件 A/B 集合已经保证固定维度，不必再比对配置。
5. 统计 trace 中的事件时，先用事件索引定位，逐条核对后再计数，并记下计数方法。
6. 开发集与留出集各用一个任务清单；报告附上留出集的读取汇总与评估次数，由写结论的人判断留出集是否仍然有效。

**SDK 模块 `maestro_sdk.workflows.attachments`（名称待定）。**

- **题面整理**：把指定任务的题面和公开元数据写成本地文件。
- **准备候选**：从集合和父候选出发解析新快照，列出计划试次、与父候选的附件差异，以及安装验收能否复用的提示。提示依据是 `bootstrap.sh` 未变、父候选在同一 Harness 上安装成功；复不复用由 Agent 决定。
- **收集证据**：按范围增量下载并校验摘要、生成清单；为 trace 生成事件索引（行号、命令、退出码、输出位置）。只建索引，不分类。
- **生成报告**：从比较结果和候选记录生成 JSON 与 Markdown，包括覆盖率、按原因的失败、逐题结果、计分口径、已知与未知的费用，以及留出集的读取汇总。
- **候选记录的读写**：见下。

**记录类型 `attachment-candidate`。** 一个候选是集合中的一份附件快照，正文包括：

- 父候选，假设（要改什么、为什么、怎样算无效），以及改进类别（自由文本）。
- 来源证据：引用加摘录。
- 关联的运行，按附件自动查出，不手填。
- 决定：未决 / 保留 / 放弃 / 证据不足，加理由与证据等级；每次决定都保留。
- 改进 Agent 自报的信息（可选）：模型与费用。

**当前最优**是集合上的一个指针（U-76），与基线类似：指向集合中的一个候选，改指向时记作者、时间与理由，进集合的修改记录。之后的比较可以默认以当前最优为起点。它取代 U-61 的做法（在分析快照的结论里写明谁最优）；分析快照照旧用于冻结比较。

### 9.6 其余已定的取舍（U-76）

- 改进 Agent 自己的 trace 暂不存进平台。
- 暂不找第二个工作流来检验通用性，等有了实际需求再说。
- 不单独做验证：实现完成后，用户重新跑一遍附件改进实验，从实际使用中发现问题。

## 10. 放弃或暂不采用的做法

| 做法 | 原因 |
| --- | --- |
| 平台内置 Hugging Face 数据源，在服务器上运行转换配方 | 转换器因 benchmark 而异；在服务器上运行第三方代码有安全问题，配方的版本也难以管理（待用户确认，见第 4.1 节） |
| 在服务进程内加载第三方 Python 插件 | 插件能接触主密钥和数据库，接口也会和内部实现绑死 |
| 执行和评测分成两个独立的产品模式 | 比较、SDK、权限都要做两份，成员会困惑结果在哪里 |
| 把执行也改为自研 | Harbor 已经处理好 agent 接入、隔离、超时和日志 |
| 数据集版本把题目、答案、评测方案打包固定 | 换答案就要复制清单与集合，旧运行对不上（第 3.1 节） |
| 评测作为运行的一个阶段，“只评测”产生新运行 | 复用旧产物时比较表里多出一行，与原运行的关系要另外解释（第 3.1 节） |
| 留出集只靠约定（现状） | 无法核对 |
| 按 PAT 限制读取 | 只拦得住 Agent，人照样能看；先有记录，确实需要时再在记录上加限制 |
| 隐藏数据集：只能上传、不能读 | 题面会经 trace 带出，trace 也得隐藏，与“证据从宽”冲突；答案保密见第 4.4 节 |
| 访问记录挂在集合上 | 集合固定的是配置维度，同一个留出集会被多个集合、多条改进线共用 |
| 为每种工作流建专门的表和页面 | 工作流会越来越多；通用记录加 SDK 模块已经够用（U-73、U-74） |

## 12. 实施（U-83、U-84）

### 12.1 方式

- 本提案整体确认后动工。各阶段在一条长期集成分支上进行（暂名 `feature/n33`，从 `dev` 建立），全部完成、恢复可运行后一次性合入 `dev`。`dev` 每次推送都会自动发布预览版和 `.devN` SDK，其他会话与 `Gitea#18` 的修复也从 `dev` 起步，所以中间状态不进 `dev`。
- 中间阶段不要求可运行：网页、SDK、E2E 可以落后，旧功能可以临时下线。每个阶段结束时后端的 ruff 与 pytest 保持通过，这是写代码的 Agent 主要的反馈来源。
- 分支 push 检查照常运行，网页构建等未跟上的部分在该分支上失败属预期，以后端检查为准。
- 长期分支定期合并 `dev`（merge，不改写历史）。每个阶段建议以 PR 合入长期分支，便于用户审阅。
- 系统说明随阶段在长期分支上改写；本提案在最终合入 `dev` 的 PR 中标记完成并归档。
- 现场已有的运行、集合与结果不保留（U-84）：升级后改用全新 state，迁移照 U-34 只追加，但不负责转换旧数据。

### 12.2 阶段

| 阶段 | 内容 | 对外的效果 |
| --- | --- | --- |
| 0 | 本提案：统一的数据模型、阶段划分与待定问题 | 只有文档 |
| 1 | 评测记录重构：分数从试次结果迁到评测记录，此时只有内置评测；评测身份；比较按评测身份分组；错误策略与失败分组的划分 | 功能不变，内部结构换掉 |
| 2 | 任务清单、集合绑定清单、按清单提交、读取记录、任务清单网页 | 留出集可用 |
| 3 | 工作流适配：skill 修订、SDK 工作流模块与 `workspace.init`、工作流记录、当前最优指针、`attachment-candidate` | 附件改进工作流可用 |
| 4 | 上传数据集、输出契约与长期保留、参考答案与评测方案、评测器与评测任务、结果包导出导入 | CADGenBench 可用 |

阶段 1 放在任务清单之前，任务清单就能直接建立在最终的分组方式上；这细化了 U-79 的“先做 N-32 再完成 N-31”。阶段 4 可能还要再拆。

### 12.3 CADGenBench 手动验证

不依赖平台改动，可以和任何阶段并行，但要在阶段 4 定格式之前完成。在独立的验证会话中进行：

1. 手动把少量题目转换成 Harbor task，并声明 `output.step` 为输出。
2. 在全新的 state 上运行，确认 `output.step` 完整进入产物，不被截断或脱敏。
3. 在平台外用 CADGenBench 的评测代码给这些产物评分，确认三件事：能否容器化，是否需要 GPU，没有参考答案时能否只算有效性门槛。
4. 根据结果写出输出契约、评测方案契约和结果包格式的草案，回填本提案。

真实模型请求需要用户确认预算后再发；没有确认时，用固定脚本生成 STEP 来代替 agent。

## 13. 验收

各阶段的验收在动工前细化，初步标准：

- **阶段 1**：同一组测试运行在重构前后得到相同的比较数字；一个试次可以有两条不同评测身份的记录，比较按身份分组、不混算。
- **阶段 2**：跨数据集的任务清单一次受理并拆成多个运行；集合只接受与清单成员一致的运行；只有能看到任务内容的读取进入汇总；成员缺失时清单不可用；复制得到新清单，旧清单与读取汇总不变。
- **阶段 3**：用户重新跑一遍附件改进实验（U-76）。
- **阶段 4**：CADGenBench 能在平台上完成“只执行 → 导出可提交的 zip”，并在本地给出有效性门槛的结果；一次已有运行的产物能换一种评测方案重新评分，而不必重跑 agent。
