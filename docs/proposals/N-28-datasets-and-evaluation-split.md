# N-28 数据集拓展与执行 / 评测拆分

状态：设计中 · 优先级：待定 · 2026-11-03 · 相关：[01](../design/01-domain-model.md)、[02](../design/02-datasets-preparation.md)、[06](../design/06-results-scoring.md)、[07](../design/07-artifacts-export.md)、[09](../design/09-identity-security.md)、[15](../design/15-stack-harbor.md)、U-10、U-20、U-31、U-68、N-29

本提案目前只定方向和关键问题，留有大量待定事项。下一步先用 CADGenBench 做一次手动验证（见“验证计划”），再根据结果拆成实施提案。

## 问题

1. **数据源只有 Harbor Hub。** 团队想测的 benchmark（目前主要是 CAD 领域）多数发布在 Hugging Face 上，提供方没有做 Harbor 适配，格式也各不相同。
2. **高质量评测集常常隐藏答案。** 以 [CADGenBench](https://huggingface.co/datasets/HuggingAI4Engineering/cadgenbench-data) 为例：
   - 公开 81 道题，其中 49 道根据工程图生成、32 道编辑 STEP，每题要求输出一个 `output.step`。
   - 参考实体放在私有仓库里，作者明确规定只在服务器端评分。
   - 评测代码（CAD Score：先过有效性门槛，再对形状、接口、拓扑三项加权）在 GitHub 公开。
   - 提交方式是把产物和 `meta.json` 打成 zip，上传到排行榜 Space。

   以上是 2026-11-03 读数据集卡片所见，评测代码尚未核对。
3. **执行和评测绑在一起。** 现在 agent 执行完由 Harbor verifier 立即判分，带来三个限制：
   - 不能只生成结果、交给外部评测；
   - 不能复用已经跑出的昂贵结果，例如旗舰模型的产物，只换评测方案或参考集重新评分；
   - 判分逻辑一改，就只能重跑 agent。

## 方向（讨论中）

### 1. 只接受已转换好的数据，平台不运行转换器

每个 Hugging Face benchmark 基本都要单独写转换器，所以平台不读取原始数据，也不在服务器上运行转换代码。转换由使用者在自己那边完成（可以参考 Harbor adapter），平台只按**格式契约**接收结果。

- **版本身份**：上传内容的 digest。上游仓库、revision 和转换器版本作为来源说明保存，只用于展示，平台不核实。
- **上传通道**：倾向复用附件的内容寻址快照与增量上传（[03](../design/03-configuration-attachments.md) 第 6 节），由 SDK 发起。
- **代价**：平台无法“检查上游更新”，转换能否复现由使用者负责。

### 2. 数据集拆成三个概念（名称待定）

| 概念 | 内容 | CADGenBench 中的对应 |
| --- | --- | --- |
| 题目集 | 输入、题面和可执行环境（Harbor task），以及**输出契约**（见关键问题 1） | `cadgenbench-data`（公开） |
| 参考集 | 按任务组织的标准答案或参考产物 | `cadgenbench-data-gt`（私有，拿不到） |
| 评测方案 | 评测镜像、入口、指标与分数格式 | `huggingface/cadgenbench`（公开） |

评测方案和参考集可以自由组合。只有题目集时，不需要答案的评测（例如 STEP 有效性门槛）仍可以在本地运行。

### 3. 记录层统一，执行层按阶段分开

一个运行由阶段组成：执行阶段走 Harbor，评测阶段走平台自研的评测器。三种用法只是阶段组合不同，共用同一套队列、容量、取消、记录、产物、比较和 SDK：

```
完整运行：执行（Harbor）→ 评测（自研）
只执行  ：执行（Harbor）→ 导出结果包（可按 benchmark 格式导出提交文件）
只评测  ：已有运行的产物 / 导入的结果包 → 评测（自研）
```

- **“只评测”预计会经常用**（用户 2026-11-03：“实验本身很贵，如果一个旗舰模型跑了一个结果，我很想复用”），所以不做成独立的小工具。
- **现有 Harbor 数据集**的 verifier 继续在 Harbor 里运行，记为“内置评测”，这次不迁移。
- **评测器只做一件事**：在容器里运行评测镜像，挂载产物与参考集，读取分数文件。它复用现有的镜像准备、容器执行和产物存储。平台不自己实现替代 Harbor 的 agent 运行器。

### 4. 上传与准入的权限

- 使用者在本地转换完成后，最自然的上传方式是 SDK 或 Agent 脚本，因此需要 PAT 能上传。
- 用户倾向更进一步：PAT 连准入也可以做，前提是 PAT 的权限可以细粒度设置，由管理员决定授予什么，平台不替管理员做决定。
- 这会推翻“PAT 永不具备管理员能力”（IAM-02）和“导入只限管理员网页会话”（U-20），影响面大，所以拆成单独的 **N-29 细粒度 PAT** 讨论。本提案只依赖“存在一种可以上传和准入的授权方式”。

### 放弃的做法

| 做法 | 放弃原因 |
| --- | --- |
| 平台内置 Hugging Face 数据源，在服务器上运行转换配方 | 转换器因 benchmark 而异；在服务器上运行第三方代码有安全问题，配方的版本也难以管理 |
| 在服务进程内加载第三方 Python 插件 | 插件能接触主密钥和数据库，接口也会和内部实现绑死 |
| 执行和评测分成两个独立的产品模式 | 比较、SDK、权限都要做两份，成员会困惑结果在哪里 |
| 把执行也改为自研 | Harbor 已经处理好 agent 接入、隔离、超时和日志 |

## 关键问题（2026-11-03 讨论中识别）

1. **Harbor 判分的对象是环境，不是产物。** Harbor 的 verifier 在 agent 结束后、容器还在时，进入同一环境检查状态。平台保存的产物只是 Runner 按上限复制的工作目录和日志，并不保存容器的最终状态。
   - 因此只有**声明了输出契约**（agent 必须交出哪些文件、放在哪里）并且平台确实保存了这些文件的任务，才能做只执行、只评测和复用。
   - Terminal-Bench 这类检查整个环境状态的任务做不到事后评测。
   - 输出契约比“三个概念”更底层，需要先定格式，并确认产物上限、脱敏等现有规则不会损坏这些输出（例如 STEP 文件会不会被当成文本脱敏）。
2. **分数需要身份。** 分数由产物、评测方案版本和参考集版本共同决定。
   - 比较页必须按评测方案和参考集版本对齐，否则不同评测器给出的分数会被悄悄混在一起。
   - 同一个运行可以有多份评测，比较时默认显示哪一份需要规则。
   - 导入的外部结果有产物但没有可复现的执行，可以参与评测和比较，但不能重跑，需要明确标识。
3. **参考答案放进平台后就不再保密。** 现有设计中，read PAT 能看到参考答案和验证代码（[09](../design/09-identity-security.md) 第 6 节），证据也从宽开放（U-10）。
   - 拆开执行和评测之后，执行容器可以完全不接触参考集，从而防止 agent 读到答案。
   - 答案对成员和 PAT 是否可见，需要用户决定。
4. **细粒度 PAT 会改变安全边界**，见 N-29。
5. **评测本身也有成本。** CADGenBench 另有 `cadgenbench-eval-gpu` Space，评测可能需要 GPU，而平台目前不支持 GPU 任务。LLM judge 也会消耗模型额度。评测阶段需要纳入容量管理与资源限制。

## 验证计划

在定格式之前，先用 CADGenBench 手动走一遍，在独立的验证会话中进行：

1. 手动把少量题目转换成 Harbor task，并声明 `output.step` 为输出。
2. 在全新的 state 上运行，确认 `output.step` 完整进入产物，不被截断或脱敏。
3. 在平台外用 CADGenBench 的评测代码给这些产物评分，确认三件事：能否容器化，是否需要 GPU，没有参考集时能否只算有效性门槛。
4. 根据结果写出输出契约、评测方案契约和结果包格式的草案，回填本提案。

真实模型请求需要用户确认预算后再发；没有确认时，用固定脚本生成 STEP 来代替 agent。

## 影响（初步）

- 01：增加题目集、参考集、评测方案、输出契约、产物包和评测记录，并定义它们与运行、试次的关系。
- 02：增加上传来源，版本身份改为内容 digest 加来源说明；首次准备与准入规则随 N-29 调整。
- 06：分数要标明来源和评测身份；需要支持独立重新评测。
- 07：结果包的格式、导出（含按 benchmark 的提交格式）和导入校验。
- 08：比较按评测身份对齐，并标明外部结果。
- 09：参考集的可见性；PAT 的变化见 N-29。
- 05：评测阶段的排队、容量和资源限制。

## 待定问题

**概念与格式**

1. 三个概念的正式名称及其在网页上的呈现。
2. 输出契约的格式：放在 `task.toml` 的扩展字段里，还是放在单独的文件里？
3. 评测方案的契约：输入目录、分数文件格式、资源与时限。它和 Harbor verifier 的奖励格式是什么关系？
4. 结果包的格式；是否按 benchmark 提供导出 / 导入转换器，转换器又由谁来写（可能同样由使用者负责）。
5. 参考集是否作为独立对象、单独管理版本；对成员和 PAT 是否可见。

**执行与评测**

6. 现有 Harbor 数据集以后是否也迁移到自研评测器上。
7. 同一运行有多份评测时，比较页默认显示哪一份。
8. 外部回填的分数（例如排行榜成绩）是否录入平台，如何标注。
9. 导入结果包的大小、格式校验与权限。
10. 评测阶段是否需要 GPU 支持；如果需要，是否作为前置工作。

**范围与顺序**

11. 拆成几个实施提案、按什么顺序；与 N-29 的先后关系。
12. 团队还想测哪些 CAD benchmark？要逐个确认数据形态、答案是否公开、评测代码是否公开。
