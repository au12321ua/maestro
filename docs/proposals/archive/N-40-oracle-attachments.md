# N-40 Oracle 运行带附件

状态：完成（U-101） · 优先级：建议二 · 2026-11-11 · 相关：[03 配置与附件](../../design/03-configuration-attachments.md)、[05 调度与执行](../../design/05-scheduling-execution.md)、[06 结果与评分](../../design/06-results-scoring.md)、[09 身份与安全](../../design/09-identity-security.md)、[11 网页](../../design/11-web-ui.md)、[15 Harbor 集成](../../design/15-stack-harbor.md)、[N-39](../N-39-skill-datasets-environments.md)、[N-41](N-41-submission-runs.md)

## 问题

附件是否能安装，目前只能通过真实模型运行验证。即使只想检查 `bootstrap.sh`，安装成功后仍会进入完整的模型执行，产生模型费用。附件还可能安装成功却破坏任务依赖，仅看安装日志发现不了。

以 `dev` 的 `5f72238` 为核对基线：

- `src/maestro/services/configuration.py` 对 Oracle 附件返回 `ORACLE_HAS_NO_ATTACHMENTS`。
- `runner/src/maestro_runner/job.py` 再次拒绝没有模型 Harness 适配器的附件；安装逻辑在 `runner/src/maestro_runner/agents.py` 的模型 Agent 包装层中。
- 当前 Oracle 执行题目自带的参考解，再由 verifier 评分；其结果是测试模式，不能参与比较或加入集合。

建议让 Oracle 在运行参考解之前安装附件，用来检查安装脚本及其对任务环境的影响。本轮只写设计。

## 方案

### 1. 沿用 Oracle，增加附件安装阶段

配置仍使用 `execution_mode = oracle`，允许传入现有的有序附件列表与安装时限。无需模型配置、模型凭据或 Harness，仍不接受这些模型字段。

每个试次的顺序为：准备并启动任务环境 → 复制、校验并按顺序安装附件 → 执行任务参考解 → verifier 评分 → 收集产物与清理。

附件列表、顺序和安装时限照常进入不可变快照与配置摘要。附件缺失、停用、冲突和内容不符沿用已有预检及受理复核，不因是测试模式绕过。

### 2. 没有 Harness 时不做兼容检查（已定，U-99）

Oracle 运行不检查附件的 `compatible_harnesses`，任何附件都可以安装。用 Oracle 检查安装，要检查的正是为某个 Harness 写的附件（例如把 skill 装进 Codex 目录的附件）；若要求附件额外声明 `oracle`，就得先改声明、发布新快照，检查的已不是原来那份附件。Oracle 是测试模式，不参与比较，放宽兼容检查不会影响模型运行的结果。

- Oracle 不安装模型 Harness。网页和预检提示：没有安装 Harness，依赖 Harness 文件或命令的脚本可能失败，失败如实记录。
- 不根据 `effects` 猜测兼容性；缺失、停用、冲突和内容不符的检查照常执行。
- 模型运行的兼容检查保持不变。

### 3. 共用安装逻辑与失败语义

将现有复制、摘要校验、容器内限时执行与安装记录的逻辑供 Oracle 包装类共用，保留模型 Agent 原有安装顺序。这层无 Harness 的安装包装也供 [N-41](N-41-submission-runs.md) 的提交评分使用。无需修改任务原件或把附件提前烘焙进共享环境镜像。

- 安装目录、任务用户、`MAESTRO_ATTACHMENT_DIR`、顺序、累计脚本时限和传输限时与模型运行一致，每个试次独立安装。
- 安装失败或超时仍记 `attachment_failed`，没有分数，不运行参考解和 verifier，不记成 0 分；传输与内容不符按原有错因和重试规则处理。
- 安装成功后参考解或 verifier 失败，保留其原有执行阶段和错因，安装记录仍可查；不能把所有后续错误都归为安装失败。
- 沿用运行队列、CPU / 内存、并发、总时限、取消与资源释放规则。没有模型费用仍占计算资源和 PAT 受理额度。

### 4. 安装网络与执行网络（已定，U-99）

有附件的 Oracle setup 也取得当前部署安装网络，供脚本使用，并在执行尝试中记录安装网络版本；这需要同步修改服务端组装 Runner 输入时“只有模型 Harness 才下发 setup 环境”的条件。

代理和安装环境只在 setup 使用，不泄入参考解与 verifier。Oracle 后续执行继续遵循已有的 Oracle 与任务网络规则，不套用模型 endpoint 的网络策略；模型运行的网络收紧保持现有语义。无附件的 Oracle 不新增安装步骤或安装网络依赖。

### 5. 网页、SDK 与结论

- 新建运行选择 Oracle 后可选附件、调整顺序及安装时限；运行详情展示逐附件安装记录与日志。
- SDK 沿用运行配置和提交入口，更新字段说明、能力说明及生成模型；skill 和工作区模板不再写“Oracle 不能带附件”。
- `maestro-package` 将检查拆成两个目的：Oracle 检查脚本和参考解在该环境中能否完成；真实模型小规模运行检查 Harness 是否发现、加载并使用附件。后者仍须按任务授权确认规模和费用。
- Oracle 仍不能参与比较或加入集合。可人工核对有附件与无附件 Oracle 的逐题得分和日志，但得分不同只能说明需要调查，不能直接证明附件导致退化或提高了模型能力。

## 影响

| 部分 | 预期变化 |
| --- | --- |
| 配置与 API | 放开 Oracle 附件；Oracle 下跳过 Harness 兼容检查；同步请求说明、OpenAPI、SDK 和网页类型 |
| 服务与 Runner | Oracle 包装类复用安装器；下发 setup 环境、记录安装网络版本、上报安装证据 |
| 网页与 skill | Oracle 表单及安装证据入口；区分脚本检查与模型加载检查 |
| 系统说明 | 实施时改写 03、05、09、10、11、13、15，解释 Oracle 安装与网络阶段 |

预计复用现有附件快照、安装记录与运行快照，不新建业务对象；实施时核对是否需要扩大现有约束，数据库变化只追加迁移。

## 验收

- 全新独立 state 中，以现有本地 Oracle fixture 运行两个有依赖顺序的附件，确认顺序、摘要、安装用户、脚本日志与参考解得分。
- 安装脚本失败或超时后，不执行参考解和 verifier，结果无分数；取消安装中的运行能释放资源。
- 一个安装成功但破坏参考解所需文件的附件，在后续执行或评分中暴露差异，能区分安装成功与任务失败。
- 只声明某个模型 Harness 的附件也能在 Oracle 下安装，并显示没有 Harness 的提示；冲突、停用和摘要不符的行为不被绕过。
- 有附件的 Oracle 获得 setup 环境与版本记录，参考解和 verifier 不继承安装专用变量；无附件 Oracle 和模型附件运行均通过回归。
- 网页和 SDK 均可提交并看到安装证据；Oracle 仍被比较与集合拒绝。验证不调用真实模型。

## 结果

已实现 Oracle 附件安装：复用有序复制、摘要校验、限时脚本与安装记录；跳过 Harness 兼容检查并提示，无附件 Oracle 保持原路径。有附件时下发并记录 setup 网络，作用域结束后参考解与 verifier 不继承安装变量。配置、SDK、网页与 Runner 回归通过；真实 Docker 验证（2026-11-12，提交 `70e5564`，Harbor 0.24.0，rootless Docker）：新增用例通过，整份 `live/test_harbor_docker.py` 串行 20 通过、6 个真实模型用例跳过，结束后无残留容器、镜像、网络或卷；`-n 4` 并行时两个既有用例因共用本机镜像互相干扰而失败，串行通过。未调用真实模型。
