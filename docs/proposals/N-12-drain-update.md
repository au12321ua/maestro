# N-12 带排空的更新与维护模式

状态：设计中 · 优先级：二 · 2026-10-27 · 相关：[部署运维](../design/12-operations.md) 第 4、5 节、[调度执行](../design/05-scheduling-execution.md)、[测试与验收](../design/13-testing-plan.md)、U-29、U-30

## 问题

`maestroctl update` 现在遇到执行中的运行或进行中的导入、首次准备就拒绝，只能等它们结束或用 `--interrupt-running` 中断（[12](../design/12-operations.md) 第 5 节）；`stop` / `restart` 同样直接中断在途工作。等待期间新运行还在不断受理和派发，团队忙时几乎找不到空档。按 U-30，CD 推送即发布，更新会变得频繁，需要一个“先停新工作、等在途工作结束、再切换”的维护模式。修改 `worker_slots` 等需要重启的执行容量配置也有同样的问题。

## 方案

维护模式（原 05 第 9 节）：先禁止新受理和新派发，再按管理员的选择等待已领取项完成（有期限）或立即取消；排队项保留到维护结束，除非已到运行总时限。查询、取消、下载照常可用；`/health/ready` 与能力接口报告 `maintenance`，阻塞项说明原因。

更新流程在现有同机更新（安装在旁、自动备份、迁移、原子切换、失败连同数据库回退）之前加入排空：

1. 管理员用 `maestroctl update <包> --drain [--deadline …]` 请求明确目标版本，先验证包来源、摘要与兼容信息，新版本在旁边装好。
2. 创建持久的维护记录，通知服务进入 draining：阻止新受理与新派发。
3. 等待已领取项完成，期限到了按选择取消或中断；排队项留存。
4. 停服务，生成一致性数据库备份与部署配置副本；主密钥不进备份。
5. 迁移、原子切换 `current`、启动并验证健康、迁移与基础读取。
6. 成功后解除维护；原排队项在派发前重新检查时限与引用（附件、凭据、准入等）。
7. 失败时保留诊断信息；已迁移则恢复更新前数据库与旧程序，与现有回退相同。

维护记录不能只存在于将被停止的 API 进程内：由 `maestroctl` 持有自己的持久存储（例如 `/var/lib/maestro/maintenance/`），记录请求、阶段与结果，API 重启后同步；`maestroctl status` 与网页在断线恢复后都能查到同一次维护的结果。

放弃的做法：网页发起更新（U-29 只做命令行）；只切换 `current` 不恢复数据库的“回滚”。

## 影响

- [12](../design/12-operations.md) 第 4、5 节：维护模式、`--drain`、维护记录；第 3 节注明哪些配置改动可以走排空后重启。
- [05](../design/05-scheduling-execution.md)：Worker 的 draining 状态（不领取新运行，已领取的照常推进）；排队项恢复时的复检。
- 受理路径与 `/health/ready`、`/capabilities`、系统状态增加 `maintenance` 阻塞项；网页显示维护状态（只读）。
- `src/maestro/backup.py` 的 `activity` 改为排空进度的依据；`ops/maestroctl.py` 增加维护记录存储。

## 验收

- 空闲与有在途工作两种情况下各完成一次更新：在途运行按选择完成或取消，排队项在新版本上继续，没有运行被重复执行或丢失评分。
- 排空期间新提交被拒绝且不扣额度，查询与取消可用。
- 迁移后启动失败时旧程序与更新前数据库一起恢复（13 的 F-14），维护记录显示失败原因。
- 更新过程中网页断线，恢复后仍可查询同一次维护的结果。

## 待定问题

- 排空期限的默认值，以及期限到时默认取消还是中断。
- 进行中的首次准备、导入是否也等待，还是一律取消后由管理员重试。
- 是否给 `stop` / `restart` 也提供 `--drain`。
