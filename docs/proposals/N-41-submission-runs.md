# N-41 用指定提交代替参考解的 Oracle 运行

状态：设计中，未确认实施 · 优先级：建议二 · 2026-11-11 · 相关：[03 配置](../design/03-configuration-attachments.md)、[04 提交与重跑](../design/04-plans-submission.md)、[06 结果与评分](../design/06-results-scoring.md)、[07 产物](../design/07-artifacts-export.md)、[08 比较](../design/08-collections-comparison.md)、[15 Harbor 集成](../design/15-stack-harbor.md)、[N-33](archive/N-33-held-out-benchmarks-workflows.md) 第 6.1 节、[N-40](N-40-oracle-attachments.md)、U-86

## 问题

mesh2cad 实验后登记的想法（`764d601`）记录了三类本地手工操作：在新旧环境中重放同一批提交、按重放条件检查一种交付写法、在评分器镜像里给改写的提交打分。它们都需要把一份已有文件提交放入任务环境，再运行题目的 verifier，而无需重新调用模型。

以 `dev` 的 `5f72238` 为基线，平台只能重新执行模型，或让 Oracle 运行任务参考解。下载旧产物后在平台外评分，执行条件、文件来源和评分结果不能作为一次完整运行留存。

[N-33](archive/N-33-held-out-benchmarks-workflows.md) 与 U-86 暂缓了独立评测记录、评测身份和评测任务，并要求有真实案例后先考虑接收外部分数。本提案提出一个候选方案：在普通运行里以文件提交替换参考解，再走 Harbor verifier。是否符合启动条件、是否采用这一方案，仍需用户决定；写成提案不解除 U-86 的暂缓。

## 方案

### 1. 创建新的运行，固定提交来源（建议）

每次评分创建普通的运行、配置快照、试次和执行尝试，沿用队列、容量、额度、超时、取消及结果语义；不改变来源试次的分数，不给一个试次追加多份评测。

原想法称它为“用指定提交的 Oracle”。但现有 Oracle 特指参考解，而且不能参与比较。建议公开配置使用单独的执行方式 `submission`（名称待定），页面称“已有提交评分”，明确它不调用模型，也不表示执行参考解。它仍是一次运行，不新增独立的评测对象。

执行顺序：恢复目标数据集版本的准备成果 → 启动干净环境 → 放入指定文件 → 运行题目 verifier → 收集评分与产物 → 清理。既不执行模型，也不执行 `solution/solve.sh`。

### 2. 提交是一份固定的文件集合

建议支持两种输入，通过同一套文件清单固定为内容快照：

| 输入 | 选择方式 | 固定时机 |
| --- | --- | --- |
| 平台内已有交付物 | 明确指定来源试次及执行尝试，再选其中的交付物；不自动挑最高分或最新运行 | 受理前复制并校验所选字节，取得独立内容引用 |
| 本地修改或外部得到的文件 | 网页选择文件夹或 SDK 上传，使用已有内容寻址通道，只传缺失文件 | 上传后校验清单与摘要，再由运行持有引用 |

文件清单记录相对路径、内容摘要与可执行位，源文件进入回收站、不可读、过期或保存失败时不能作为新输入。来源索引还在但字节已失效，也不能继续评分。

不把它伪装成附件：输入无需 `manifest.json`、没有 `bootstrap.sh`，也不声明工具或 Harness 兼容性。可共用内容存储和上传组件，但输入语义独立。文件大小与数量受现有内容上传及产物配置约束，实施时明确各阶段适用的上限。

### 3. 显式映射文件到任务，不能反推收集路径

Harbor 的 `task.toml` 中 `artifacts` 描述如何收集文件，并非通用的提交还原协议：文件可重命名、目录可筛选，默认的 `/logs/artifacts/` 也未必是 verifier 实际读取的位置。因此不能看到一个产物路径就推断应该写回容器哪里。

建议请求为每个目标任务列出文件映射，语义类似：

```text
目标任务 cad-part-a：
  输入文件 output.step → 主容器 /app/output.step
```

- 目标任务来自明确的数据集版本，以该版本任务标识固定。来源可来自其他版本或数据集；同名任务只供选择时提示，不自动建立对应关系。
- 映射是输入相对文件路径到主容器绝对路径的明确列表，路径与字节一起进入快照和摘要；拒绝重复目标、路径穿越及指向平台凭据、附件、参考解、验证材料或日志控制目录的写入，不能借符号链接绕过。
- 首版建议只处理主容器中的普通文件，不支持恢复容器、服务、数据库或挂载卷的状态。目录由文件列表展开，不通过解包任意归档恢复现场。
- verifier 需要文件出现在哪个位置，由任务作者或操作者指定；不是平台依据文件名猜测。只有 `/logs/artifacts/` 收集副本而无实际输出时，必须明确如何放到 verifier 所需路径。
- 独立验证器只沿用任务已声明的文件传递契约；没有该契约、需要向验证器容器任意注入文件的任务，首版明确拒绝。多步骤任务同样留待扩展。

一个目标试次对应一份固定输入及其来源。首版建议每个目标任务每次运行选一份提交，重复次数固定为 1；对同一文件重复评分或换另一份提交，都创建新运行。来源的一批不同重复试次可由调用方展开成显式运行批次，避免隐含配对或取优。

### 4. 来源关联与保留

运行快照保存输入内容摘要、每个目标试次的文件映射、来源运行 / 试次 / 执行尝试 / 产物标识，以及目标数据集版本和执行条件。上传文件仅保存上传者与摘要；由人补充其真实来历，不能从文件名推断模型身份。

现有 `source_run_id` 表示整次运行的来源，不足以表达不同任务来自不同试次的情况。本提案的逐试次来源必须作为程序可读事实保存；工作流记录可写原因和结论，不能代替重跑所需的输入。

建议输入内容随新运行持有独立引用，直至新运行被物理删除，不受来源产物的到期或删除影响。原始产物仍按原保留期清理，其索引和来源关联可继续查看。这样同一文件可以在另一数据集版本或不同执行条件下再次评分，也能按固定快照重跑。代价是这部分输入会长期占用存储，需要在确认时接受这一保留规则。

受理失败不留下长期输入引用；复制和确认引用须处理与来源清理的竞争。按原配置重跑仍核对当前权限、准入和目标内容可得性；主动换数据集版本或映射属于“修改后运行”。

### 5. 评分、比较与读取记录

- 文件传输或摘要校验失败是执行错误，没有分数；文件放置成功但 verifier 判定交付物不合格，可以得到有效 0 分。verifier 没产分数、超时或崩溃按既有规则区分。
- 运行详情展示“已有提交评分”、输入来源、目标数据集版本和映射，不把新分数显示成来源模型当时的分数。
- 建议首版仅允许这类运行彼此比较，与 `agent`、`oracle` 分开；同一目标数据集内容和计分规则下沿用已有对齐规则，跨版本仍只并列原始汇总、不给差值。输入文件及映射是明确的比较条件，集合需要固定目标数据集与映射规则，不能混入现有模型集合。最终比较范围待确认。
- 读取来源交付物计入来源任务的内容读取汇总，包括服务端为操作者复制提交的入口；查看新运行日志与产物记目标任务读取。来源关联本身不算内容读取，平台不自动宣称某次留出评估仍然有效。

### 6. 首版边界与替代方案

建议首版同时提供网页和 SDK：从已结束试次选择交付物，或上传文件；选择目标数据集和任务、填写映射、预检后提交。网页复用文件上传组件和运行详情，SDK 提供相同语义，均需 `experiment` 权限；不要求登录服务器。

不增加附件安装或任意预处理脚本。需要另一种评分环境时，先按 [N-39](N-39-skill-datasets-environments.md) 改数据集版本。本项与 N-40 独立，不以 Oracle 附件支持为前置条件。

U-86 所说的“上传外部分数”仍是可选的更小方案：它避免服务器执行和输入长期保留，但无法提供平台内固定环境下的可重跑评分。确认本提案前，应由用户决定是否需要后一种能力。

## 影响

- 数据与接口：新的运行输入、文件快照引用和逐试次来源，解析与受理、幂等、重跑、删除及存储回收；具体字段与端点在模式和范围确认后确定。迁移只追加。
- Runner：实现仅放入输入文件的 Agent 适配器及安全路径校验，再调用已有 verifier；明确阶段网络策略，不下发模型凭据，不执行参考解。
- 网页与 SDK：选择来源文件或上传、文件到任务的映射与预检、来源展示及提交；同步 OpenAPI、生成模型和能力发现。
- 比较与导出：新增执行方式的准入和条件核对、来源与固定输入的导出说明；不得沿用 Oracle 或模型标签造成误读。
- 实施时改写系统说明 01、03～11、13、15；不创建独立评测身份或引入暂缓的整套评测对象。

## 验收

- 全新独立 state 上，选一个只靠文件交付物评分的任务，用固定文件和 verifier 完成一次运行；确认既没有模型请求，也没有执行任务参考解。
- 从来源试次选择文件，与上传同字节文件，映射一致时得到同样的有效输入；结果都能追溯固定摘要，平台来源能定位到确切尝试。
- 换目标数据集版本后重新运行，来源文件与历史分数不变，新运行保存新的条件和结果；跨版本比较不给按题差值。
- 文件内容不合格得到有效 0 分；传输失败、缺少有效输入及 verifier 没产分数不记成 0。输入映射有遗漏或路径不安全时在预检拒绝。
- 来源交付物已过期时不能新建输入；新运行受理后再清理来源，不影响其执行和按快照重跑。新运行物理删除后释放它持有的输入引用。
- 重复提交使用同一幂等键只建一个运行；取消、资源释放、总时限及只读 PAT 限制沿用现有规则。
- 来源与目标的内容读取按上述入口计入；网页与 SDK 能完成同一流程，比较按最终确认的模式边界执行。

## 待定问题

1. **是否启动这项能力？** 实验中的三个手工案例是否满足 U-86；采用平台内可重跑评分，还是先做上传外部分数。
2. **运行身份与比较范围。** 是否接受独立执行方式 `submission`，首版仅同类运行互比；还是保留为 Oracle 子模式并继续排除所有比较。
3. **输入和映射范围。** 是否同时支持来源交付物和上传文件，首版采用显式逐文件映射、主容器单步骤、每任务一份提交且重复次数为 1。
4. **输入保留。** 是否接受由新运行独立持有输入直至物理删除，以保证来源产物过期后仍可重跑；如果不接受，需要另定保留期与不可重跑的提示。

## 结果

本轮从想法整理为提案，尚未实施。待定问题确认前不改变 U-86 或现有 Oracle、比较与产物保留行为。
