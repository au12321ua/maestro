# N-43 简化版本发布与开发包构建

状态：实施中 · 日期：2026-11-13 · 相关：[部署运维](../design/12-operations.md)、[发布指南](../guides/releasing.md)、U-104

## 问题

正式版本、dev 占位版本、预览 tag 与 SDK 的 CI 运行号同时存在，增加发布和辨认运行版本的成本。取消自动预览后，维护者仍需要容易构建、可安装的开发包。

## 方案

- 日常修改从 dev 建短期分支、独立 worktree，经审查与检查合入 dev；dev push 只验证，不再自动发布开发 Release 或 SDK。
- 选定 dev 的固定提交后，在一条临时 release 分支上统一设置 X.Y.Z、生成契约与发布说明，对最终候选 SHA 验证。正式 master、附注 tag、两端 Release、SDK 包与 Pages 校验沿用现有保证。
- 发布后把正式候选同步回 dev，保留并发开发提交；不再准备下一开发版本或 release/*-next 分支。dev 的包版本保持最近一次正式版本，发布时按实际变化定下一版本。
- 源码运行及临时开发安装包报告提交与 unreleased 标记，正式构建仍报告版本与提交。开发 SDK 与服务共用源码中的版本，只随开发包交付，不上传包索引。
- 提供一条本地开发打包命令：默认获取 origin/dev，也可选择已提交的 ref；自动建独立工作树、隔离构建环境、安装锁定依赖、构建与验证实际 wheel，输出安装包和摘要。成功后核对并清理工具自建工作树；失败保留目录和诊断。命令不操作服务或已有 state。
- 开发包经已有 maestroctl update 本地包入口安装。网页仍只检查正式版本；打包不等于部署。

## 影响

调整发布准备、收尾、版本校验、构建清单与运行版本展示，增加开发打包入口，移除 CI 自动预览路径；同步系统说明、交接、开发、发布、部署与 SDK 文档。不改变任务执行、数据库或公开 API 的结构，不执行实际发布或部署。

## 验收

- 中断后的候选准备可续跑，固定业务范围；无下一开发分支和版本递增提交。
- 正式发布只接受准确候选 SHA 的完整检查，不改动已共享 tag 或附件；部分发布失败不报告完成。
- dev 收尾包含发布提交与并发工作，可重复执行，不回退后续正式版本。
- 开发包构建不改变调用者 checkout；构建与校验失败保留现场，输出不覆盖其他构建；包中服务、SDK、清单、摘要一致。
- 实际构建并在全新环境校验开发包；运行版本可区分正式版、开发源码与开发包。
- Python、契约、前端及文档检查通过；不使用真实团队 state、Docker 或模型请求。

## 待定问题

无。发布流程由用户本轮确认；开发包的一条命令与隔离工作树为实现选择。

## 结果

实施中；完成后结论并入系统说明，同一 PR 归档本提案。
