# N-41 给已有提交评分

状态：完成（U-101） · 优先级：建议二 · 2026-11-11 · 相关：[03 配置与附件](../../design/03-configuration-attachments.md)、[05 调度与执行](../../design/05-scheduling-execution.md)、[06 结果与评分](../../design/06-results-scoring.md)、[08 集合与比较](../../design/08-collections-comparison.md)、[N-40](N-40-oracle-attachments.md)、[N-33](N-33-held-out-benchmarks-workflows.md) 第 6.1 节、U-86

## 问题

mesh2cad 实验后登记的想法（`764d601`）记录了三处本地手工操作：在新旧环境里重放同一批提交、按重放条件检查一种交付写法、在评分器镜像里给改写的提交打分。它们都是把已有的文件放进任务环境，再跑题目的 verifier，不调用模型，也不跑参考解。

以 `dev` 的 `5f72238` 为基线，平台只能重新执行模型，或让 Oracle 运行任务参考解。在平台外评分时，执行条件、文件和分数不能作为一次运行留存。

这三处都是检查数据集或 verifier，不产出拿去比较的结果。所以本提案只解决“在平台里放入文件、跑 verifier、留下记录”，不做 U-86 暂缓的评测拆分（评测记录、评测身份、一个试次多份评测），也不让这类分数参与比较。

## 方案

### 1. 待评提交：附件的一个类别

在附件包上增加类别：`attachment`（附件，默认）与 `submission`（待评提交）。类别写在 `manifest.json` 中，属于内容身份。待评提交复用附件已有的全部机制：选文件夹上传、内容寻址存储、不可变快照与标签、文件数与大小上限、回收站与物理删除、安装记录与日志。

待评提交仍由 `bootstrap.sh` 把文件放到 verifier 读取的位置。安装时除 `MAESTRO_ATTACHMENT_DIR` 外，还提供当前任务名 `MAESTRO_TASK_NAME`，脚本按任务名取本题的文件。包的典型结构：

```text
manifest.json        {"kind": "submission", ...}
bootstrap.sh         按 $MAESTRO_TASK_NAME 复制 submissions/<任务名>/ 下的文件
submissions/
  cad-part-a/output.step
  cad-part-b/output.step
```

清单中 `compatible_harnesses` 与 `effects` 只对模型 Harness 有意义，待评提交不要求填写。来源（哪次运行、哪个试次，或本地如何改写）写在包的说明里，平台不另外记录。

**平台不检查待评提交是否真的起到答案的作用。** 文件放到哪里、放了什么，由包里的脚本决定；平台只负责放进去、跑 verifier、记录结果。这与附件的 `effects` 一样是作者的声明，不是平台的保证。类别带来的是更明确的语义：

- 待评提交只能用于提交评分运行；普通附件不能当待评提交用，待评提交也不能加进模型运行或 Oracle 运行的附件列表。
- 网页与 SDK 按类别分开列出和选择，页面上叫“待评提交”，不叫附件。

### 2. 提交评分运行

新增执行方式 `submission`，页面称“提交评分”，不显示为 Oracle。规则沿用 Oracle：不需要也不接受模型配置、模型凭据和 Harness，不发出模型请求。

每个试次的顺序：准备并启动任务环境 → 复制、校验并安装待评提交 → 直接运行 verifier → 收集产物与清理。不执行 `solution/solve.sh`。

- 安装使用 [N-40](N-40-oracle-attachments.md) 的无 Harness 安装包装与安装网络，安装目录、任务用户、时限和传输规则与附件相同。
- 首版每个运行恰好带一个待评提交，不同时带普通附件；有真实需要时再放开。
- 换环境或换评分器时，改选另一个数据集版本、待评提交不变，再提交一次运行。按原配置重跑沿用现有规则。
- 沿用运行队列、CPU / 内存、并发、总时限、取消、幂等与资源释放规则；没有模型费用，仍占计算资源和 PAT 受理额度。

### 3. 失败与分数

- 待评提交安装失败或超时记 `attachment_failed`，没有分数，不运行 verifier，不记成 0 分；容器内副本不符与附件相同，算沙箱失败、可重试。
- 安装成功、verifier 判定交付物不合格，是有效 0 分；verifier 没产分数、超时或崩溃按既有规则区分。
- 缺题会被误读成有效 0 分：某题在包里没有文件，脚本什么都不放，verifier 可能对空输出打 0 分。平台不检查这一点，由 skill 给出的模板脚本防住：找不到本题文件时以非零退出，记为安装失败、没有分数。

### 4. 比较与集合

提交评分运行与 Oracle 一样，不能参与比较，也不能加入集合；比较与集合中“拒绝 Oracle”的检查改为“只接受模型运行”。逐题分数和日志在运行详情里人工对照。若以后需要比较这类分数，按 U-86 另行讨论。

### 5. 网页、SDK 与 skill

- 网页附件页按类别分开显示，上传时选择类别；新建运行选择“提交评分”后，选一个待评提交、数据集版本与任务范围，展示安装记录与日志。
- SDK 沿用附件上传与运行提交入口，增加类别和执行方式，同步 OpenAPI、生成模型与能力说明。
- `maestro-package` 增加一节“给已有提交评分”：从来源试次下载交付物，按模板组织待评提交，模板脚本在缺题时以非零退出，说明结果不能比较。

## 影响

| 部分 | 预期变化 |
| --- | --- |
| 附件与配置 | 清单增加类别；待评提交的清单检查；执行方式 `submission` 的配置检查与预检；比较与集合的准入改为只接受模型运行 |

| 系统说明 | 实施时改写 03、05、06、08、10、11、13、15；数据库变化只追加迁移 |

不新增评测记录、逐试次来源、文件映射协议或独立的输入保留规则。

## 验收

- 全新独立 state 中，以本地 fixture 上传一个待评提交，提交评分运行完成；确认没有模型请求、没有执行参考解，verifier 按放入的文件评分。
- 同一待评提交在两个数据集版本上各跑一次，得到两次独立运行；待评提交与来源运行不变。
- 文件不合格得到有效 0 分；安装失败、模板脚本遇到缺题时没有分数，不记成 0 分。
- 普通附件不能用于提交评分，待评提交不能加进模型或 Oracle 运行；提交评分运行被比较与集合拒绝。
- 取消、资源释放、幂等与只读 PAT 限制沿用现有规则；网页与 SDK 都能完成同一流程。验证不调用真实模型。

## 结果

已实现待评提交类别和 submission 执行方式，复用附件发布、存储、安装、引用保护与删除；安装后通过 Harbor 空 Agent 直接验证，不执行参考解。配置与两种包的互斥、有效 0 与安装失败无分数、仅 agent 可比较及加入集合均有回归覆盖。API、SDK、网页和 skill 已更新。新增真实 Docker 用例涵盖有效 1、有效 0 和缺题脚本失败，在真实 Docker 上通过（与 N-40 同一轮：2026-11-12，提交 `70e5564`，Harbor 0.24.0）；未新增评测对象、逐文件映射、逐试次来源或独立输入保留。
