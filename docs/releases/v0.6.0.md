# Maestro 0.6.0

按试次与环境阶段动态分配执行资源，让准备等待、较小的独立验证阶段和运行尾部及时交还容量。

## 更新后

- 数据库自动追加迁移 0014，保留已有结果、排队运行及冻结配置，不需要重新首次准备数据集。
- 建议使用网页更新，先排空在途工作。命令行强制更新或直接重启会按既有规则中断在途运行，保留已得评分；启动后先核对、清理遗留资源，再派发新尝试，不续跑旧容器。
- 执行容量仍需为系统、Runner 和镜像构建等开销留余量；本次调度限制试次环境的已授权资源，不限制整台主机所有进程的总资源。

## 破坏性变更

- 服务与 Runner 的执行协议升级到 v3，必须一起更新；使用完整发布包更新会安装配套 Runner。
- 数据库升级到 0014 后，回退旧程序需要恢复升级前的备份，不能只切回旧二进制。

## 新功能

- **按试次派发、按阶段分配容量**：每个 Runner 执行一个试次的一次尝试。准备等待不预占执行容量；执行环境停止后，独立验证按自身需求申请资源，共享验证继续保留原环境预算。较大的验证阶段可以先归还旧资源再等待。
- **运行先来优先，允许有限填空**：按运行受理顺序派发，在运行内组合资源互补的试次；空余资源可用于后续运行，等待保护限制持续越过较早或较大的请求。
- **平台统一重试与回收**：平台按冻结的错误策略安排重试和退避，未确认释放的资源持续占用容量；取消、Runner 失联和服务重启后先对账再释放。
- **容量与等待原因更清楚**：运行详情和管理页显示活动试次槽位、当前 CPU / 内存占用、环境阶段许可、填空及等待原因；API 与 SDK 同步提供这些信息。原有资源覆盖输入保持可用，旧运行原样重跑保留其容器限制。

## 修复

- 环境启动超时或取消时，继续跟踪尚未结束的启动命令；确认启动结束并完成清理后才归还容量，避免旧 Compose 命令晚创建容器。
- 回收站物理删除等待执行资源清理确认，避免丢失仍需回收的资源归属。
