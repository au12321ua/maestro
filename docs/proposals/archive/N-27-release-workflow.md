# N-27 发布流程与 CI 分工

状态：已完成 · 优先级：一 · 日期：2026-11-02 · 相关：U-66、U-67、[发布指南](../../guides/releasing.md)、[开发验证](../../guides/testing.md)、[部署运维](../../design/12-operations.md)

## 问题

`v0.4.0` 最终发布提交为 `a6cccbf`。该次发布暴露出版本准备、契约生成、tag 指向与开发版本收尾需要分别操作的问题；正式发布完成后，`dev` 仍保留正式版本声明，与开发预览版的构建要求冲突。现有流程写明了顺序，但缺少能准备完整候选、核对最终结果并继续失败步骤的统一入口。

代码检查与发布上传放在同一个任务中，使上传失败和源码检查失败共用一个结果。功能分支的 push 与 PR 又会触发重复检查；若只保留 PR 检查，直接 push 就失去覆盖。正式 tag 当前再跑完整检查，与已验证提交的检查也有重叠。

版本同时存在于源码、服务与 SDK 的包声明、锁文件和发布清单中。tag 本身不会修改这些值；仅给开发提交命名为正式版本，不能保证安装后的版本正确。上传脚本的重跑行为也不同：Gitea Release 会替换附件，SDK 包仓库拒绝覆盖，GitHub 创建已有 Release 会失败。

## 已确认的方向与范围

- 用户可以用“把 dev 的 `<commit>` 正式发布为 `<版本>`”表达发布意图。Agent 负责版本准备、最终提交验证、推进 `master`、创建 tag、两端发布及开发版本收尾；服务器部署继续单独进行。
- 采用源码中的单一权威版本，准备并验证最终提交后创建对应正式 tag。已共享的正式 tag 固定指向，已发布的同版本文件保持不变。
- 所有分支 push 是代码检查入口，PR 使用对应提交的结果；正式 tag 验证最终提交已有成功检查，并检查实际发布物。此项取代 U-43 中 tag 重复跑完整 CI 的要求，GitHub 从 tag 重建、不重复测试的约定沿用。
- 保留开发预览版、Gitea SDK 包仓库与 GitHub Pages 正式版索引。实现沿用现有构建工具与脚本，属于维护者发布工具，不增加产品 CLI 或 MCP 入口。

用户随后以“那继续，完成N-27”授权实施；实现与系统说明同步交付。

## 方案与取舍

### 1. 一个发布入口，两个确定的提交

维护者发布入口接受固定 dev 提交和正式版本。开始时解析完整 SHA、核对远端引用、版本是否已使用及当前发布状态，使用独立工作目录准备候选，保留其他工作区的修改。发布选定的内容范围不会随着 dev 后续推进而改变。

入口区分用户选定的业务提交与包含版本准备变更的最终提交：

| 阶段 | 动作与结果 |
| --- | --- |
| 准备 | 在选定提交上更新正式版本、锁文件和生成契约，准备发布说明及下一开发版本的变更；给出可审阅的最终候选与差异 |
| 验证 | 对最终候选取得完整代码检查成功记录，并完成该次变更需要的其他验收；版本准备产生新提交时，原提交的成功结果不能代用 |
| 推进主线 | 核对最新远端 `master`，将已验证候选快进到主线；无法安全快进或必须引入其他改动时报告差异，重新准备并验证，不强推或暗中扩大发布范围 |
| 正式发布 | 为最终提交创建附注 tag，推送后验证发布条件、构建与检查正式包，完成 Gitea Release 和 SDK 包发布 |
| GitHub 分发 | Gitea 发布成功后同步准确的 `master` 与 tag，由同一 tag 重建并发布 GitHub Release，再更新 SDK 索引 |
| 收尾 | 将正式版本准备改动带回 dev，并连同下一开发版本的修改一起推送，使远端 dev 的头保持开发版本；报告最终提交、各渠道链接与未完成步骤 |

发布说明在公开发布前准备，包含用户可见变化、破坏性变更、迁移要求及验证的实际覆盖。真实 Docker、Hub、模型和系统级安装测试仍按变更影响与既有授权选择，代码 CI 成功不代表这些项目全部通过。

下一开发版本在准备阶段生成，避免最后临时手改；未另行指定时建议下一补丁版本的 `.dev0`，发布入口在候选中明示这个值。收尾失败时记录并继续同一发布的收尾，不重新发布文件；dev 已有新提交时重新集成，不能覆盖后续工作。

这保留一次明确的版本准备提交，代价是发布候选可能与用户最初选择的 SHA 不同，收益是 tag 所指源码、检查对象和正式包具有一致、可查看的版本。

### 2. 一个权威版本，其他位置派生

建议以根 `pyproject.toml` 的项目版本为权威声明，服务运行时版本与 SDK 的版本声明由构建或准备过程派生。生成结果与锁文件一起进入候选，发布前核对源码、安装元数据、SDK 与发布清单，避免旧 editable 环境掩盖版本不一致。SDK 的安装与导入继续独立于服务源码。

正式版本与 `v<版本>` tag 一致。开发 SDK 继续沿用 `.dev<CI 运行号>`，同一次运行的重试使用原运行号；开发服务的基础版本与具体源码 SHA 由发布清单区分。Runner 的独立版本与修订保持其自身含义；网页中无实际用途的独立产品版本声明去除。

契约生成纳入版本准备入口，保留现有摘要算法与漂移检查。该提案不因版本自动化另行改变 API 兼容语义。

采用“源码决定版本、tag 校验版本”，不引入从 tag 推导全部开发版本的构建插件。构建可以直接读取已准备源码，也更容易配合已有锁文件和契约生成；代价是准备入口仍需生成并验证派生文件。

### 3. push 检查代码，tag 检查发布条件与产物

| 事件 | 代码检查 | 发布行为 |
| --- | --- | --- |
| 任意分支 push | 对该次推送的最终提交运行现有完整代码检查；保留纯 Markdown 例外及 SDK 文档、skill 的检查范围 | 功能分支与 master 不发布；dev 通过后构建并发布预览版 |
| PR 创建、更新 | 使用本仓库对应提交的 push 检查结果，不再次触发相同测试 | 无 |
| 合并产生新提交 | 新 SHA 按 push 规则检查，不能沿用合并前的结果 | 目标为 dev 时，通过后生成预览版 |
| 正式 tag | 核对准确的最终提交已有可信的完整代码检查成功记录；不重复执行源码全套检查 | 检查版本、构建正式包、验证产物，再发布 |
| 手动运行 | 对明确指定的提交重验，用于缺少自动运行、检查环境变化或主动复核 | 检查成功本身不自动成为正式发布请求 |
| GitHub tag | 不重复 Gitea 的源码测试 | 从同一 tag 构建、验证并发布附件，再更新 SDK 索引 |

发布任务从 Gitea Actions 读取本仓库预期工作流与必需任务的结果，核对完整源码 SHA 和实际成功的检查范围，并在日志中引用被复用的运行。其他任务的绿色状态、跳过的检查和旧 SHA 都不能代替。没有成功记录时等待检查完成，或明确停止并给出重验入口，不能默认为通过。

纯文档免检适用于日常提交；若这样的提交被选为正式发布候选，仍需先对准确 SHA 手动完成完整代码检查。PR 合入条件也需保留日常文档免检的既有边界，不能用不匹配的状态检查配置阻塞这类 PR。

PR 使用 push 结果需要核对 Gitea 实际记录的检查名称与分支保护。直接 push 的检查发生在推送之后，失败不会撤销分支更新；是否阻止直接更新受保护分支，沿用仓库协作边界并实时核对设置。合入前仍核对最新目标分支与候选，合并后的新提交照常检查。外部 fork 的代码不在现有宿主 runner 上自动执行。

代码检查与发布上传分别给出结果。发布任务检出相同源码提交，自行构建与验证发布包，避免依赖曾不可达的 CI artifact 跨任务传输；其构建环境继续使用既有隔离与缓存规则。代价是发布任务也需要初始化构建环境，但不重复源码测试，上传失败可独立继续。

第一轮允许同一 SHA 因跨分支 push 偶尔重复检查，优先消除 push 与 PR 的双触发及 tag 重跑全套。使用现有 Actions 记录判断发布资格，不增加独立的测试去重服务或检查结果登记库。

### 4. 验证实际交付的包

源码检查通过后，发布任务仍需验证本次构建的真实产物：

- tag、源码版本、服务与 SDK wheel 元数据、服务运行时版本及发布清单一致，清单记录准确的最终 SHA。
- 在全新隔离环境中安装实际 wheel，核对导入路径和版本，排除工作区源码、旧环境与 editable 安装的干扰；确认必要入口及包内网页可用。
- 包内容、许可证、锁定依赖和文件摘要完整；SDK wheel 与对应 Release 附件、包仓库内容一致。

这些验证覆盖从源码到安装物的转换，不能用源码测试代替；也不要求每次发布自动调用真实模型或操作已有团队 state。

### 5. 固定发布物，按阶段重试

正式 tag 创建并共享后不再移动。源码或发布内容需要修改时使用新提交、新版本；网络、上传或索引失败则继续同一提交和版本。

Gitea 与 GitHub Release 先准备草稿，附件及说明齐全后再公开。SDK 包仓库、Release 与 Pages 没有跨平台原子事务，发布入口逐项报告状态，全部目标完成后才报告发布完成。部分渠道已成功时保留成功结果，重试剩余阶段。

| 重试时的事实 | 行为 |
| --- | --- |
| 同一 tag、同一提交，目标附件不存在 | 补传缺失文件 |
| 同名附件已存在且摘要一致 | 跳过，继续缺失步骤 |
| tag 已指向其他提交，或同版本文件摘要不同 | 停止并报告冲突，保留原 tag 与文件 |
| SDK 已发布，Release 或其他渠道未完成 | 校验 SDK 摘要，继续未完成渠道 |
| Release 已发布，Pages 索引失败 | 单独重建索引，复用已发布 wheel |
| 发布完成，dev 收尾失败 | 核对最新 dev 后继续收尾，不重复创建正式 Release |

发布物保持固定需要解决当前归档中构建时间和文件元数据造成的摘要变化。实现应锁定影响产物的构建输入，规范 tar/gzip 等归档元数据，将每次执行时间留在 CI 运行记录中，使相同输入可得到相同产物；已有完整产物优先复用。不能通过覆盖旧文件来消除重建差异。

同一版本的发布任务串行执行，重试依据 Git 引用、Actions、Release、包仓库和 Pages 的实际状态恢复。开发预览版及开发 SDK 的最近 10 个保留规则沿用，正式版本不参与清理。写入令牌仍只交给必要发布步骤，不在公共文档、日志或发布包中保存凭据。

## 影响

- 维护者工具：调整 `tools/build_release.py`、`tools/publish_release.py`、`tools/publish_package.py`、`tools/package_index.py`，提供统一准备与续跑入口；实际入口名称和内部拆分按实现确定。
- 工作流：调整 `.gitea/workflows/verify.yml` 与 `.github/workflows/release.yml` 的触发、代码检查结果读取、构建验证和上传重试；实施时核对实际 Gitea 版本、检查名称与分支保护。
- 版本与生成物：根与 SDK 的包声明、服务版本读取、依赖锁和生成契约随准备入口同步；网页中无用途的独立版本声明去除。公开 API 的业务行为、数据库结构与部署布局不变。
- 文档：实施时改写[发布指南](../../guides/releasing.md)、[开发验证](../../guides/testing.md)、[协作规则](../../guides/development-workflow.md)、[部署运维](../../design/12-operations.md)与[开发交接](../../HANDOFF.md)，说明当前真实入口与限制；用户安装说明有变化时同步 SDK 说明与 skill。
- 交付：本提案实施合入 dev 时将结论并入系统说明、标记完成并归档；实施证据写入提交与 PR。CI 输出保留在 Actions，现场材料按既有规则放私有仓库。

## 验收

1. 以固定 dev 提交准备一个正式版本，候选明确展示最终 SHA、版本、发布说明及下一开发版本；dev 后续推进不会改变选定内容。无法安全推进 master 时保留现场并报告。
2. 版本准备产生新提交时，旧 SHA 的成功检查不能放行新候选；最终 tag、源码、实际安装的服务与 SDK、发布清单版本一致。
3. 未创建 PR 的直接 push 也有代码检查；同一提交随后创建或更新 PR 不额外跑相同测试；新的合并提交照常检查。
4. 正式 tag 使用准确最终提交的成功代码检查，日志可定位原运行，并执行产物验证；缺记录、错误 SHA、错误工作流、跳过或失败的必需检查均不能发布。
5. 发布上传失败时，代码检查仍有独立结果；开发预览版失败不会被误报为源码测试失败。纯文档例外与手动补验可按既有范围使用。
6. 在无工作区源码与旧 editable 环境的隔离环境中安装正式包，服务、SDK、必要入口及包内网页检查通过；只给开发提交打正式 tag 无法绕过版本检查。
7. 缺失附件可以补传，同摘要附件可跳过；同版本不同摘要、同 tag 不同提交均拒绝覆盖。构建输入相同时，重建的正式产物摘要一致。
8. 分别模拟 SDK 上传、Gitea Release、GitHub Release 和 Pages 失败，重试只补齐缺失步骤；已有成功发布物保持不变，不把部分成功报告为全部完成。
9. 发布成功后 dev 回到下一开发版本并能生成预览版；dev 有并发更新或收尾中断时可以安全续上，不强推、不丢失后续提交。
10. GitHub 从相同 tag 构建且不重复源码测试，两端正式 wheel 与对应索引摘要一致；正式版本不受开发预览清理影响。以上验证不依赖生产 state、真实模型调用或自动部署。

## 待定问题与实施前核对

无新增的用户方向选择。实现前核实以下平台条件，并把实际验证结果写入提交与 PR：

- 当前 Gitea 对 push 检查、手动运行与 PR 状态的关联、结果查询权限及检查名称；缺少自动运行时的可靠补验路径。
- 两端草稿 Release、附件摘要读取、独立重试与 SDK 索引更新所需能力；不假定现有脚本已满足。
- 锁定构建工具、规范归档元数据后，跨环境重建的一致性；平台限制导致设计无法成立时，说明限制和取舍，再调整方案。

未来是否改成 Gitea 构建一次、两端分发同一份文件，留待另行讨论；本提案保留 GitHub 按 tag 重建，避免现在增加跨站发布凭据与网络依赖。

## 结果

已实现统一准备、补验、状态与发布续跑入口，单一权威版本、独立检查与发布任务、准确 SHA 门禁、实际 wheel 安装验证、可复现归档和两端草稿续传。开发版本恢复为 `0.4.1.dev0`。实现与验证依据见同一合入 PR；未执行新的正式版本发布或服务器部署。
