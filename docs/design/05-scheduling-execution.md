# 05 调度与执行生命周期

导航：[总览](00-overview.md) · 依赖：[提交](04-plans-submission.md)、[评分](06-results-scoring.md)、[产物](07-artifacts-export.md) · 相关代码：`src/maestro/services/worker.py`、`src/maestro/services/scheduling.py`、`src/maestro/services/capacity.py`、`src/maestro/execution/resources.py`、`src/maestro/boundaries/executor.py`、`src/maestro/execution/harbor.py`、`runner/src/maestro_runner/resources.py`

## 1. 拓扑与职责

服务进程内的 Worker 是唯一的调度协调器。它按运行受理顺序派发就绪试次，持有运行租约，在短写事务中授予阶段许可、确认执行事件，负责重试、取消、到期和启动对账。SQLite 是事实来源。

运行是提交、排序、并发与取消的单位；试次是计划样本；执行尝试归属一次具体执行及其清理责任。每次派发只启动一个 Runner、执行一个 Harbor Job，Job 内只有一个试次、一次尝试、并发一，Harbor 重试关闭。服务进程不导入 Harbor。平台依据冻结策略重试同一试次，上一尝试的资源未确认释放前不开始下一尝试。

| 编号 | 要求 |
| --- | --- |
| EXE-01 | 持久队列，运行按受理顺序优先，允许有限填空；重启后恢复管理状态 |
| EXE-02 | 活动尝试满足运行并发和主机槽位；环境阶段满足 CPU、内存；模型阶段满足提供商限制。未满足：每成员 / PAT 的活动试次限制 |
| EXE-03 | 进度与日志按准备、执行、收集、验证阶段上报，资源归属按环境生命周期记录 |
| EXE-04 | 取消与总时限保留已完成结果 |
| EXE-05 | 意外重启不自动续跑容器，明确标记中断并清理 |
| EXE-06 | 执行资源带实例、运行、试次、尝试与环境阶段标签 |

## 2. 执行器接口与资源许可

Worker 与执行器之间是进程内接口（`src/maestro/boundaries/executor.py`）。`Executor.execute` 执行一个尝试；`cleanup` 按标签清理，`reconcile` 核对旧 Runner 身份并清理遗留资源。`RunSpec` 下发单个试次、尝试身份、阶段需求、冻结配置、总时限、标签和执行时才解密的凭据。凭据值不持久化、不写日志。

执行器通过 `ExecutionSink` 上报身份、心跳、阶段、日志、产物和结果，并申请与归还环境许可。`AttemptSink` 校验运行租约、服务代次、试次和尝试身份；过期消息不能修改新尝试。执行结果、产物保存、资源清理分别确认。

阶段需求从冻结的实际容器限制派生，不使用瞬时 CPU / 内存监控值。持久化 `stage_permits` 记录等待、已授予和已释放的许可；已授予尚未启动、执行中和释放未确认的许可都占容量。容器只能在许可提交后启动。

| 环境组 | CPU / 内存占用 | 归还条件 |
| --- | --- | --- |
| 启动、安装、Agent 执行、产物收集 | 主环境及同时运行的辅助服务 | 该组环境确认停止 |
| 共享验证 | 保持原环境及上限 | 共享环境确认停止 |
| 独立验证 | 验证容器及对应辅助服务 | 验证环境确认停止 |
| 阶段间等待 | 已停止的环境不占 CPU / 内存，活动尝试仍占槽位 | 获得下一阶段许可或结束 |

独立验证使用 `tests/` 镜像时计入 `tests/` 服务；回退主环境定义时计入重新启动的 `environment/` 服务。未声明资源的辅助服务使用团队默认限制。覆盖输入及旧快照的还原规则见 [03](03-configuration-attachments.md)。

Runner 停止环境后，执行器再按尝试、阶段标签清理并确认无残留，平台才归还许可。独立验证需求能放下时，旧许可归还和新许可授予在同一事务提交；更大的验证需求放不下时先归还旧资源，再等待，不能占住旧环境等待扩容。共享验证不缩减仍在运行的容器预算。

## 3. 调度与各种容量

Worker 循环先处理停止、到期和清理重试，再推进共享准备，领取运行租约并调度试次：

1. 运行领取只组织准备，不预留执行资源。各任务准备独立，先就绪的试次先加入候选；等待缓存不占 CPU、内存、活动尝试槽位或提供商额度。
2. 已启动尝试的验证续行优先检查，仍须满足容量。验证许可等待 30 秒后暂停新尝试，等待在途环境释放资源，防止较大验证环境被持续填空越过；其他已启动尝试仍可推进续行。
3. 新尝试按运行受理时间、持久化入队顺序选择。批次不是优先级分组；同一时刻的运行有稳定顺序。阶段切换和重试保留运行顺序，重跑是新运行。
4. 在同一运行内，依运行并发、槽位、提供商名额和 CPU / 内存余量选取互补组合。启发式搜索每个窗口最多 32 个候选、保留 128 个组合；评分同时考虑 CPU 与内存利用，同分优先较早候选。窗口放不下时继续检查同运行的后续窗口，再考虑后续运行。
5. 较早运行没有能利用余量的候选、仍在准备 / 退避或已达自身并发上限时，后续运行可以填空。候选等待 30 秒或被越过 8 次后受保护，暂停会妨碍它的新尝试，等待在途工作释放容量；已启动尝试仍可申请必要续行。阈值是当前实施策略，见 `scheduling.py`。
6. 检查容量、创建尝试、占用槽位和授予首阶段许可在同一短写事务完成，Runner 在提交后启动。磁盘低于派发水位或待更新时暂停新尝试，已有尝试继续收尾。

运行并发限制该运行的活动尝试数，主机槽位限制总活动尝试数；执行、等待验证和验证期间均占一个槽位，清理未确认时继续占用。CPU / 内存只统计有效环境许可。提供商名额在首阶段一并检查，模型调用确认结束后归还；共享多步骤任务仍可能再次调用模型，保留名额至尝试结束。Oracle 与提交评分不占模型名额。提供商限制不协调 RPM / TPM。

受理检查每个不可拆分环境组能否在空闲主机上执行，不要求整个运行的最大并发组合同时放下；不可能执行时返回 RUN_EXCEEDS_CAPACITY。实际并发可以低于请求的上限。容量总量由部署配置提供，管理员在网页调整提供商上限。

运行及试次显示等待原因，区分缓存准备、资源不足、运行并发、提供商限制、优先等待、重试退避和清理阻塞。排队不记作执行失败。运行占用是其许可之和，详情同时展示排序、填空与阶段许可。

### 已知限制

- 有限填空不抢占已启动容器，可能延后较早运行的下一试次；没有耗时预测，不保证最短完成时间。
- 构建只受独立恢复并发限制，CPU / 内存不计入执行容量；主机容量须为系统、Runner、数据库与出口控制等开销留余量。
- 没有每成员 / PAT 的活动试次限制，不提供多租户公平份额。

## 4. 运行与试次状态

运行：queued → preparing → running → finalizing → finished / cancelled / interrupted。有试次进入执行或验证后为 running。未领取的运行被取消或到期时直接结束。finished 表示全部试次已有终态，即使全部失败；到期停止也是 finished，用户或管理员取消为 cancelled，服务重启为 interrupted。运行的 Operation：取消为 cancelled，中断为 interrupted，自然结束时有有效评分为 succeeded、没有为 failed。

试次：queued → preparing → executing → verifying → scored / execution_error / not_started / cancelled / interrupted，reason_code 补充终结原因，queue_reason 说明等待。执行器步骤映射见 `STEPS`。产物与清理状态独立记录，不阻止确认结果。

状态只按允许的迁移前进，先被接受的终态生效，迟到阶段事件被忽略。平台判定重试时，当前尝试先终结，试次回到 queued；退避结束且清理确认后才重新竞争派发。最终获分仍只形成一个样本，不挑最高分。

## 5. 一次尝试的执行顺序

1. 领取运行后解密当前绑定凭据，不可用时以 CREDENTIAL_UNAVAILABLE 结束。每个任务独立申请缓存，共享恢复和失败处理见 [02](02-datasets-preparation.md)。
2. 材料就绪并获批首阶段许可后，启动单尝试 Runner。执行器核对任务与附件内容，缺失或不符时不执行。
3. Harbor 启动有许可的环境，按运行模式安装附件、执行和验证。模型运行收紧网络；Oracle 执行参考解；提交评分安装待评提交后直接验证。附件独立安装，不写回共享缓存。
4. 原环境完成收集并确认停止后，独立验证申请自己的许可；共享验证保持原许可。等待许可时心跳、日志和取消持续工作。
5. 尝试结束时 Runner 归档目录，执行器核对摘要、脱敏并保存产物和结果。交付物累计上限跨同一试次的多次尝试保留，保存失败不推翻评分。
6. Runner 退出后按尝试标签兜底清理。清理确认才释放槽位和剩余许可；需要重试时由平台退避并重新派发。全部试次终结后运行结束。

三种模式共用队列、计算容量、总时限、取消、幂等与资源释放规则。Oracle 与提交评分没有模型费用，仍消耗计算资源及 PAT 受理额度。

## 6. 租约与重复消息

运行租约不可复用，每次服务启动使用新 service_epoch。尝试和阶段许可都绑定具体身份；重复申请、授权和释放幂等，已释放阶段不能再次启动，旧进程与旧尝试不能修改新许可。结果按摘要去重，终态后的消息不能改写已确认评分。

Runner 长时间无事件、协议错误或管道丢失时，执行器结束其进程组并按标签清理。心跳超时不是释放证据。尚无结果的尝试按错误策略处理，平台是唯一重试决策者；Harbor 不在内部重试。

## 7. 取消、到期与清理失败

取消粒度为整个运行。未领取的运行在请求事务中直接结束；已领取的由 Worker 设置停止令牌。等待缓存时只退出本运行的等待，不终止其他等待者需要的恢复。Runner 收到 SIGTERM 协作取消，宽限期后 SIGKILL 进程组，再按标签清理；进程退出不能代替 Docker 清理。

总时限到期按取消处理。停止后不授予新环境许可，已有评分保留；执行过的未完成试次记 cancelled，未开始的记 not_started。Agent、验证、安装超时分别归类，见 [06](06-results-scoring.md)。

清理无法确认时运行照常结束，cleanup_state=failed，相关槽位与已授予许可仍占容量；从未授予的等待许可作废。Worker 定期重试，确认释放后才减账或重试下一尝试。旧版本留下的整体预留也保留到清理确认。回收站物理删除同样等待清理确认，不能删除仍承担占用或清理责任的尝试与许可。

## 8. 意外重启与对账

启动时先运行 `Worker.start_epoch` 和 `Worker.recover`，之后才派发：

1. 建立新代次，关闭旧运行租约。从未有尝试且未请求停止的运行按原顺序重新排队；全部试次已终态的正常结束；其余在途尝试记 interrupted，执行过的未完成试次记 SERVICE_RESTARTED，未开始的记 RUN_INTERRUPTED。已确认评分保留，不自动续跑旧容器。
2. 核对每个遗留尝试的 Runner PID、内核启动时间和 boot id，只停止确属原 Runner 的进程组，并确认进程不能继续启动容器。
3. 按尝试与阶段归属清理，再按实例标签兜底扫描，不触碰其他实例和无标签资源；未确认释放的许可与槽位继续计账。旧版本按运行保存的身份与预留同样对账。
4. 准备协调器和产物索引分别恢复管理状态，结果写入服务代次记录。对账异常时暂停派发，周期性安全重试。

重启不会自动新建运行或消耗 PAT 额度，用户可以创建重跑。

## 9. 停机与验收

手动停止或重启会中断在途运行；网页更新先暂停新尝试、等待在途工作结束，终端停止与更新不排空。关键验证覆盖阶段许可上限、独立 / 共享验证、运行顺序与有限填空、平台重试、准备独立推进、取消与评分竞争、管道丢失、重启、旧快照及迁移，见 [13](13-testing-plan.md)。
