# N-08 安装网络在管理页配置

状态：设计中 · 优先级：二 · 2026-10-28 · 相关：[12](../design/12-operations.md) 第 3 节、[03](../design/03-configuration-attachments.md) 第 7 节、[02](../design/02-datasets-preparation.md) 第 6 节、[11](../design/11-web-ui.md) 第 1 节、U-30、U-38；合并了原 N-10

## 问题

安装阶段的网络条件（镜像构建、Harness 自身安装、附件脚本能否顺利下载）取决于部署主机，现在只能写在 `config.toml` 里，改一次要 sudo 并重启服务。这和“管理员日常配置在网页完成”不一致。具体缺口：

- 准备代理 `setup_proxy` 只能在配置文件里改。
- 没有入口给包管理器指定镜像源。部署现场 OpenCode 的安装（nvm 下载 Node、`npm i -g`）经代理时常超时；只开 apt 缓存代理时整条链跑不完。另外注入 npmmirror 的两个变量后，裸 `ubuntu:22.04` 上 55 秒装完（2026-10-28，本机试验分支 `feature/setup-env`，一次样本，不合入，U-38）。
- 没有附件时，Harness 安装用的是 Harbor 写死的时限（多数 agent 为 360 秒），网络慢的主机没有办法放宽。
- 运行和准备记录只写“是否有代理”，事后看不出当时经什么网络装的。
- 网页看不到部署配置本身（[12](../design/12-operations.md) 第 3 节的已知限制）。

## 方案

把它们放在同一个管理分区里一起做，一次改完数据结构、接口和页面，避免出现“代理在网页、镜像源在配置文件”的中间状态。

### 1. 管理页“安装网络”分区

```
管理 · 安装网络                                    当前：第 3 版（auua，10-28 14:02）
┌──────────────────────────────────────────────────────────────────────────────┐
│ 准备代理       [x] 启用   http://10.0.0.5:3128                                │
│                不走代理   localhost,10.0.0.0/8                               │
│                用于：镜像构建、Harness 安装、附件脚本（Agent 与验证阶段从不使用） │
│                                                                              │
│ 安装变量       npm_config_registry      https://registry.npmmirror.com   [删] │
│                NVM_NODEJS_ORG_MIRROR    https://npmmirror.com/mirrors/node [删] │
│                [+ 添加]                                                       │
│                用于：Harness 安装、附件脚本（不用于镜像构建）                   │
│                                                                              │
│ Harness 安装时限  [ 600 ] 秒   （空 = 用 Harness 自己的默认值）                  │
│                                                                              │
│ 说明（写入修订）[ 换 npmmirror，nodejs.org 经代理常断               ]          │
│                                              [保存为第 4 版]                  │
├──────────────────────────────────────────────────────────────────────────────┤
│ 修订历史   第 3 版 … 第 2 版 … 第 1 版 …（每版可展开看完整内容与差异）            │
├──────────────────────────────────────────────────────────────────────────────┤
│ 部署配置（只读，来自 config.toml 与服务环境）                                   │
│   监听 127.0.0.1:8420 · 试次槽位 10 · 服务代理 已设置 · Docker 镜像源 未配置 …    │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **准备代理**：从 `config.toml` 移到这里，规则不变：只接受 `http(s)://主机:端口`，不能带用户名密码，不接受 SOCKS；写成 127.0.0.1 / localhost 时提示容器到不了。
- **安装变量**：环境变量注入，与代理一起只交给运行 setup 中的安装（Harness 自身安装与附件脚本），不交给镜像构建（Dockerfile 只看得到自己声明的参数），也不交给 Agent 与验证阶段。校验沿用试验时的规则：名字须是普通 shell 变量名；代理变量只能在上面一栏设；`MAESTRO_` 开头的名字留给平台；名字像凭据（含 token、secret、password、auth、key 等）或值里带 `user:password@` 的拒绝，因为 Harbor 用 `docker exec -e` 传变量，本机进程列表人人可见。
- **Harness 安装时限**：设了就作为 Harbor 的 setup 时限，有附件时再加上附件的安装与复制时间。空着保持 Harness 自己的默认值。
- **部署配置只读区**：显示 `config.toml` 的生效值与服务进程环境里“是否有代理”，`maestroctl check` 同时报告 Docker 守护进程是否配了 registry 镜像源，不代为修改。

### 2. 修订与记录

- 每次保存产生一个修订，带修改人、时间与说明，最新的生效。与团队策略分开成一条修订线：团队策略在受理时冻结进运行，安装网络则在**执行时**读当前修订（见待定问题 1），镜像源挂了，管理员换掉后排队中的运行和重跑都能用上。
- 每个执行尝试和每次环境准备都记下用的是第几版。修订的完整内容团队成员都能看到，因为里面不允许有凭据（见待定问题 3）。
- 不进运行配置与 `config_digest`：它是部署的网络条件，同一份实验配置换一台主机仍是同一份。

### 3. 本机缓存不需要平台再做

N-10 原本想做本机包缓存代理。有了安装变量之后，缓存就是部署方的事：apt 用缓存代理（如 squid）设为准备代理；npm、Node 若要不重复下载，在本机跑一个缓存型 registry（如 Verdaccio），把地址填进安装变量即可，平台不需要另外支持。

### 放弃的做法

- **在新建运行页或 SDK 里由成员设置**：镜像源是主机的网络条件，不是实验内容。算进实验配置，会让只差镜像源的两次运行在比较里分开，公开结果也换不了机器；不算进去，又成了成员能改、实验身份里却看不到的变量。成员也不知道这台主机上哪个源可用，而且等于让每个成员都能往容器里注入任意变量。
- **管理员预设几套、成员选用**：几个镜像源的安装结果应该相同，区别只在这台主机上能不能用。这个判断该由管理员在一处做，坏了在一处换。
- **继续放在 `config.toml`**：本机试验分支就是这样做的（`setup_env` 内联表），能用，但要 sudo 并重启，也看不出历史，作为短暂试验不合入（U-38）。

### 不放在一起的

- **N-09 Claude Code 与 Codex**：属于另一层，但依赖本提案，排在它之后。锁定的 Harbor 中，Codex 的安装命令写死 `NVM_NODEJS_ORG_MIRROR=https://nodejs.org/dist`，平台注入的变量优先级更高，能盖过它（读代码确认，未实测）；Claude Code 在 glibc 镜像上用 curl 从 `downloads.claude.ai` 下载，不走 npm，只能靠代理。
- **服务自身的代理**（`/etc/maestro/environment`，用于 Hub 下载、镜像仓库令牌与 Terminus 的模型请求）：它是服务进程的环境，改动牵涉面大，本次只在只读区显示是否设置。
- **N-12 排空更新**：无关；但本提案做完后，改安装网络不再需要重启。

## 影响

- 数据库：追加迁移，新增安装网络修订表；执行尝试与准备记录加修订引用（U-34）。
- 配置：`config.toml` 去掉 `setup_proxy`、`setup_no_proxy`；`maestroctl install` 去掉 `--setup-proxy`；`maestroctl check` 增加 Docker 镜像源报告。
- 接口：管理员读写安装网络的接口（只限网页会话，PAT 不可改），重新生成 OpenAPI、SDK 模型与网页类型；运行详情与准备记录返回修订号。
- 执行：Worker 派发时读当前修订，把代理与变量交给 Runner（现有 `setup_env` 通道），镜像构建只取代理。
- 网页：管理分区“安装网络”；运行详情的执行尝试、数据集的准备记录显示“安装网络 第 N 版”，可点开看内容。
- 系统说明：12 第 3 节、03 第 7 节、02 第 6 节、11 第 1 节、部署指南、交接。

## 验收

- 管理员在网页改代理或安装变量后，不重启，下一个开始执行的试次就用新修订；记录里能看到版本号与内容。
- 非法输入（凭据、代理变量、`MAESTRO_*`、SOCKS、非法名字）在保存时被拒绝，并指出是哪一项。
- 安装变量出现在 Harness 安装与附件脚本中，不出现在镜像构建参数、Agent 与验证阶段（沿用现有代理边界测试的做法）。
- 部署现场：裸 `ubuntu:22.04` 任务经 OpenCode 跑通一个试次，安装在时限内完成（需真实模型，按当时授权）。

## 待定问题

1. 安装网络在执行时读当前修订（推荐），还是像团队策略一样在受理时冻结？前者能救排队中的运行，后者让“同一次运行”的条件更固定。
2. 已有部署的 `config.toml` 里还留着 `setup_proxy`：新版本**忽略旧键并在启动日志提醒**、由管理员在网页重新填写（推荐，最简单，也不会因为配置不认而触发更新回退）；还是首次启动时自动导入为第 1 版？
3. 成员能否看到代理地址与镜像源的具体值？推荐能看到（不含凭据，便于排查）；现在的记录有意只写“是否有代理”。
4. 安装变量要不要按 Harness 分开写（例如 npm 镜像只给 OpenCode 和 Codex）？推荐首版全局一份，N-09 时再看是否需要。
5. 保存前要不要提供“试一下”：起一个临时容器，经新设置访问几个地址并报告结果？有用，但要用 Docker，可以放到后续。
