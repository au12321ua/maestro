# N-01 独立验证环境、Compose 辅助服务与按内容寻址的镜像存储（吸纳 N-14）

状态：设计中 · 优先级：一 · 2026-10-28 · 相关：[02](../design/02-datasets-preparation.md) 第 3、5～8 节、[05](../design/05-scheduling-execution.md)、[09](../design/09-identity-security.md) 第 5 节、[12](../design/12-operations.md)、[15](../design/15-stack-harbor.md)、[14](../design/14-decisions.md) U-30、U-32、U-53

## 问题

现在一个任务只准备一个镜像（主环境），存成一份 `docker save` 归档，运行时 Runner 把任务副本指向这个镜像，Harbor 不再构建或拉取。Harbor 0.24.0 还有两种起容器的方式，平台没有覆盖：

**独立验证器**（`[verifier] environment_mode = "separate"`）：Agent 阶段结束、收集完产物后，Harbor 停掉 Agent 的整个环境（主容器与辅助服务），另起一个容器跑 `tests/`，只传入声明的产物。作者用它防止 Agent 改动判分条件，或把判分所需的重型工具与 Agent 环境隔开（mesh2cad-smoke 就是这样）。验证容器的镜像按 `harbor/models/task/verifier_mode.py` 的顺序决定：

1. `[verifier.environment]` 给了 `docker_image`：用这个镜像；
2. `tests/` 下有 `Dockerfile` 或 `docker-compose.yaml`：从这里构建；
3. 都没有：照主环境再起一份全新的容器（用同一个镜像）。

**Compose 辅助服务**：`environment/docker-compose.yaml`（以及第 2 种验证器的 `tests/docker-compose.yaml`）中 `main` 以外的服务，例如数据库或模拟接口，可以是 `image:` 也可以是 `build:`。

现状与缺口：

- 第 1、2 种独立验证器在导入检查时标为不支持，首次准备以 `PREPARATION_UNSUPPORTED` 失败。
- 辅助服务的镜像不经平台准备，运行时由 Compose 隐式构建或拉取：内容不固定、依赖外网、上游删除后无法运行，也不计入容量。这类任务目前可以准入。
- 第 3 种目前不被拒绝。但 Harbor 创建独立验证环境时清空了 Job 的 `extra_docker_compose`（`trial.py` 的 `_separate_verifier_env`），平台的清理标签与网络收紧补丁都不会作用到验证容器。**这是读代码的推测，尚未实测**；实施时先用真实 Docker 确认，确认后作为缺陷一并修复。
- 准备结果按任务存一份完整归档：多镜像的任务需要“成组”保存与恢复；内容相同的镜像和共用的基础层在每个任务里各存一份（原 N-14 的问题；`fix/separate-verifier` 估算 mesh2cad-smoke 每任务约 9 GB，未实测）；回收只删本机镜像、归档仍在，并不省总磁盘。

远端分支 `fix/separate-verifier`（`bfe2885`、`34a1293`）实现过“成组准备 + 每个环境目录一份 Compose override”，只作参考，不合并（U-32）。它为兼容已有缓存保留了两条准备路径；用户已决定不兼容、全部重新准备（U-53），本提案只保留一条。

## 复杂度从哪来

1. **平台与 Harbor 对镜像来源的约定不同**：Harbor / Compose 按任务定义在运行时构建或拉取，平台要求事先准备、运行时不构建不拉取。每多一种起容器的方式就要多一处补丁（任务副本、改写 `task.toml`、Compose override、在 Harbor 丢掉 override 的地方补回）。这部分是固有的，只要使用 Harbor 且坚持运行时不构建就躲不开，但较为机械。
2. **存储单位是“一个任务一份 tar 包”**：成组校验、缺一个怎么办、跨任务重复、`save` / `load` / 核对 / 重建比对，都源于此。Docker 本身按层内容寻址，打成 tar 包放弃了这个能力。
3. **为兼容维持两条路径**：已由 U-53 去掉。

## 方案

### 一、镜像按内容寻址，存进本机镜像仓库（建议，待用户在两种存储中选定）

思路与 N-06 附件相同：从“每版本一个包”改为按内容寻址、只存一份。

- **存储**：本机运行一个标准镜像仓库（Docker 官方 `registry`，数据在 data 目录下，只监听本机），由 `maestroctl` 安装、启动和检查。准备一个镜像 = 构建或拉取 → 推入本机仓库 → 记下 digest。仓库按层去重：任务之间共用的基础层、同一个 `postgres:16` 只存一份。
- **任务的准备结果**：一张镜像清单，每项是“角色 + digest”，角色为主环境、验证器、各辅助服务（含验证器侧的服务）。第 3 种验证器复用主环境一项。只有主环境的任务就是只有一项的清单；所有任务走同一条路径。
- **相同定义只构建一次**：作者定义完全相同（环境目录内容摘要、冻结的构建参数、准备方式相同）的构建在任务间复用同一结果，例如同一数据集共用的验证器镜像只构建一次。只按内容精确匹配，不做 Dockerfile 语义比对（沿用原 N-14）。拉取的镜像按上游 digest 天然共享。
- **运行**：Runner 为每个环境目录生成 Compose override，把每个服务钉到 `本机仓库/…@sha256:…`、去掉 `build:`（实测 Compose 在镜像缺失时即使 `pull_policy: never` 也会构建）、加平台标签与资源限制；不改写作者文件（PyYAML 的 YAML 1.1 与 Compose 对 `yes`、`22:22` 等写法解读不同）。override 需要 `!reset`，即 Docker Compose 2.24 以上，`maestroctl check` 检查。在 Harbor 创建独立验证环境处补回 override 与标签。
- **回收与恢复**：Docker 本地镜像随时可删，使用时按 digest 从本机仓库拉回；去掉 `docker save` 归档及其核对、加载、重建比对代码。本机仓库也缺失时，按固定的上游 digest 重拉或重建，内容不同仍拒绝（沿用 02 第 5 节）。
- **清理**：数据库记录每个 digest 被哪些任务引用；不再被引用的由仓库垃圾回收删除。官方仓库的垃圾回收要求期间没有写入，放在没有准备在进行时执行。
- 异机备份恢复（N-21）以后只需同步仓库目录。

代价：多一个常驻组件，它不可用时已回收的镜像无法恢复（未回收的照常运行）；垃圾回收的时机要处理；准备层整体重做，范围比“补两种任务”大，但删掉的代码多于新增。

**轻量折中**：保留 tar 包，改为每个镜像一份、按 digest 命名并引用计数。不加组件、改动小；但只有完全相同的镜像能共享，基础层仍重复，“成组”问题仍在。

### 二、准备时的规则

- 辅助服务的可变标签（`postgres:16`）在首次准备时固定为 digest；`build:` 的服务在准备时构建。
- 影响镜像内容的 Compose 变量（`image:`、构建参数中的 `${X:-默认}`）按默认值冻结进准备规格，成员不能修改（U-53）；没有默认值或默认值是秘密的不能准备，报错指出文件位置与变量名、不含值。只影响运行时环境的变量照旧作为作者参数由成员填写。
- 构建选项中不改变镜像内容的（`labels`、`cache_from`、`cache_to`、`tags`）忽略，其余拒绝。构建上下文限于对应环境目录。
- 任何一项必要镜像无法准备，整个任务首次准备失败。

### 三、运行与容量

- 辅助服务未声明 `cpus` / `mem_limit` 时，平台以 override 施加默认上限并按该值计入容量（U-53）；默认值放团队策略，管理员可改。作者声明了的按作者值。
- 容量按主环境、验证器与全部辅助服务之和保守预留（U-53），不按“先停 Agent 环境再验证”的峰值计算。提高资源覆盖时，额外预算给主环境，验证器与辅助服务保持各自上限（沿用分支做法）。
- 独立验证容器与 Agent 环境一样按任务声明的验证阶段网络策略再由平台收紧；自带网络、会绕过出口控制的服务沿用现有规则，以 `NETWORK_POLICY_UNSUPPORTED` 拒绝。
- 验证容器、辅助服务及其网络和卷都带平台标签，取消或崩溃后按标签清理；卷加入清理范围。
- 多步骤任务的步骤自带环境仍不支持，不在本提案范围内。

### 四、已有数据

不兼容（U-53）：上线时迁移把所有准入重置为待准备，删除旧的准备记录与归档，管理员重新首次准备。此前因独立验证器被拒的任务同样重新准备即可，不需重新导入。发布说明列为破坏性变更。

## 影响

- 系统说明：02（准备规格、三类事实、恢复与回收、已知限制）、05（容量）、09 第 5 节（验证容器网络、卷清理）、12（本机仓库的安装、检查、垃圾回收与备份）、15（Harbor 边界与 override）、13（新增验收场景）。
- 数据结构：准备结果由单个镜像加归档改为镜像清单；新增 digest 引用关系；迁移重置准入。
- 部署：`maestroctl` 安装与检查本机仓库、要求 Docker Compose 2.24 以上；备份恢复覆盖仓库目录。
- 接口：准备与任务详情中显示镜像清单；团队策略增加辅助服务默认资源。

## 验收

- 本地 fixture 任务的真实 Docker 测试（全用 Oracle，不调模型、不花钱）：三种验证器镜像来源各一个；一个辅助服务用 `image:`、一个用本地 `build:`；验证器侧带辅助服务一个。确认执行期间没有构建与外部拉取，结束后容器、网络、卷按标签清空。
- 先单独确认上文第 3 种验证器丢失 override 的推测，结论写进实施记录。
- 两个任务共用同一验证器定义时只构建一次；删除本地镜像后从本机仓库恢复为同一 digest；去掉引用后垃圾回收释放空间。
- 已有实例升级后所有准入回到待准备，重新准备后可运行。
- 现场主机上以 mesh2cad-smoke 做一次端到端测试（Oracle），记录实际磁盘占用。

## 待定问题

1. **存储方式**：本机镜像仓库（建议）还是轻量折中（每镜像一份 tar 包、引用计数）。用户待定。
2. 选本机仓库时，先在有 Docker 的主机上用全新独立 state 做小实测（开发机的 WSL 中没有 Docker）：系统 Docker 是否默认信任 `127.0.0.1` 上的 HTTP 仓库；推入与拉回速度；与 tar 包相比实际省多少磁盘；垃圾回收在只读模式下的流程。不碰现场 state。
3. 辅助服务默认资源上限的具体数值（例如 1 CPU、1 GB）。
4. 本机仓库运行方式：作为容器由 Docker 管理，还是由 `maestroctl` 安装独立的 `registry` 二进制并作为 systemd 服务。
