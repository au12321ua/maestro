# N-06 附件整包下载与 Git 来源发布

状态：设计中 · 优先级：一 · 目标版本：0.4.0 · 2026-10-28 · 相关：[配置与附件](../design/03-configuration-attachments.md)、[权限](../design/09-identity-security.md)、[API 与 SDK](../design/10-api-sdk-cli.md)、[网页](../design/11-web-ui.md)、U-48

保留压缩包上传和现有附件展示，增加整包下载；新增按仓库地址和确切提交发布附件的入口。代码的修改、协作和历史由 Git 仓库管理，Maestro 保存实验实际使用的附件版本。

用户已明确的范围见 U-48；本文其余方案是供审阅的建议，尚未授权实施。

## 问题

现有附件只能上传和查看文件清单，无法从网页下载。改一个脚本也要在本地重新打包、上传整个包；已有 Git 仓库的团队还要额外维护发布压缩包的步骤。

用户将 N-06 纳入 0.4.0 核心功能，并把范围收敛为下载和 Git 来源添加。原先讨论的目录树、内容预览、网页编辑、版本差异查看不纳入本次；这些操作可以在源码仓库中完成。

## 方案

### 1. 两种添加来源，同一套附件版本

附件页继续使用现在的列表和展开的文件清单，在发布区提供“上传压缩包”和“从 Git 添加”两个入口，每个可下载的版本增加“下载整包”。

| 入口 | 用户提供什么 | 发布结果 |
| --- | --- | --- |
| 上传压缩包 | 现有的 tar / tar.gz / zip 包 | 沿用现有校验和发布流程 |
| 从 Git 添加 | 仓库地址、完整 commit hash、访问配置；建议可选附件子目录 | 导出指定提交中的附件文件，校验后发布为同一种附件版本 |

附件名称、版本和兼容信息继续取自附件根目录的 manifest.json。新入口不增加另一套版本号，也不把每次 Git 提交自动变成附件版本。

### 2. 按需下载完整内容

建议统一下载 ZIP，文件名包含附件名称和版本。归档根目录直接包含 manifest.json、可选的 bootstrap.sh 及其余附件文件，保留相对路径、文件字节和可执行位；两种来源采用同样的下载方式。

下载包按点击时保存的附件内容重新生成，与最初上传压缩包的字节和格式可以不同。在现有上传大小限额内，重新上传未改动的下载包，应识别为同名同版本同内容，返回已有版本。

生成前检查内容完整性；缺文件或摘要不符时给出明确错误，用户可通过重新提交原内容修复。下载不会触发向远程仓库取内容，也不会把 Git 历史或访问凭据打进包里。

归档按需生成，完整生成后开始传输，结束或失败后清理临时文件；生成过程有大小、时限和并发限制。与物理删除并发时，只能成功取得完整内容或明确失败，不返回缺文件但看似成功的归档。

已停用版本仍可下载；回收站中版本的下载仅向管理员网页会话开放；物理删除后明确显示内容不可用，即使其他版本的存储或 Git 缓存中还有相同文件，也不能绕过删除标记下载。

### 3. 从指定 Git 提交发布

用户选择“从 Git 添加”，填写仓库地址和完整 commit hash，选择访问配置；公有仓库可选择匿名访问。建议支持相对于仓库根目录的附件子目录，留空表示根目录，便于一个仓库维护多个附件。

提交后显示一次可查询的导入进度：等待、获取提交、导出与校验、发布完成或失败。导入请求支持幂等，断线后重试同一请求返回同一次导入。只有全部校验通过，版本才出现在可选附件中；获取和校验不运行仓库或附件里的脚本。

服务获取并核对确切提交，导出选中目录中的文件，再执行与压缩包相同的附件检查。只接受完整的 commit hash，不接受短哈希、分支名或标签。远端找不到该提交、拒绝提供它或在限额内无法获取时，导入明确失败，不能改用分支当前内容。

成功后保存一份完整的附件内容。运行、重跑和下载都读取这份内容；源仓库被删除、历史被重写、访问凭据被停用或 Git 缓存被回收，不影响已保存版本。附件本身被停用或删除时，仍按现有规则限制使用。

发布后显示仓库地址、确切提交和附件子目录，方便用户在自己的仓库平台查看源码和历史。添加后续版本时可沿用这些输入，填入新的提交，再显式发布。

### 4. 版本身份与来源分开保存

版本继续遵循现有规则：

- 同名同版本同内容，复用既有附件版本；同名同版本内容不同，拒绝覆盖并提示修改 manifest 中的版本号。
- Git 提交变化而选中目录内容不变时，不因此制造新的附件版本。
- 压缩包与 Git 内容相同时，采用相同的内容身份。重复导入只记录本次来源和结果，不改写已有版本的原始来源、发布者或发布时间。
- 在回收站中的同名同版本仍须先恢复或改版本号，不能用 Git 导入绕过回收站。

仓库地址、commit、子目录和获取时使用的访问配置用于追溯。附件内容摘要继续覆盖文件路径、字节和可执行位，来源信息不进入内容摘要或运行生效配置。

N-11 的集合和比较继续按现有附件维度核对名称、版本、内容等条件；不会因来源仓库或 SSH 私钥不同而增加条件差异。已有集合规格与分析快照不需要回填 Git 信息。

### 5. 管理员配置 Git 访问

管理员在网页维护命名的 Git SSH 访问配置，包含私钥、适用的 Git 主机与端口、用于验证服务器身份的主机公钥。支持多个配置，成员和 experiment PAT 只选择配置名称；私钥保存后不回传。

私钥沿用团队凭据的加密、轮换、停用和删除机制，新增专门的 SSH 私钥类型和校验。配置与 Git 主机绑定，只在绑定主机的连接中使用该凭据，连接时严格验证管理员配置的主机公钥；不自动信任新出现或变更的主机公钥。建议管理员使用只读部署密钥。

成员可用团队配置读取该密钥本来有权读取的仓库，发布内容全团队共享。这项权限用于 Git 附件发布；Hub 数据集检索与导入仍按 U-20 只向管理员开放。

凭据在任务实际获取仓库时解析当前可用修订，并记录所用修订。停用或删除后不能启动新的获取；已发布附件仍可使用。进行中的导入使用该凭据时，删除须等导入结束或先取消；已经建立的连接不承诺因停用而立即断开。

SSH 私钥仅在服务端获取仓库时临时使用，不进入附件、Git 缓存配置、运行容器、下载包或日志。带口令私钥本次不支持，保存时明确提示。

### 6. 缓存、失败与恢复

服务端保留有容量限制、可回收的仓库缓存，后续获取新提交时复用已有 Git 对象，减少重复传输。缓存命中仍须检查当前访问配置，并通过远端认证和主机校验，不能绕过凭据停用。已发布附件的完整文件独立保存；首次获取仍需下载所需对象，频繁变动的大型二进制文件不保证明显节省流量。

获取总时限、并发、缓存与临时空间有部署上限；导出的附件沿用现有文件数量和内容大小限制。达到限制、远端无法访问、认证失败或主机公钥不符时，进度显示原因，清理本次临时材料，不留下可选的半成品版本。

取消由导入者或管理员发起；取消成功后不再发布结果。服务重启时尚未完成的导入标为中断，用户可以重试；发布与完成记录要保持一致，重试不能重复创建版本或覆盖并发发布的内容。

导入计入在途工作，更新或停服检查能发现它。凭据、导入记录与附件的删除按现有两步回收站规则处理；导入记录进入回收站前须先取消或等待终态。物理删除附件时也安排清理其来源仓库缓存，不能因缓存仍在而保留下载入口。其他已发布版本仍从各自保存的内容使用。

### 7. 权限与范围

| 操作 | 成员网页 | 管理员网页 | read PAT | experiment PAT |
| --- | --- | --- | --- | --- |
| 查看与下载正常附件版本、查看 Git 来源 | 允许 | 允许 | 允许 | 允许 |
| 发起 Git 导入 | 允许 | 允许 | 禁止 | 允许 |
| 取消 Git 导入、导入记录进回收站 | 本人的 | 含他人的 | 禁止 | 本人的 |
| 管理 SSH 访问配置、回收站恢复与物理删除 | 禁止 | 允许 | 禁止 | 禁止 |

导入记录与进度按团队业务记录可读；写操作保留个人和 PAT 身份。read PAT 不发起向外部仓库的获取。附件启停和删除的归属限制沿用现有规则。

本次采用现有附件页的展示方式。代码浏览、版本差异和编辑仍通过源仓库完成；Maestro 不提供 Git remote、分支合并、自定义增量上传或自动跟踪分支更新。上述边界用于落实本次收敛范围，不影响将来单独讨论。

**已定待补项**：Git LFS、子模块、带口令 SSH 私钥。首版遇到选中附件目录内的 LFS 文件或子模块时明确拒绝并说明原因，不能把 LFS 指针当成真实文件、忽略子模块或自动访问额外仓库；仓库其他目录的此类内容不阻止导入一个完整的普通附件目录。

## 验收

1. **原流程与下载**：现有压缩包发布、文件清单和启停操作保持可用；成员与 read PAT 均可下载完整附件，包含原始 manifest、路径、文件字节和可执行位；在上传大小限额内直接重新上传下载包返回已有版本。
2. **Git 来源发布**：从 SSH 私有测试仓库取得指定提交的附件；网页与 SDK 返回相同版本及来源，安装时核对的内容与该目录一致；仓库脚本不在导入时运行。若采用匿名 HTTPS 推荐方案，另验证公开仓库。
3. **确切提交与目录**：分支继续前进时，导入旧提交仍得到旧内容；短哈希、分支名、标签、缺失提交明确失败。若支持可选子目录，根目录和子目录都能发布，非法路径与缺 manifest 明确失败。
4. **唯一性与重复来源**：同内容的压缩包、Git 提交或其他仓库复用已有版本；导入记录保留本次来源，原来源与发布者不变。同名同版本内容不同被拒绝，失败操作不发布附件。
5. **后续版本与离线使用**：更改 manifest 版本并选择新提交后得到新版本；旧运行和快照不变。关闭源仓库、停用私钥并回收 Git 缓存后，已保存附件仍可下载与执行；需要完整文件的备份恢复同样可用。
6. **SSH 凭据**：管理员可配置、轮换和停用私钥，成员只能选名称；主机不匹配、主机公钥不符、密钥无权访问、带口令私钥都有明确错误。响应、普通日志、归档、Git 缓存配置及运行输入中无私钥。
7. **权限与删除**：read PAT 能下载但不能导入、取消或管理凭据；成员不能取消他人的导入。正常、停用、回收站和物理删除状态的下载权限符合正文；仍被其他版本共享的文件不能绕过某版本的删除标记。
8. **中断与并发**：覆盖获取超时、超限、取消、服务重启，以及请求断线后的幂等重试、重复导入、同版本并发发布和下载与清除竞争；没有半成品可选版本、迟到发布、静默缺文件或遗留私钥临时文件；更新检查能发现活动导入。暖缓存导入复用已有 Git 对象，但仍通过本次认证，凭据停用或失去仓库访问权后不能用缓存继续导入。
9. **待补类型**：选中目录含 LFS 指针或子模块时明确拒绝；不能把不完整目录发布为成功。选中目录外的此类内容不影响一个完整目录的导入。
10. **N-11 回归**：仅来源提交或访问配置不同、附件内容和既有比较字段相同的运行，集合核对与比较结果保持一致；来源信息不混入固定维度，原分析快照不变。

验证使用全新的隔离 state、测试密钥和测试仓库。先用本地临时仓库及受控 SSH / HTTPS 服务验证协议与失败行为，再按部署依赖核对目标 Git 服务；真实私仓与真实凭据不作为默认测试前提，不需要模型调用。

## 待定问题

用户已明确 LFS、子模块和带口令私钥后补，不再作为本次待定问题。

| 问题 | 推荐 | 取舍 |
| --- | --- | --- |
| 首版仓库访问方式 | 支持 SSH 私钥访问与匿名 HTTPS；私有 HTTPS 的 token / 密码认证后补 | 覆盖已提出的私仓需求及公开仓库；团队凭据先只增加 SSH 类型 |
| 是否支持附件子目录 | 支持，可选，默认仓库根目录 | 允许一个仓库发布多个附件；每次仍只导出一个含 manifest 的完整目录 |

ZIP 下载、manifest 定义名称与版本、命名的主机绑定 SSH 配置等是本提案的推荐设计，随整体提案审阅确认；未填写新的数值默认值，实施时按现有限额分类与测试确定。

## 实现草图（供开发核对）

以下为可调整的实现安排，不增加正文之外的产品要求。现有依据为 N-11 合入后的 dev，26a638a。

- 附件发布：复用 src/maestro/services/attachments.py 的校验、版本冲突、发布事务与审计，压缩包和 Git 目录在进入发布事务前形成同一种已检查内容。重复来源写入导入记录；已有版本的来源不被覆盖。
- 文件内容：沿用 src/maestro/execution/attachments.py 的文件索引、摘要及存储；Git 以树与文件对象导出普通文件和可执行位，不执行 checkout 过滤器或仓库 hooks。沿用路径和链接检查，明确拒绝选中目录的子模块与 LFS 文件；不靠有损的导出选项忽略文件或替换文本。
- 下载：按需生成临时 ZIP，写入可执行位和原始文件字节；读取期间保护版本内容，与回收站清除协调。发送响应头前确认归档完整，结束或异常时释放临时材料；包字节摘要与附件内容摘要分开表达。
- Git 获取：单独的服务端适配器管理 Git 子进程与仓库缓存，不放进 Harbor Runner。只接受支持的网络 URL，拒绝 URL 中的密码、本地文件路径和自定义 remote helper；显式构造命令参数，隔离继承的 Git / SSH 配置、交互认证与代理命令。对网络、进程树、磁盘和缓存占用设置边界；同一缓存并发获取串行化，缓存按仓库与访问配置隔离。
- 来源与身份：追加附件来源及导入记录迁移，不重写已有迁移。已部署版本的来源回填为 upload；运行生效配置和 src/maestro/services/configuration.py 的 comparison_view 不增加 Git 字段，避免影响 N-11 维度与快照。
- 凭据：src/maestro/services/credentials.py 当前仅支持单行值，需按凭据类型分别校验，新增可存多行 SSH 私钥的专用类型，保留其他凭据原约束。主机、公钥和凭据引用作为 Git 访问配置保存；复用主密钥加密和修订机制，不另存明文长期文件。加入在途导入的凭据删除检查。
- 后台任务：增加导入业务记录与 Operation，复用请求幂等机制，使用有界后台执行，不在 HTTP 请求或数据库事务内等待 fetch，也不阻塞产物回收。受理和取消检查权限，发布前复核任务状态与版本冲突；记录实际取用的访问配置与凭据修订；启动对账处理未完成导入、Git 子进程与临时文件。终态导入记录按正文进入回收站，删除记录不级联删除已发布附件。
- 接口与客户端：在 src/maestro/api/routes/attachments.py 和公开模型中增加下载、来源及导入资源；同步 SDK 手写方法、OpenAPI 和生成模型、网页类型及 test_sdk.py 登记。具体接口与字段在实施时由契约表达，本提案不另维护接口清单。
- 运维：Git 缓存与临时目录同附件原件分开放置，备份继续保存附件完整内容和凭据密文，排除可重建缓存及临时私钥；备份不包含外置主密钥。现有 backup.activity 统计非 run / batch / export 的活动 Operation，新增导入应纳入它并补验；安装检查增加 Git 与 OpenSSH 可用性。
- 文档验证：本提案只检查 Markdown 相对链接与差异空白；实施时按正文验收，补充附件、凭据、回收站、恢复、SDK 契约和网页操作检查。Git 服务器对历史提交获取的限制、ZIP 可执行位往返和目标主机的 SSH 行为须实际验证，失败不得用最新提交或不完整文件替代。

| 决定 | 原因 | 可观察结果 | 可能的实现位置 |
| --- | --- | --- | --- |
| 两种来源复用附件版本 | 保持发布与实验选择一致 | 同内容复用，同版本异内容拒绝 | attachments 服务与存储 |
| 保存完整发布内容，Git 信息作来源 | 运行不依赖上游或访问密钥持续有效 | 仓库离线、缓存清理后仍可使用 | 附件存储、来源迁移、备份 |
| 从确切提交导出并检查 | 固定实验材料，避免缺文件 | 不跟随分支，不静默忽略 LFS / 子模块 | Git 适配器与内容校验 |
| 管理员维护主机绑定 SSH 配置 | 团队共用私仓访问，私钥不回传 | 成员选名称，主机校验失败明确报错 | credentials、管理页、Git 适配器 |
| 有进度、可取消的导入 | 网络操作需要可观察与恢复 | 失败无半成品，更新能发现活动导入 | 导入服务、Operation、启动对账 |
| 下载保留原始内容与可执行位 | 支持检查和再次发布 | 下载包重新上传识别为原版本 | 附件下载路由与 ZIP 生成 |
